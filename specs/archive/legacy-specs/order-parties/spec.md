# Отправитель и получатель складских ордеров

## Результат

Пользователь видит наименование отправителя приходного ордера и получателя расходного ордера независимо от того, в каком из четырёх справочников 1С хранится сторона.

## Правила разрешения

- Ордер хранит ссылку как пару идентификатора 1С и `PartyType`; полиморфный внешний ключ EF не создаётся.
- `PartyQueryService` разрешает склады, партнёров, физических лиц и подразделения в единый `PartyInfo`.
- Пакетный `GetManyAsync` принимает составные `PartyReference` и группирует запросы по типу, поэтому количество запросов к БД не зависит от числа ордеров на странице и не превышает числа используемых типов.
- Одинаковые идентификаторы в разных справочниках различаются по `PartyType`.
- Деактивированные записи продолжают разрешаться для отображения исторических ордеров.
- Группы справочника физических лиц не являются допустимыми сторонами и не разрешаются.
- Разрешение использует только локальные справочники и не обращается к 1С по запросу UI.
- Пустая ссылка отображается как `—`, неизвестный тип — как `Неизвестный тип`, отсутствующая локальная запись — как `Не найден`.
- Ошибки чтения БД не маскируются как отсутствие стороны.

## UI

- В списке приходных ордеров отображается несортируемая колонка `Отправитель`.
- В списке расходных ордеров отображается несортируемая колонка `Получатель`.
- Сторона отображается в деталях ордера и на рабочих страницах приёмки, размещения и отбора.
- Фильтрация и сортировка по стороне не входят в текущий объём.

## Критерии приёмки

- Оба query-сервиса обогащают одиночный ордер и страницу списка соответствующим `PartyInfo`.
- Получатель или отправитель корректно отображается для каждого из четырёх `PartyType`.
- Загрузка списка не выполняет отдельный запрос стороны для каждого ордера.
- Неперсистентные свойства `Shipper` и `Receiver` исключены из EF-модели и не требуют изменения схемы БД.
