# План реализации закрепления остатка

- **Ветка** `codex/picking-route-reservations`
- **Дата** 2026-11-25
- **Спецификация** [spec.md](spec.md)

## Резюме

Сохранить текущее действие «Начать сборку» и динамический обход. На завершении старта записывать закрепления вместе с переходом в рабочее состояние. Маршрут и «SKU» используют один расчёт по закреплениям, а изменения количества проходят через команды.

## Технический контекст

Использовать существующие проекты C#/.NET 10 и EF Core с SQL Server. Серверные команды работают через `CommandExecutor`, ТСД использует текущий Mobile V1. Проверки критических переходов выполнять в `Wms.Tests` на SQL Server LocalDB. Удерживать блокировки только на время команд склада. Вызовы 1С остаются за пределами этих транзакций.

## Проверка конституции

- **I и II.** Закрепление меняет доступность. Движение запаса при отгрузке и подпитке остаётся в существующих точках проводки. Изменения закреплений, факт, аудит и квитанция согласованы в пределах команды.
- **III.** Типы очереди читаются из локальной проекции 1С. Порядок приоритета определяет WMS. Протокол старта и обмена с 1С сохраняется.
- **IV.** Правила располагаются в действующих сценариях и общих расчётах доступности. Схема закрепления описана в [модели](data-model.md).
- **V.** Проверки защищают от двойной выдачи, изменения запаса при неуспешной замене адреса и утечки закреплений. Сценарии проверки приведены в [quickstart.md](quickstart.md). После разбора транзакций отклонений от конституции нет.

## Что меняем и в каком порядке

1. **Храним закреплённое количество.** Записываем сборку, ячейку, SKU, срок годности и количество. Основание закрепления — потребность этой сборки. При записи используем существующую транзакционную блокировку ячейки (`InventoryLocationLock`). После завершения транзакции доступность ограничивает сохранённое количество. Удержание всей ячейки остаётся отдельной операцией для физической работы с поддоном. Подключаем новую запись к общему расчёту свободного остатка и готовим EF-модель для миграции.
2. **Выдаём товар в «Начать сборку».** После подтверждения всех РО WMS распределяет остаток между готовыми сборками по общему приоритету РО. Закрепление и переход сборки в работу фиксируются вместе. Повтор команды возвращает результат без повторной выдачи.
3. **Используем закрепление на ТСД.** «SKU» показывает, сколько выделено и сколько ещё нужно, а «Маршрут» пересчитывает порядок обхода по выделенным ячейкам. Отбор из выданной ячейки заменяет закреплённое количество фактом. Отбор из другой допустимой ячейки освобождает заменённое количество одновременно с записью факта из нового адреса.
4. **Обновляем остаток в действующих командах.** Недостача убирает невыполнимые шаги у затронутых сборок. При проведении подпитки закрепляем поступившее количество в пределах непокрытой потребности. Уменьшение плана освобождает лишнее, а закрытие и принятая отмена — всё неотобранное. При увеличении плана и возврате пересчитываем вновь открытую потребность.
5. **Проверяем и вводим в работу.** Проверяем одновременный старт, повтор запроса, смену адреса, общую недостачу, подпитку и отмену. После реализации обновляем текущую документацию. Новое правило вводим после завершения или отмены уже начатых сборок.
