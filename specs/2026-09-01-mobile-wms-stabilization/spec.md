# Стабилизация Mobile WMS

Статус: **Active**

## Результат

Стабилизировать общий Mobile V1 контур после принятия первых четырёх
операционных процессов: перемещений, инвентаризации, приёмки/размещения и
отбора/отгрузки.

Изменения должны устранять подтверждённые риски без нового складского процесса,
новой архитектуры и широкого косметического рефакторинга.

## Подтверждённые выводы ревью

| Приоритет | Область | Вывод | Решение |
| --- | --- | --- | --- |
| P1 | Ответ изменяющей команды | Пустой или повреждённый успешный ответ обрабатывается неодинаково. Старые команды перемещения могут сбросить `ClientRequestId`, а ошибка разбора JSON может выйти из страницы необработанной. | Все нечитаемые успешные ответы изменяющих команд считать неопределённым результатом и разрешать повтор только с тем же `ClientRequestId`. |
| P1 | Мобильная сессия | Любой неуспешный ответ обновления токена удаляет сессию, включая временный `5xx`. После очистки сессии главный экран может продолжать показывать пользователя, потому что проверяет сессию только один раз. | Не удалять сессию при временном сбое обновления. После окончательной потери авторизации согласованно переводить клиент в состояние входа. |
| P2 | Mobile V1 ошибки | Бизнес-эндпоинты используют общий формат ответа, но описание ответов и применение стабильных кодов неодинаково между процессами. | Зафиксировать небольшой общий набор стабильных Mobile V1 кодов и единообразно применять его во всех четырёх процессах. |
| P2 | Очереди ордеров | Очереди приёмки и отгрузки загружают полный граф строк, единиц измерения и штрихкодов, хотя для списка большая часть данных не нужна. | Выделить компактное чтение очереди с прежним составом и сортировкой результата; подробный граф загружать только для документа. |
| P3 | Сопровождение API | Метаданные возможных ответов описаны неодинаково, а чтение успешных ответов повторяется в `MobileApiClient`. | Убрать только повтор, связанный с классификацией ответа, и выровнять метаданные без изменения маршрутов и контрактов. |

Проверкой также подтверждено, что текущая схема квитанций сохраняет складское
изменение и `MobileCommandReceipt` одной операцией `SaveChangesAsync`; ключ
включает пользователя, тип команды и запрос, а хэш запроса детерминирован.
Доменная модель отклоняет нечисловые и недопустимые количества. Подписки
операционных страниц на сканер симметрично снимаются, а повторный скан во время
обработки блокируется.

## В объёме

- единая классификация определённых и неопределённых HTTP-результатов команд;
- корректное удержание идентификатора неопределённой команды;
- устойчивое обновление и сброс мобильной сессии;
- единообразные Mobile V1 problem responses и OpenAPI metadata;
- очевидное сокращение лишней загрузки данных для очередей приходных и
  расходных ордеров;
- синхронизация текущей документации.

## Вне объёма

- новые мобильные складские процессы;
- изменение принятых бизнес-переходов четырёх процессов;
- decimal-миграция количеств, упаковки и характеристик SKU;
- offline-команды и сохранение незавершённого UI-процесса после удаления
  приложения или очистки его данных;
- аутбокс, процедура восстановления 1С и аутентификация входящих вызовов 1С;
- подготовка staging, HTTPS-сертификаты и разделение диагностических настроек
  между development, staging и production;
- изменение цепочки OpenAPI-пакетов и устранение предупреждения `NU1903` для
  `Microsoft.OpenApi 2.0.0`;
- автоматическая очистка `MobileCommandReceipt`: политика хранения должна быть
  определена по фактическому объёму пилота;
- произвольное ограничение количества ордеров в очереди или новая пагинация;
- общая переработка `MobileApiClient`, страниц или контрактов;
- создание и запуск тестов.

## Правила результата команды

Результат изменяющей команды является неопределённым, если клиент не может
доказать, что сервер её не зафиксировал. К таким случаям относятся:

- транспортная ошибка;
- HTTP `408`;
- HTTP `5xx`;
- успешный HTTP-статус с пустым, повреждённым или несовместимым телом.

После такого результата страница сохраняет исходные данные команды и тот же
`ClientRequestId`. Любой окончательный `4xx` business/client response освобождает
идентификатор и позволяет оператору исправить данные.

## Правила сессии

- Временная транспортная ошибка, `408` или `5xx` при refresh не удаляет
  сохранённую сессию и явно показывается как временная недоступность.
- Окончательный отказ refresh (`400` или `401`) удаляет сессию.
- Полученный бизнес-запросом `401` удаляет локальную сессию; при возвращении на
  главный экран клиент не должен продолжать показывать устаревшего пользователя.
- Один refresh остаётся общим для конкурирующих запросов.

## Правила Mobile V1

- Формат ошибки остаётся `MobileProblemResponse(Code, Message)`.
- Коды являются короткими стабильными protocol values; русский текст может
  уточняться без изменения кода.
- Минимальный общий набор различает некорректную или недоступную команду,
  отсутствие ресурса, конфликт и общий отказ. Более подробная классификация не
  расширяет `OperationError` в рамках этой стабилизации.
- Все четыре процесса описывают одинаковые `401`, `404`, `409` и `422` там,
  где эти ответы реально возможны.
- Маршруты и успешные wire contracts не меняются.

## Правила оптимизации

- Состав, группировка и сортировка очередей ордеров не меняются.
- Очередь не должна материализовывать коллекции штрихкодов SKU и другие поля,
  нужные только экрану документа.
- Подробный запрос документа продолжает возвращать строки, движения и сведения,
  необходимые текущему UI.
- Оптимизация не вводит кэш, новую инфраструктуру или скрытый лимит выдачи.

## Приёмка

1. Для каждой изменяющей команды пустой и повреждённый успешный ответ оставляет
   возможность повтора с тем же `ClientRequestId` и не завершает приложение.
2. `408`, `5xx` и транспортная ошибка сохраняют запрос; окончательный `4xx`
   освобождает его.
3. Временный сбой refresh не удаляет сессию; окончательный отказ и обычный
   авторизованный запрос с `401` приводят UI в согласованное состояние входа.
4. Все Mobile V1 процессы возвращают и документируют одинаковые базовые problem
   responses.
5. Очереди приходных и расходных ордеров сохраняют результат, но не загружают
   штрихкоды SKU.
6. Полная сборка решения проходит без ошибок. Тесты не создаются и не
   запускаются.
