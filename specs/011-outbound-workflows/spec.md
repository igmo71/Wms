# Спецификация: Отбор, подпитка и закрытие с отгрузкой

**Ветка**: `codex/011-outbound-workflows`
**Создана**: 2026-11-05
**Статус**: рабочая спецификация для декомпозиции по [плану реализации](plan.md).

**Исходная задача**: переработать Отбор, добавить самостоятельный процесс Подпитки и перейти от связи одного расходного ордера WMS с одним документом 1С к связи с несколькими документами. В этом этапе закрытие сборки одновременно означает учётную отгрузку; отдельный процесс Отгрузки отложен.

## Рабочие термины и последовательность

| Термин | Значение в этом черновике |
|---|---|
| **РО 1С** | Документ 1С: источник задания на сборку и самостоятельная единица обмена при закрытии сборки. |
| **РО WMS / сборка** | Одно складское задание, объединяющее один или несколько РО 1С одного склада. Перечень привязанных документов фиксируется при начале Отбора. |
| **План WMS** | Запланированные SKU и количества по каждому привязанному РО 1С с общим итогом по SKU. До начала Отбора их задаёт 1С; после начала руководитель склада может осознанно изменить план. |
| **Факт WMS** | Физически отобранные SKU и количества. До закрытия он рассчитывается из исправляемых записей по ячейке и сроку годности; при закрытии весь факт распределяется по связанным РО 1С и проводится на складе. |
| **Текущие данные источников 1С** | Актуальные строки и количества каждого связанного РО 1С, полученные при проверке. Их изменения после начала Отбора не меняют план WMS сами по себе. Ожидаемые переключения статуса оцениваются отдельно. |

Один сборщик может поочерёдно работать с несколькими самостоятельными РО WMS: оставить первую сборку в ожидании Подпитки, собрать вторую и вернуться к первой. Это не делает их одной мультиордерной сборкой. Мультиордерный РО WMS ожидается сравнительно редким; ограничение на число строк или документов из этого наблюдения не следует.

Последовательность согласованных переходов:

| Этап | Складской результат WMS | Граница с 1С |
|---|---|---|
| Формирование сборки | Связать один или несколько РО 1С одного склада; до начала Отбора источник определяет план WMS. | Документы 1С находятся в статусе «Подготовлен». |
| Начало Отбора | Зафиксировать состав сборки; разрешить работу только после подготовки всех документов. | Перевести каждый связанный РО 1С в «КОтбору»; частичный успех блокирует начало до безопасного повтора. |
| Отбор | Сохранять исправляемые записи Отбора без движения остатков; маршрут остаётся рекомендацией. | Изменения источников показываются, но сами не меняют начатый план WMS. |
| Подпитка по потребности | Отдельное задание переносит товар из «Хранения» в «Комплектацию»; подтверждение назначения проводит перемещение и делает количество доступным Отбору. Начатое задание может продолжиться после закрытия сборки. | Не меняет документы 1С. |
| Закрыть и отгрузить | После свежей проверки всех источников одним складским проведением списать отобранный факт непосредственно из исходных ячеек за пределы учётного остатка. Промежуточного остатка в зоне отгрузки нет. | Зафиксировать для каждого РО 1С целевые строки и статус «Отгружен», затем синхронизировать документы независимо. Ошибка последующей записи не отменяет складское проведение. |

## Пользовательские сценарии и проверка

### Сценарий 1 — Создать общий расходный ордер WMS (P1)

Из 1С поступают расходные ордера в статусе «Подготовлен». Оператор сканирует один из них. Если документ свободен, WMS создаёт собственный расходный ордер и прикрепляет к нему документ. До начала Отбора к тому же ордеру WMS можно добавить другие расходные ордера 1С; их текущие данные задают план WMS. При начале сборки WMS фиксирует перечень связанных документов и переводит их в статус «КОтбору». Если переход не завершился успешно, сборка остаётся заблокированной; начало можно повторить. Позднейшие изменения документов 1С показываются рядом с планом WMS, но сами не меняют его или факт WMS. Изменения плана руководителем склада остаются в аудите.

Первая попытка «Начать отбор» фиксирует список РО 1С и текущий план WMS по каждому из них до команд в 1С. Если часть документов успела перейти в «КОтбору», а остальные нет, WMS показывает результат по каждому, не разрешает Отбор и не допускает добавления или открепления источников. Повтор сначала сверяет каждый РО 1С: уже подтверждённый переход не выполняется заново, оставшиеся переходы повторяются. Автоматического возврата успешно переключённых документов в «Подготовлен» из-за сбоя другого нет. При отмене всей сборки WMS безопасно возвращает в «Подготовлен» только документы, которые сама переключила и которые с тех пор не менялись в 1С.

До начала Отбора связанный РО 1С можно открепить: WMS пересчитывает план, освобождает документ для другой сборки и сохраняет действие в аудите без команды в 1С. Если откреплён последний документ, пустой черновик РО WMS отменяется с сохранением истории. После начала Отбора состав сборки остаётся неизменным.

До начала WMS проверяет проведение каждого РО 1С. Снятие проведения при последующей сверке блокирует продолжение работы до восстановления документа или отмены сборки. После начала Отбора каждый связанный РО 1С должен оставаться в статусе «КОтбору» без пометки удаления до закрытия сборки. Если источник неожиданно перешёл в другой статус или помечен на удаление, «Закрыть и отгрузить» блокируется также для руководителя склада. Продолжение возможно после восстановления корректного состояния документа в 1С и новой сверки либо после отмены всей сборки с физическим возвратом отобранного товара. WMS не исправляет такую смену статуса автоматически при закрытии.

Если после начала Отбора изменился вид складской операции хотя бы одного связанного РО 1С, закрытие всей сборки блокируется для оператора и руководителя склада. Продолжение возможно после восстановления прежней операции в 1С и новой сверки либо после отмены сборки с возвратом отобранного товара; подтверждение расхождения количества не снимает этот запрет.

Если после начала Отбора в связанном РО 1С изменился получатель при неизменном составе товара, оператор не закрывает сборку самостоятельно. Руководитель склада видит прежнего и текущего получателя, сверяет физически сгруппированный товар и бумажную маркировку с актуальным документом 1С и может подтвердить закрытие с фиксацией решения в аудите. WMS не редактирует получателя в 1С. Это исключение не снимает запреты при смене склада, статуса или пометке удаления.

Изменение только плановой даты отгрузки или направления доставки в связанном РО 1С после начала Отбора обновляет отображаемые данные источника, но само по себе не меняет план или факт WMS и не блокирует закрытие. Приоритет Подпиток определяется типом очереди, а не этими реквизитами.

Дополнительных проверок прочих реквизитов РО 1С на этом этапе нет: для начала, закрытия и обмена действуют перечисленные выше правила.

Главная страница Отбора показывает незакрытые сборки, созданные сборщиком, и начатые сборки, закреплённые за ним; Закрытая сборка с неподтверждённым обменом остаётся видимой с предупреждением. После успеха обмена всех документов она уходит из активного списка. Скан любого связанного РО 1С открывает его сборку независимо от списка. Если начатая сборка закреплена за другим сотрудником, WMS показывает его имя и предлагает явно принять сборку на себя. После подтверждения новый сборщик становится единственным ответственным за продолжение Отбора, а предыдущему показывается смена ответственного. Черновой факт, резервы и маршрут сохраняются; отдельное подтверждение содержимого тележки не требуется.

Новая сборка открывается на списке связанных РО 1С для добавления документов, существующая незакрытая — на списке SKU. Кнопка «Начать отбор» находится внутри ещё не начатой сборки. Внутри сборки доступны список документов 1С, список SKU, список Подпиток и маршрут; карточка факта открывается из списка SKU либо маршрута. После подтверждения Отбора содержимое той же карточки обновляется следующим доступным шагом без накопления страниц; «Назад» возвращает в исходный список. Переход к закрытию доступен из списка SKU и маршрута.

**Самостоятельная проверка**: сканировать первый свободный РО 1С на главной странице, затем второй с общим SKU на странице документов созданной сборки, получить один ордер WMS с двумя различимыми источниками и суммарным планом.

### Сценарий 2 — Собрать и закрыть общий ордер (P1)

Отборщик выполняет Отбор по плану WMS. До закрытия он может исправлять записи о взятом товаре с указанием ячейки, SKU, срока годности и количества; из этих записей рассчитывается факт WMS. Они не меняют остатки до закрытия сборки. Перед закрытием WMS запрашивает текущие данные каждого документа 1С. Оператор выбирает «Закрыть и отгрузить» на ТСД, если факт WMS совпадает с планом WMS, а план WMS по каждому документу совпадает с его текущими строками 1С. При расхождении руководитель склада выбирает один из двух путей: меняет план WMS в соответствии с текущими документами 1С, после чего оператор донабирает или возвращает товар и может закрыть сборку; либо сохраняет складской результат и сам закрывает сборку, сознательно заменяя конфликтующие изменения документов 1С в пределах допустимого плана каждого документа. Если ограничение документа-основания известно до закрытия и не позволяет передать факт, сначала исправляют основание в 1С либо физический Отбор. Если ограничение обнаружилось только при последующем проведении в 1С, WMS показывает ошибку обмена; уже проведённый складской факт не правится. Для каждого SKU сумма количеств «Отгрузить» по всем связанным документам должна равняться факту WMS этого SKU. Успешное закрытие с положительным фактом одним учётным действием списывает товар непосредственно из исходных ячеек за пределы склада с сохранением исходных групп сроков в истории и фиксирует целевое состояние связанных документов 1С: строки «Отгрузить» и «НеОтгружать» и статус «Отгружен». Последующая ошибка записи в 1С не отменяет проведённое складское движение. Физически товар может ожидать покупателя на площадке отгрузки, но уже не входит в учётный остаток WMS.

Если весь факт сборки равен нулю и руководитель склада решает завершить её с недостачей, WMS закрывает сборку без складских движений. Связанные документы 1С доводятся до статуса «Отгружен» со всеми применимыми строками «НеОтгружать»; это закрытие отличается от отмены незавершённой работы. Если ноль распределён только одному документу, складское списание создаётся лишь для положительного факта других документов.

До закрытия руководитель видит общий физический факт по SKU, а по каждому связанному РО 1С — его план WMS и текущие строки источника с отличиями. Отдельного уже отобранного факта по документу до распределения нет. Руководитель может принять изменения 1С в план одного документа и сохранить складское решение вопреки изменениям другого; распределение общего факта по документам и закрытие выполняются для всей сборки согласованно.

После распределения факта на РО 1С адаптер последовательно заполняет строки одного SKU внутри этого документа в исходном порядке до исчерпания выделенного количества. Для каждой строки количество «Отгрузить» не превышает её утверждённый план. Остаток планового количества получает действие «НеОтгружать». Связи строк с распоряжениями сохраняются. При закрытии WMS заранее распределяет факт SKU, который относится только к одному РО 1С, на этот документ. Для общего SKU с фактом, равным сумме планов WMS связанных документов, распределение повторяет их плановые количества. При недоборе общего SKU WMS не выбирает пострадавший документ за руководителя: он вручную указывает распределение по РО 1С. Итог всех распределённых количеств должен точно равняться факту SKU; предложенное или введённое распределение показывается перед подтверждением закрытия.

Для каждого SKU распределение на отдельный РО 1С не превышает утверждённый план WMS этого документа, а сумма по документам равна факту WMS. Текущая строка РО 1С после начала Отбора может отличаться от плана WMS и сама по себе не является неизменным пределом: руководитель вправе утвердить восстановление плана в 1С через PATCH, если получившийся документ может быть проведён. Если 1С отклоняет проведение, WMS сохраняет уже закрытый складской факт и показывает ошибку обмена для разбора; повторная попытка не создаёт второго списания.

WMS не требует отдельной предварительной проверки всех ограничений документа-основания. Отказ проведения может быть вызван этим или другой причиной; текст ошибки из ответа 1С показывается для конкретного РО 1С, после устранения причины оператор или руководитель может повторить обмен той же кнопкой «Закрыть и отгрузить».

После закрытия сборки результат обмена с 1С показывается отдельно по каждому связанному документу: ожидание записи и перепроведения, подтверждённый целевой результат либо новое расхождение источника. При обычном сбое оператор на ТСД или руководитель в Web повторно нажимает «Закрыть и отгрузить». У закрытой сборки это действие запускает обмен только по документам без подтверждённого успеха. Успешные документы пропускаются. Если PATCH уже принят, повторяется POST. После потери ответа POST повторное проведение допустимо. WMS сохраняет исходное складское списание. Если документ 1С изменился после рассмотренного руководителем состояния, прежнее разрешение на замену строк не используется: Web показывает новые расхождения для нового решения перед следующей попыткой записи. Новые потребности источника оформляются отдельными документами и новой работой WMS.

На текущем этапе руководитель не заменяет общий факт WMS вводом числа в Web. Он меняет план и распределение уже подтверждённого факта; физический факт до закрытия исправляется действиями Отбора или возврата с указанием ячейки, SKU, срока и количества на ТСД. Если руководитель сам выполняет физическое действие, ему также нужна роль `Operator`, и он использует тот же складской сценарий под своей учётной записью. Закрытие с расхождениями не меняет записи физического Отбора.

До успешного закрытия складской остаток остаётся учтённым в исходных ячейках, а подтверждённый Отбор удерживает его резервом. При закрытии WMS проверяет собственные резервы сборки и покрывающий их учётный остаток. При остатке 10 и резерве сборки 10 ей доступны к списанию все 10, хотя для нового Отбора свободно 0. Если закрытие заблокировано, физически собранный товар остаётся в сохранённом черновом факте; для решения через Web повторный скан фиктивной ячейки отгрузки не требуется. После закрытия физическое местонахождение товара до передачи покупателю не создаёт складского остатка в зоне отгрузки.

Ввод количества меньше предложенного означает обычный частичный Отбор: сам по себе он не сообщает о недостаче и не исключает остаток ячейки из дальнейшего маршрута. Для обнаруженной фактической недостачи на карточке есть отдельное действие «Недостача в ячейке». Оно сохраняет фактически взятое количество под резервом и блокирует спорную группу ячейка–SKU–срок от предложения другим сборкам до разбора, не исправляя учётный остаток молча. Форма предлагает необязательное пояснение для руководителя; сборка, ячейка, SKU, срок, ожидаемое и обнаруженное количество, сотрудник и время фиксируются автоматически. Отсутствие текста не блокирует сообщение.

Руководитель склада может принять сообщение о недостаче по данным сотрудника либо проверить ячейку лично. Если недостача подтверждена, отдельная операция складской корректировки с типом причины и ссылкой на исходную сборку проводит изменение остатка и в том же действии снимает блокировку спорной группы. Если учётный остаток оказался верным, руководитель снимает блокировку с фиксацией решения в истории без движения товара. Корректировка не затрагивает фактически взятое количество, удерживаемое сборкой.

До закрытия сборщик может уменьшить ранее подтверждённый факт по конкретной записи Отбора. Он указывает освобождаемое количество, сканирует исходную ячейку и подтверждает, что это количество физически находится в ней после исправления. Один порядок применим и после возврата товара в исходную ячейку, и при исправлении ошибочно введённого количества, когда товар из ячейки не брали. Только после этого WMS уменьшает факт и соответствующий резерв, сохраняет историю исправления и перестраивает оставшийся маршрут.

Для обычной отмены уже начатой сборки весь фактически взятый товар возвращают именно в исходные ячейки, подтверждая возврат по каждой записи Отбора тем же действием уменьшения факта. Когда факт и его резервы стали нулевыми, руководитель склада отменяет сборку с сохранением истории. Дополнительных складских движений эта отмена не создаёт, поскольку до закрытия остатки продолжали числиться в исходных ячейках. Если возврат в исходную ячейку невозможен, обычная отмена останавливается для отдельного разбора; размещение в другой ячейке в этот сценарий не входит.

После отмены WMS возвращает связанные РО 1С в статус «Подготовлен», если сама перевела их в «КОтбору» и с тех пор они не менялись в 1С. Изменённый в источнике документ не перезаписывается автоматически; руководитель видит требующее разбора состояние. Сбой обмена оставляет возврат статуса ожидающим безопасного повтора и не создаёт новую сборку по тому же документу до разрешения состояния.

При отмене сборки предложения Подпитки и заказанные, но ещё не начатые задания отменяются. Начатое сканом источника задание не отменяется и остаётся в работе подпитчика до выполнения заказанного количества и завершения работы со всеми снятыми поддонами; отмена сборки ожидает его завершения. Уже проведённое в целевую ячейку количество не откатывается: товар физически находится там и доступен другим сборкам. Если выполнить начатую Подпитку нельзя из-за недостачи или отсутствия другого источника, задание и ожидающая отмена сборки остаются на разборе, без автоматического снятия удержаний или блокировок.

**Самостоятельная проверка**: выполнить Отбор по двум источникам с общим SKU, проверить успешное закрытие оператором при обоих совпадениях и отказ оператору при недоборе либо изменении одного документа 1С после начала Отбора; затем проверить явное решение руководителя склада по расхождению.

#### Выбор ячеек и маршрут Отбора (рабочие правила)

- Цель выбора и маршрута — уменьшать суммарное время и труд складских операций, в том числе за счёт освобождения ячеек; правила ниже задают приоритеты, когда кратчайший путь одной сборки конфликтует с этой целью.
- Адресный порядок склада образует физическую «змейку». Значимость частей адреса: Помещение → Ряд → Стойка → Уровень → Ячейка; визуальный порядок последних двух частей на этикетке не меняет порядок маршрута. После выбора необходимых ячеек базовый обход идёт в обратном адресном порядке, пока это не нарушает приоритет более раннего срока одного SKU. Существующее поле `PickSequence` сохраняется в модели, но в базовой маршрутизации пока не участвует.
- При разных сроках годности одного SKU действует FEFO: сначала отбирается товар с более ранней датой окончания срока. Остаток с неуказанным сроком располагается после всех остатков с известной датой. Этот порядок имеет приоритет перед самоочисткой ячеек и палетным Отбором. Если учётная группа SKU с обязательным сроком осталась без даты, карточка напоминает визуально проверить срок на выбранном товаре. Отборщик подтверждает количество обычным действием, без ввода даты и отдельного подтверждения; просроченный товар или товар с нечитаемым сроком не подтверждается.
- Карточка факта Отбора показывает предлагаемый срок и доступное количество именно для его группы. Отборщик подтверждает срок, фактически прочитанный на товаре, и количество этой группы; при нескольких сроках одного SKU в ячейке их факты остаются раздельными.
- Поле количества на карточке заранее заполнено количеством, предложенным маршрутом. После скана другой исходной ячейки WMS пересчитывает предложение по её доступному остатку и оставшейся потребности. Отборщик проверяет значение, при необходимости меняет его и всегда явно подтверждает факт; автоматического подтверждения по одному скану нет.
- Если прочитанный срок отличается от предложенного, отборщик может выбрать другую уже учтённую группу этого SKU в просканированной ячейке; WMS повторно проверяет FEFO и доступность. Если предложенной более ранней группы физически нет, отборщик сообщает о расхождении, чтобы её остаток был заблокирован до разбора. Если прочитанного срока нет среди учтённых групп ячейки, обычное подтверждение Отбора блокируется до разбора, без автоматической правки срока в учёте. Исключение — учётная группа с неизвестным сроком: физический срок проверяется визуально, но в учёте и факте Отбора группа остаётся без даты.
- Для SKU в нескольких допустимых ячейках приоритетом служит освобождение ячеек. Если остаток одной ячейки точно равен требуемому количеству SKU, выбирается она; при нескольких точных совпадениях выбирается ячейка, дающая наименьший дополнительный путь от предыдущей точки через неё к следующей обязательной точке маршрута. В остальных случаях ячейки рассматриваются по возрастанию остатка: меньшие остатки забираются полностью, а из последней нужной ячейки берётся недостающее количество. Выбранные точки затем упорядочиваются по адресному маршруту, а не по величине остатков.
- У первой точки маршрута нет предыдущей обязательной точки, у последней нет следующей: расчёт дополнительного пути учитывает только существующих соседей. Обычные пятичастные адреса упорядочиваются по согласованным частям `(Помещение, Ряд, Стойка, Уровень, Ячейка)`. Для адреса вне этого формата используется стабильная сортировка по существующему `Code`; сам `Code` и штрихкод ячейки не меняются.
- Ячейка зоны «Хранение» может стать источником прямого Отбора, если весь её остаток нужного SKU не больше ещё требуемого количества и съём всей ячейки не нарушает FEFO. Под «целым поддоном» в этом правиле понимается полное опустошение ячейки «Хранения», а не самостоятельная учётная единица палета. Съём такой ячейки имеет приоритет перед обычным выбором ячеек и выполняется первым среди действий по этому SKU; недостающее количество добирают из других ячеек. Если подходят несколько ячеек, сначала выбирают ячейку с наибольшим допустимым остатком; при равенстве — ближайшую к следующей нужной ячейке «Комплектации», затем — к следующей точке маршрута. Несколько подходящих ячеек «Хранения» последовательно опустошают по убыванию остатка, пока очередная ячейка целиком помещается в оставшуюся потребность и сохраняется FEFO. Для этого допускается возврат против основного адресного обхода. Если полное опустошение нарушило бы FEFO, палетный вариант недоступен; потребность решается обычным Отбором либо Подпиткой. Это прямой Отбор с участием работника, умеющего пользоваться погрузчиком, а не операция Подпитки.
- Маршрут является рекомендацией. В сборке нужен альтернативный экран общего списка требуемых SKU по образцу Приемки; отборщик может начать с удобного ему SKU, например крупного и твёрдого товара для размещения на тележке, и выбрать другую допустимую ячейку для него. Выбор работника не отменяет FEFO, проверки срока и доступного количества; подтверждённые действия остаются фактом, а маршрут для оставшейся потребности пересчитывается после такого выбора или изменения доступных остатков.
- После подтверждения факта открывается следующий доступный шаг перестроенного маршрута. Ожидающая Подпитки или заблокированная недостачей позиция не останавливает Отбор остальных доступных SKU; её причина видна в списке SKU и маршруте. Только когда доступных шагов больше нет, экран показывает оставшуюся потребность и причину ожидания, включая переход к списку Подпиток. К своим другим сборкам работник возвращается обычной навигацией. Когда сборщик физически закончил доступный Отбор, он может выбрать «Закрыть и отгрузить»; при оставшемся расхождении операторское закрытие блокируется по общим правилам, а разбор выполняет руководитель склада.
- Если отборщик открыл карточку SKU и пришёл к другой ячейке, он сканирует её адрес прямо на карточке. Только после скана WMS проверяет, можно ли отобрать выбранный SKU из этой ячейки: учитывает её назначение, наличие SKU, FEFO, ограничения доступности и свободный остаток. При несовпадении WMS явно показывает просканированный адрес, выбранный SKU и другой SKU либо список SKU, числящихся в ячейке; факт не подтверждается и SKU не переключается автоматически. Иные причины отказа также показываются явно. При допустимом выборе карточка показывает срок и доступное количество перед подтверждением; отдельный экран смены ячейки не требуется. Скан штрихкода самого товара необязателен, но, если он выполнен, WMS проверяет совпадение с выбранным SKU.
- Карточка Отбора всегда показывает количество, доступное для нового Отбора. Когда оно меньше учётного остатка, дополнительно показываются причина и занятое количество: ранее подтверждённый факт своей сборки, резерв другой работы либо блокировка. В обычном случае без различия дополнительные данные не загромождают карточку. Руководитель в Web видит подробные удержания с документом и исполнителем; подтверждение сверх текущего доступного количества отклоняется.
- Прямой палетный Отбор допускается только из ячейки «Хранения» с одним SKU; разные сроки этого SKU допустимы при соблюдении FEFO. Если в ячейке несколько SKU, потребность выполняется через Подпитку с удержанием исходной ячейки и возвратом остатка поддона. При допустимом прямом Отборе скан исходной ячейки и съём поддона создают исключительное удержание всей ячейки за сборкой до её закрытия либо подтверждённого физического возврата поддона при отмене Отбора. Оно не заменяет количественный резерв подтверждённого факта по SKU и сроку: удержание сохраняет исходную ячейку доступной для возможного возврата, а резерв защищает количество от повторного использования.
- Эти правила описывают целевой процесс; действующий старый Отбор ограничен ячейками «Комплектации».

### Сценарий 3 — Выполнить Подпитку (P1)

Один поддон может содержать нужный SKU с несколькими сроками. После скана источника подпитчик видит группы срока и переносит сначала товар с более ранней действительной датой (FEFO); количества разных сроков подтверждаются и проводятся раздельно. Несколько SKU на одном поддоне не являются обычным сценарием, но удержание снятой ячейки охватывает всё её содержимое.

Если в просканированной исходной ячейке числится несколько SKU, Подпитка остаётся допустимой. Экран выделяет SKU текущего задания и его группы сроков, а остальные SKU этой ячейки показывает только для сведения. Подтвердить перенос можно только для SKU задания и его выбранной группы срока; остальные SKU не меняются в этом задании. Исходная ячейка удерживается целиком, а не только по SKU задания. Если после переноса в ячейке физически остаётся другой товар, подпитчик возвращает его и подтверждает это сканом ячейки; вариант «ячейка пуста» к нему неприменим.

Подпитчик работает в самостоятельном процессе со своей стартовой кнопкой, страницами и экранами ТСД. Расчёт маршрута сборки сразу формирует полный список необходимых подпиток по каждому SKU, в том числе несколько подпиток из разных ячеек, если одной не хватает для покрытия потребности. Список показывается отборщику на отдельной странице; наличие предложений обозначается на кнопке перехода. Отборщик оценивает весь список и явно заказывает каждую нужную Подпитку. Если доступного товара на складе в целом не хватает, это отдельное расхождение, а не скрытое предложение заведомо недостаточной подпитки. Подпитчик видит заказанные задания, упорядоченные по убыванию приоритета очереди «ЖиваяОчередь» → «СобратьКДате» → «СобственнаяДоставка» → «Очередность не указана», а внутри одного приоритета — по времени получения запроса. Для сборки с несколькими РО 1С используется наивысший приоритет среди связанных документов. Принадлежность к очереди обозначается цветом и/или иконкой.

Отбор и Подпитка имеют разные рабочие места, но оба доступны пользователю с существующей ролью `Operator`; один сотрудник при необходимости может выполнять оба процесса. Для прямого палетного Отбора и работы подпитчика с погрузчиком отдельная системная роль на этом этапе не вводится: допуск к технике определяет склад. Решение о расхождении, снятие блокировки через учётную корректировку и исправление проведённого количества относятся к роли `Manager`. Роль `Administrator` сама по себе не даёт этих полномочий.

В задании видны SKU, количество, рекомендуемые исходная ячейка «Хранения» и целевая ячейка «Комплектации». Для назначения сначала предлагается подходящая ячейка с текущим остатком этого SKU; если её нет, можно предложить историческую ячейку этого SKU с нулевым остатком. Подпитчик вправе выбрать другие допустимые ячейки источника и назначения. Он сканирует выбранную исходную ячейку, после проверки FEFO и доступности временно удерживая весь её доступный для съёма остаток, снимает поддон, сканирует выбранную целевую ячейку, вводит фактически добавленное количество и подтверждает. Это подтверждение проводит указанное количество из выбранной ячейки «Хранения» в выбранную ячейку «Комплектации», сохраняя исключительное удержание исходной ячейки до подтверждения завершения работы с поддоном. Сборщик узнаёт о доступном пополнении и обновлённом маршруте при очередном штатном обновлении своего экрана. Затем подпитчик возвращает остаток поддона в исходную ячейку и сканирует её; если возвращать нечего, сканирует ту же ячейку и подтверждает, что она физически освобождена. Оба действия снимают удержание всей ячейки без повторного движения товара; отдельная блокировка недостачи сохраняется до учётной корректировки.

Рекомендации адресов не заменяют проверки фактического скана и повторной проверки перед проведением. Источник должен быть активной ячейкой «Хранения» того же склада, без чужой блокировки и с доступным количеством SKU задания; действуют ограничения срока и FEFO. Назначение должно быть активной ячейкой «Комплектации» того же склада, без блокировки; добавление SKU должно соблюдать действующее правило смешения товаров. При отказе WMS показывает конкретную причину и позволяет сканировать другой допустимый адрес без движения товара. Если исходный поддон уже снят, его ячейка продолжает удерживаться до подтверждённого завершения работы с ним; другой источник можно взять только после этого, а другое допустимое назначение можно выбрать сразу.

На странице Подпиток сборщика предложения и заказы показываются белыми и различаются доступным действием. Когда подпитчик приступил к заданию, карточка становится жёлтой: сборщик может выдвинуться к целевой ячейке, но подтверждение Отбора из ещё не пополненного остатка недоступно. После частичного подтверждения карточка остаётся жёлтой и показывает проведённое и оставшееся количество; уже проведённое количество доступно для Отбора. Когда вся заказанная Подпитка подтверждена в целевой ячейке, карточка становится зелёной, даже если подпитчик ещё возвращает остаток поддона. Когда все нужные пополнения получены, кнопка перехода на страницу показывает знак завершения. Дополнительные состояния возврата поддона или освобождения пустой ячейки показываются подпитчику, а не сборщику. Для других работников исходная ячейка в это время видна как «Поддон снят для Подпитки» с номером задания и исполнителем; это рабочее удержание всей ячейки, а не недостача. Оно запрещает новые операции с её остатками, кроме действий владельца задания, и снимается после подтверждённого завершения работы с поддоном.

Если после другого допустимого Отбора потребность сборки в заказанной Подпитке исчезла, ещё не начатое задание отменяется автоматически с видимой сборщику причиной. После успешного скана источника и удержания ячейки задание считается начатым: оно не отменяется и подпитчик выполняет заказанное количество до конца, при необходимости последовательно используя другие источники. Подпитчику не требуется следить за изменением потребности сборки во время работы. Проведённое в целевую ячейку количество не откатывается из-за изменения потребности и остаётся обычным складским остатком.

Если сборщик полностью выполнил Отбор из других доступных ячеек, начатая Подпитка не препятствует «Закрыть и отгрузить» при соблюдении обычных проверок плана, факта и 1С. Связанное задание остаётся у подпитчика до своего завершения; его последующее перемещение не относится к уже закрытому складскому факту сборки и пополняет обычный остаток целевой ячейки.

Если подпитчик сканирует другую допустимую исходную ячейку вместо рекомендованной, за его заданием удерживается фактически выбранная ячейка. Остальные ещё не начатые заказы Подпитки того же SKU сохраняются, но их рекомендуемые источники пересчитываются с учётом этого удержания и оставшейся потребности; один и тот же доступный остаток не назначается дважды. При отсутствии свободного источника подпитчик и сборщик видят «Нет доступного источника» для невыполненной потребности. Новое задание не создаётся молча, а уже снятый поддон не переназначается.

Если работа прервалась после подтверждения количества в целевой ячейке, при повторном открытии того же задания подпитчик видит уже проведённое количество и требование вернуть поддон или подтвердить пустую исходную ячейку. Проведённое перемещение не повторяется, исходная ячейка остаётся удержанной. Повтор подтверждения после потери ответа возвращает прежний результат без второго движения. Скан той же исходной ячейки с подтверждением возврата остатка или её физического освобождения снимает удержание и завершает работу с этим поддоном; задание завершается, если вся заказанная потребность выполнена. Для сборщика проведённое количество доступно с момента первого успешного подтверждения в целевой ячейке.

Если на снятом поддоне обнаружена недостача, подпитчик фиксирует её по группе «ячейка–SKU–срок»: физически найденный товар остаётся за заданием, а спорный учётный остаток блокируется до разбора и не исправляется молча. Найденное количество можно подтвердить в целевой ячейке. После возврата остатка поддона или подтверждения пустой исходной ячейки заказанная Подпитка остаётся незавершённой на недостающее количество; подпитчик выбирает другой допустимый источник и продолжает то же задание без создания нового заказа. Сборщик видит уже доступное количество и оставшуюся потребность. Если свободного источника нет, оба рабочих места явно показывают причину ожидания; задание не завершается на меньшем количестве автоматически.

До подтверждения в целевой ячейке подпитчик может исправить введённое количество. После подтверждения движение уже проведено: его количество не редактируется, и отдельный экран исправления для подпитчика на этом этапе не нужен. При обнаружении ошибки подпитчик обращается к руководителю склада; тот оформляет отдельное корректирующее движение с причиной и ссылкой на ошибочный шаг Подпитки. Исходное движение остаётся в истории, а складской остаток меняется только корректирующим движением.

Если тип очереди связанного РО 1С изменился после заказа Подпитки, при очередном штатном обновлении ещё не начатые задания пересортировываются по актуальному приоритету сборки. Для мультиордерной сборки снова берётся наивысший приоритет её документов. Начатое задание продолжает выполняться без смены исполнителя; время исходного запроса остаётся критерием порядка внутри равного приоритета.

**Самостоятельная проверка**: открыть отдельное рабочее место Подпитки, перенести SKU из «Хранения» в «Комплектацию», убедиться, что товар доступен сборщику после подтверждения назначения, а исходная ячейка удерживается до возврата поддона или подтверждения её освобождения.

### Сценарий 4 — Довести каждый РО 1С до закрытого складского факта (P1)

После единого закрытия сборки WMS хранит отдельную цель обмена для каждого связанного РО 1С: распределённое количество, строки «Отгрузить» и «НеОтгружать», пустые «Товары по распоряжениям» при нулевом распределении и статус «Отгружен». Интеграция сверяет актуальный источник с состоянием, проверенным при закрытии оператором либо рассмотренным руководителем, затем отправляет OData PATCH и POST для проведения документа по действующим принципам корректировки РО 1С. Документ 1С в WMS доступен только для просмотра. Успех или ошибка одного документа не меняет уже проведённый складской факт и не мешает обмену с другими документами сборки. При сбое ТСД и Web показывают причину по документу. Повтор той же кнопкой «Закрыть и отгрузить» обрабатывает только неподтверждённые документы; после нового изменения источника он рассматривает новое расхождение и принимает новое решение до следующей записи. Повтор не создаёт второе складское списание.

Если после закрытия WMS статус РО 1С неожиданно изменился до завершения обмена, автоматический повтор останавливается. Руководитель видит актуальный документ и сохранённую цель, затем может явно разрешить повторное приведение строк и статуса к складскому факту через PATCH/POST; это не меняет проведённое списание. Если свежая проверка показывает целевые строки и статус «Отгружен», а проведение именно этой редакции подтверждено, WMS подтверждает успешную синхронизацию без повторной записи. Новое изменение источника после решения руководителя снова требует рассмотрения.

Если после складского закрытия РО 1С помечен на удаление, автоматический и ручной повтор PATCH/POST для него блокируются. WMS не снимает пометку удаления и не переносит распределённый факт на новый РО 1С автоматически. Складское списание остаётся проведённым; после восстановления того же документа в 1С руководитель заново сверяет его и разрешает обмен. Невозможность восстановить документ требует отдельного решения, не предусмотренного текущим сценарием.

Если после закрытия сборки на отдельный РО 1С распределено ноль товара, его строки передаются как «НеОтгружать» с количествами утверждённого плана WMS этого документа, а «Товары по распоряжениям» пусты. 1С допускает такой документ в статусе «Отгружен»; он не означает физической передачи товара. После закрытия WMS не хранит не забранный товар как остаток зоны отгрузки. Если покупатель не забрал товар, текущий этап не оформляет его обратное оприходование: руководитель отдельно организует будущую Приёмку по приходному ордеру после действий в 1С либо инвентаризационную корректировку после её переработки с учётом сроков. Эти действия создают новое складское поступление, а не откатывают закрытую сборку.

**Самостоятельная проверка**: закрыть сборку из двух документов при недоборе, добиться успешного обмена лишь по одному РО 1С и затем безопасно повторить обмен по второму; складской факт должен остаться неизменным.

## Требования

### Функциональные требования

- **FR-001**: WMS должна предоставлять отдельные рабочие места Отбора и Подпитки со своими точками входа на ТСД. Единственный режим завершения Отбора на этом этапе — «Закрыть и отгрузить»; отдельное рабочее место Отгрузки не входит в текущий объём.
- **FR-002**: Расходный ордер WMS должен иметь собственную идентичность и связывать один или несколько расходных ордеров 1С; один активный источник 1С не должен одновременно входить в два ордера WMS.
- **FR-003**: Сканирование свободного расходного ордера 1С в статусе «Подготовлен» должно создавать ордер WMS и первую связь. До начала Отбора к нему можно добавлять только свободные документы 1С того же склада; совпадение получателя, направления, даты и других реквизитов источников не требуется. До начала Отбора связанный документ можно открепить с пересчётом плана, освобождением документа и аудитом без записи в 1С. Открепление последнего документа отменяет пустой черновик РО WMS с сохранением истории.
- **FR-004**: До начала Отбора текущие документы 1С должны определять план WMS по каждому связанному документу и общий итог по SKU. Ордер WMS должен показывать различающиеся реквизиты источников отдельно, без выдачи одного значения за общее для всех.
- **FR-005**: Первая попытка начала Отбора должна зафиксировать перечень связанных документов 1С до отправки команд перевода в «КОтбору». Если переход любого документа не завершился успешно, Отбор и изменение набора источников блокируются до безопасного повтора либо отмены всей сборки. Повтор проверяет результат по каждому документу, не повторяет уже подтверждённые переходы и завершает оставшиеся; частичный успех сам по себе не возвращает документы в «Подготовлен». После успешного начала изменения данных 1С сами не переписывают план или факт WMS.
- **FR-006**: До закрытия Отбора уполномоченный работник должен иметь возможность исправлять записи о взятом товаре по исходной ячейке, SKU, учётной группе срока годности и количеству. Карточка Отбора показывает предлагаемый срок и доступное количество его группы; при известном учётном сроке работник сверяет его с маркировкой и подтверждает количество. Для редкой группы SKU с обязательным сроком, но без даты в учёте, карточка напоминает визуально проверить срок выбранного товара. Дата не вводится, отдельное действие не требуется, подтверждение количества сохраняет учётную группу `null`. Просроченный товар или товар с нечитаемым сроком отбирать нельзя. Факт сборки рассчитывается из записей Отбора; их редактирование не проводит складские остатки.
- **FR-007**: Перед закрытием WMS должна успешно получить актуальные данные каждого связанного документа 1С и повторно проверить, что известный срок годности отобранных групп не истёк. При недоступности хотя бы одного документа либо истёкшем известном сроке закрытие блокируется без складского проведения для оператора и руководителя склада. Для учётной группы без даты WMS не может автоматически повторить проверку срока при закрытии и опирается на визуальную проверку работника при Отборе. Оператор на ТСД может закрыть сборку только после завершения Отбора, совпадения факта WMS с общим планом WMS по SKU и совпадения плана WMS по каждому документу с его текущими строками 1С.
- **FR-008**: Руководитель склада через Web должен видеть план WMS, факт WMS и текущие данные документов 1С. Он может изменить количество и состав строк плана WMS согласно источникам и вернуть работу оператору для доведения факта до плана; либо утвердить складской результат и закрыть сборку вопреки конфликтующим изменениям строк и количества 1С. Изменения плана, просмотренные данные 1С, исполнитель, время и принятое решение сохраняются в аудите. Изменение склада связанного РО 1С не допускает менеджерского закрытия: сначала склад в 1С должен быть восстановлен либо вся сборка отменена.
- **FR-009**: Закрытие сборки должно одним авторитетным складским действием списывать фактически отобранный товар непосредственно из исходных ячеек за пределы складского остатка, сохраняя группы сроков годности в истории; промежуточное проведение в зону отгрузки и обязательные сканы «палета» либо ячейки отгрузки не допускаются. Складской факт сохраняется независимо от последующего успеха обмена с 1С. По каждому SKU сумма количества «Отгрузить» во всех связанных документах должна точно равняться проведённому факту; нераспределённый товар не допускается. Количество «Отгрузить» по отдельному документу и SKU не может превышать утверждённый план WMS для этого документа. Руководитель может восстановить изменённый после начала Отбора РО 1С до утверждённого плана через обмен, если 1С сможет провести получившийся документ; отказ проведения оставляет обмен в состоянии ошибки без повторного складского списания.
- **FR-010**: Закрытие должно сохранить отдельное целевое состояние обмена по каждому связанному документу 1С: строки «Отгрузить» и «НеОтгружать», распределённое количество и статус «Отгружен». Ожидание или ошибка обмена отображаются отдельно от проведённого складского факта; Web показывает полученную причину ошибки и повторное действие «Закрыть и отгрузить» для оператора и руководителя. После складского закрытия оно повторяет обмен только по неподтверждённым документам. Ошибка одного документа не блокирует обмен другого.
- **FR-011**: Перед записью целевого состояния в 1С WMS должна сверять текущий документ с состоянием, проверенным при закрытии оператором либо рассмотренным руководителем. При новом расхождении автоматическая запись старого решения блокируется до нового решения руководителя; закрытый факт WMS не переписывается. Документ 1С в WMS доступен только для чтения; изменение отправляется через OData PATCH, затем документ проводится через POST. Обычный сбой допускает повтор той же кнопкой на ТСД или в Web. Поддержка If-Match в используемой 1С отсутствует по проверке пользователя. Гонка между GET и PATCH принимается на текущем этапе. Свежая сверка перед записью сохраняется.
- **FR-012**: Документ с нулевым распределением завершается в 1С в статусе «Отгружен» со всеми применимыми строками «НеОтгружать» и пустыми «Товарами по распоряжениям», без складского списания для этого документа. Сборка с общим нулевым фактом не создаёт складских движений.
- **FR-013**: Подготовленные грузовые места физически группируются по РО 1С и помечаются его распечатанным документом; отдельный учёт грузовых мест в WMS на этом этапе не требуется.
- **FR-014**: WMS должна проверять известный срок годности выбранных групп при закрытии сборки и сохранять учётную группу срока, включая `null`, в истории списания. Распределение факта по документам 1С выполняется по SKU и количеству без назначения конкретных сроков каждому документу.
- **FR-015**: Товар, не забранный после закрытия сборки, не является учётным остатком зоны отгрузки. Текущий этап не создаёт операцию его обратного оприходования и не откатывает сборку; в будущем руководитель организует новую Приёмку по приходному ордеру 1С либо корректировку инвентаризации после её переработки с указанием фактического срока.
- **FR-016**: После закрытия сборки её проведённый складской факт не должен изменяться простой правкой количества; исправление физического результата требует явного отражения в складской истории.
- **FR-017**: WMS должна предлагать маршрут Отбора как рекомендацию и отдельно показывать общий список требуемых SKU. Отборщик может выбрать SKU вне предлагаемого порядка и другую допустимую ячейку для него, соблюдая FEFO и ограничения доступного количества; после подтверждённого действия или изменения доступных остатков WMS должна перестраивать маршрут для оставшейся потребности, сохраняя ранее подтверждённый факт.
- **FR-018**: Подтверждение физического Отбора в незакрытой сборке должно резервировать выбранное количество по ячейке, SKU и учётной группе срока; предложение маршрута не резервирует товар. Резерв принадлежит сборке и конкретному действию Отбора, а исполнитель сохраняется в истории. Доступное для другой работы количество рассчитывается из учётного остатка за вычетом активных резервов; никакая операция не должна повторно использовать зарезервированное количество. Уменьшение факта освобождает соответствующее количество резерва только после скана исходной ячейки и подтверждения, что освобождаемое количество находится в ней физически, включая исправление ошибочного ввода без физического возврата. Закрытие сборки проводит складской факт и завершает соответствующий резерв согласованно. Истечение времени само по себе не снимает резерв.
- **FR-019**: Один сотрудник может переключаться между несколькими начатыми сборками. Ожидание Подпитки не закрывает и не сбрасывает сборку: её черновой факт, резервы и оставшийся маршрут сохраняются до продолжения. Главная страница Отбора показывает незакрытые сборки, созданные сотрудником, и начатые сборки, закреплённые за ним. Закрытые сборки с неподтверждённым обменом остаются видимыми до его завершения. При возвращении скан любого связанного РО 1С открывает соответствующий РО WMS; для принятия начатой сборки другого сотрудника требуется явное подтверждение передачи ответственности.

- **FR-020**: Прямой палетный Отбор допускается только из ячейки «Хранения» с одним SKU; при нескольких сроках этого SKU сохраняется FEFO. Ячейка с несколькими SKU направляется в сценарий Подпитки. При допустимом прямом Отборе WMS должна удерживать исходную ячейку целиком за текущей сборкой после её скана и съёма поддона. Удержание запрещает другим операциям использовать или занять эту ячейку до закрытия сборки либо подтверждённого возврата поддона при отмене Отбора; количественный резерв факта учитывается отдельно, без повторного вычитания остатка.
- **FR-021**: После начала Отбора неожиданная смена статуса любого связанного РО 1С с «КОтбору», снятие проведения либо пометка удаления должна блокировать закрытие всей сборки для оператора и руководителя. WMS не восстанавливает статус автоматически; требуется исправление источника в 1С с повторной сверкой либо отмена всей сборки и возврат отобранного товара.
- **FR-022**: Изменение получателя связанного РО 1С после начала Отбора должно блокировать закрытие оператором. Руководитель склада может утвердить закрытие после сверки физически сгруппированного товара с актуальным документом; WMS сохраняет прежнее и текущее значение получателя и решение руководителя в аудите, не изменяя получателя в 1С. Смена получателя не разрешает обход блокировки по складу, статусу, складской операции или пометке удаления.
- **FR-023**: Изменение складской операции связанного РО 1С после начала Отбора должно блокировать закрытие всей сборки для оператора и руководителя склада. WMS не возвращает операцию в прежнее состояние автоматически: требуется исправление в 1С и повторная сверка либо отмена сборки с физическим возвратом товара.
- **FR-024**: При изменении типа очереди связанного РО 1С уже заказанные, но ещё не начатые Подпитки должны менять место в очереди подпитчика по актуальному наивысшему приоритету документов сборки. Начатые задания не переназначаются и не прерываются. Время первоначального запроса сохраняется для сортировки внутри одного приоритета.
- **FR-025**: Изменения плановой даты отгрузки и направления доставки связанного РО 1С после начала Отбора должны обновлять их отображаемые значения без автоматической правки плана или факта WMS. Сами по себе они не блокируют закрытие сборки и не влияют на приоритет Подпиток; остальные проверки источника сохраняются.
- **FR-026**: Неожиданная смена статуса связанного РО 1С после закрытия WMS и до подтверждения обмена должна останавливать автоматический повтор. Руководитель склада может после просмотра свежего состояния явно разрешить PATCH/POST к сохранённой цели «Отгружен»; складской факт не меняется. Если свежая проверка подтверждает целевые строки, статус и проведение, обмен отмечается успешным без повторной записи. Новое изменение после решения руководителя требует нового рассмотрения.
- **FR-027**: Пометка удаления связанного РО 1С, появившаяся после складского закрытия, должна блокировать автоматический и ручной PATCH/POST для этого документа до восстановления того же РО 1С в источнике. WMS не снимает пометку и не переназначает распределённый факт другому документу автоматически; складское списание не откатывается. После восстановления руководитель заново сверяет источник и разрешает обмен.
- **FR-028**: При выборе подпитчиком другого допустимого источника WMS должна удержать просканированную ячейку и пересчитать рекомендации источников для остальных ещё не начатых заказов того же SKU без отмены заказов или двойного назначения остатка. Отсутствие доступного источника для невыполненной потребности показывается явно сборщику и подпитчику; новое задание автоматически не создаётся.
- **FR-029**: Подтверждённое перемещение Подпитки в целевую ячейку должно сохраняться при прерывании работы и повторном открытии задания. WMS показывает подпитчику проведённое количество и незавершённый возврат поддона либо подтверждение пустой ячейки, сохраняет удержание исходной ячейки до её скана при завершении работы с поддоном и не проводит перемещение повторно при повторе той же команды. Сборщик видит проведённое количество доступным после первого успешного проведения, независимо от возврата поддона.
- **FR-030**: При фактической недостаче в источнике Подпитки WMS должна зафиксировать расхождение и блокировать спорный учётный остаток, не корректируя его молча. Подпитчик может провести физически найденное количество в целевую ячейку и после завершения работы с поддоном продолжить недостающую часть из другого допустимого источника в том же задании. До выполнения всего заказа задание остаётся незавершённым; уже проведённый товар доступен сборщику, а отсутствие другого свободного источника показывается явно без автоматического создания нового задания.
- **FR-031**: Если после Подпитки на исходном поддоне не осталось физического товара, подпитчик должен сканировать исходную ячейку и подтвердить, что она освобождена. Это снимает исключительное удержание всей ячейки без нового движения товара, но не снимает отдельную блокировку спорного остатка, если ранее была зафиксирована недостача.
- **FR-032**: Успешный скан источника с удержанием ячейки начинает задание Подпитки. До этого момента заказ может быть отменён при исчезновении потребности или отмене сборки. Начатое задание нельзя отменять из-за изменения потребности или вручную: подпитчик выполняет заказанное количество и завершает работу с источниками. Отмена сборки ожидает завершения начатых Подпиток; уже проведённые перемещения не откатываются. Физически невыполнимое задание остаётся на разборе без автоматического освобождения удержаний и блокировок.
- **FR-033**: Введённое количество Подпитки можно исправить до подтверждения в целевой ячейке. После проведения движения исходный факт не редактируется. Для исправления ошибки руководитель склада оформляет отдельное корректирующее складское движение с причиной и связью с исходным шагом; подпитчик не получает отдельный сценарий правки проведённого количества.
- **FR-034**: Подпитка из исходной ячейки с несколькими SKU допустима при удержании всей ячейки. WMS выделяет на экране SKU задания и его сроки, показывает другие SKU только для сведения и принимает количество переноса только по SKU задания и выбранной группе срока. Остальные SKU не должны изменяться при проведении этого шага; при их физическом остатке работа с источником завершается сканом возврата, а не подтверждением пустой ячейки.
- **FR-035**: При сканировании исходной и целевой ячеек Подпитки и повторно перед проведением WMS должна проверять склад, активность, назначение зоны и действующие блокировки. Источник должен иметь доступное количество SKU задания с учётом FEFO; целевая ячейка должна допускать итоговый состав SKU по правилу смешения. При неуспехе WMS показывает причину и разрешает выбрать другой допустимый адрес без движения; удержание уже снятого источника сохраняется до завершения работы с поддоном.
- **FR-036**: Рабочие места Отбора и Подпитки, включая прямой палетный Отбор, должны быть доступны пользователю с существующей ролью `Operator` без отдельной роли подпитчика или допуска к погрузчику в WMS. Решения по исключениям, снятие блокировки через учётную корректировку и корректирующие движения требуют явного членства в `Manager`; роль `Administrator` сама по себе этих прав не даёт.
- **FR-037**: Начатая Подпитка не должна блокировать закрытие и отгрузку сборки, если её факт уже полностью набран другим допустимым Отбором и выполнены остальные проверки закрытия. Задание подпитчика сохраняется до своего завершения; его последующее проведение пополняет обычный складской остаток целевой ячейки и не меняет закрытый факт сборки.
- **FR-038**: Пользователю с ролью `Operator` в списках и карточках SKU, кроме списка подбора, должна быть доступна кнопка «i» для просмотра SKU по ячейкам. Основным числом показывается количество, доступное для новой работы с учётом резервов и блокировок; учётный остаток дополнительно показывается только при отличии от доступного. Просмотр не должен изменять остатки.
- **FR-039**: Расчёт маршрута должен сразу показывать отборщику все необходимые Подпитки SKU, даже если нужен перенос из нескольких источников. Отборщик явно заказывает каждую из них. Подтверждение подпитчиком количества в целевой ячейке проводит перемещение из «Хранения» в «Комплектацию» и делает это количество доступным Отбору без ожидания возврата поддона; сам источник остаётся удержанным до подтверждённого завершения работы с ним.

### Основные сущности

- **Расходный ордер WMS**: самостоятельное складское задание для общего Отбора; содержит связи с документами 1С, план, факт и состояние завершения сборки.
- **Расходный ордер 1С**: отдельный источник плана и отдельная единица обмена с 1С при закрытии сборки.
- **План WMS**: запланированные строки по связанным документам 1С и общий итог по SKU; изменения после начала Отбора выполняет руководитель склада и сохраняет в аудите.
- **Факт WMS**: до закрытия исправляемые записи физического Отбора по ячейке, SKU и сроку; после закрытия проведённый итог по SKU и его распределение по документам 1С.
- **Текущие данные источников 1С**: полученные при проверке строки и количества каждого связанного документа; WMS показывает их отличие от плана WMS, не подменяя им план начатой сборки.
- **Грузовое место / группа товара РО 1С**: физически отложенный в зоне отгрузки товар конкретного документа. Сборщик берёт распечатанные РО 1С и по мере набора формирует отдельные группы товара, помечая каждую соответствующим бумажным документом. Раскладка и проверка содержимого остаются его ответственностью; отдельное подтверждение каждой группы в WMS на этом этапе не требуется.
- **Целевое состояние РО 1С**: сохранённые при закрытии сборки строки, распределённое количество и статус «Отгружен» вместе с состоянием синхронизации конкретного документа.

## Критерии успеха

### Проверяемые результаты

- **SC-001**: В проверке с двумя документами 1С одного SKU создаётся ровно один ордер WMS с двумя источниками; повторное сканирование не создаёт второго активного ордера или связи.
- **SC-002**: При расхождении факта WMS с планом WMS или плана WMS по документу с текущими строками соответствующего РО 1С закрытие оператором блокируется. После согласования плана с 1С и доведения факта до плана оператор может закрыть сборку; руководитель склада может вместо этого утвердить складской результат для передачи в 1С с сохранением решения в аудите.
- **SC-003**: До закрытия сборки складское списание и целевой статус «Отгружен» по её документам 1С не возникают; на ТСД нет отдельного действия Отгрузки.
- **SC-004**: В проверке с двумя связанными документами сбой обмена по второму не отменяет успешно синхронизированный первый и не откатывает складское списание.
- **SC-005**: После закрытия не забранный товар отсутствует в учётном остатке WMS; само сообщение, что покупатель не забрал товар, не создаёт остаток и не отменяет складское списание.
- **SC-006**: В проверках добавления или открепления источника после начала Отбора перечень документов сборки остаётся неизменным; при изменении уже прикреплённого документа план и факт WMS сами не меняются, а закрытие оператором блокируется до решения руководителя склада.
- **SC-007**: До закрытия изменение записей Отбора не меняет складские остатки; успешное закрытие уменьшает остатки исходных ячеек на подтверждённый факт без создания промежуточного остатка зоны отгрузки.
- **SC-008**: Повтор обмена с одним из двух РО 1С после закрытия не создаёт нового складского движения и не меняет цель обмена для другого документа.
- **SC-009**: При закрытии с недобором по одному SKU в двух документах 1С сумма утверждённых количеств «Отгрузить» по ним равна фактически собранному количеству; попытка оставить часть факта без документа отклоняется без складского проведения.
- **SC-010**: При согласовании руководителем склада изменения количества или состава документа 1С план WMS обновляется с сохранением решения в аудите; последующее исправление оператором записей Отбора меняет факт WMS без складского движения до закрытия.
- **SC-011**: После закрытия сборки изменение РО 1С не меняет проведённый факт WMS; старый PATCH блокируется, пока руководитель не рассмотрит новые строки и не разрешит привести документ к распределённому на него факту.
- **SC-012**: При сборке двух документов одного склада смена склада одного источника останавливает закрытие для оператора и руководителя склада до исправления источника либо отмены всей сборки.
- **SC-013**: При плане 5 + 5 и факте 10 распределение 10 + 0 отклоняется из-за превышения плана первого документа, хотя общий итог равен факту WMS.
- **SC-014**: Если актуальные данные хотя бы одного связанного документа 1С не получены перед закрытием, сборка остаётся открытой без движения остатков. Если чтение всех документов прошло успешно, сборка закрыта в WMS, а последующая запись в 1С завершилась ошибкой, складское движение сохраняется и ошибка обмена показывается отдельно.
- **SC-015**: Если срок выбранной при Отборе группы истёк до закрытия сборки, закрытие блокируется без складского движения.
- **SC-016**: При остатке 10 и подтверждённом Отборе 7 из ячейки другая сборка видит доступными не более 3. Запрос на уменьшение факта с 7 до 4 не увеличивает доступное количество до 6, пока сборщик не просканирует исходную ячейку и не подтвердит, что освобождаемые 3 физически находятся в ней.
- **SC-017**: Сборщик, оставивший первую сборку ждать Подпитки и выполнивший Отбор по второй сборке, при возвращении к первой видит прежний черновой факт, резервы, заказанные Подпитки и обновлённый остаток маршрута; две сборки сохраняют разные идентификаторы и составы РО 1С.
- **SC-018**: Если после закрытия сборки на один из связанных РО 1С распределено ноль, WMS не создаёт для него складского списания; после успешного обмена документ 1С имеет статус «Отгружен», все применимые строки «НеОтгружать» и пустую таблицу «Товары по распоряжениям».
- **SC-019**: Если руководитель склада закрыл сборку с общим нулевым фактом и недостачей, WMS не создаёт складских движений и доводит все связанные документы 1С до статуса «Отгружен» без физической выдачи; отмена сборки остаётся отдельным действием.
- **SC-020**: После скана исходной ячейки и съёма поддона для прямого Отбора другой работник не может использовать или занять эту ячейку; подтверждённое количество Отбора резервируется отдельно. Успешное закрытие сборки либо подтверждённый возврат поддона при отмене освобождает удержание ячейки.
- **SC-021**: Если начальный план РО 1С по SKU равен 5, после начала Отбора источник изменён на 3, а факт WMS равен 5, руководитель может сохранить план 5, закрыть сборку и отправить цель 5 в 1С. Успешный POST подтверждает обмен; отказ 1С оставляет этот документ с ошибкой обмена без изменения проведённого складского факта.
- **SC-022**: Если в начатой сборке из двух РО 1С один документ вместо «КОтбору» получил другой статус или пометку удаления, закрытие всей сборки не создаёт складского списания даже при совпадении количеств и попытке руководителя подтвердить расхождение.
- **SC-023**: Если SKU требует срок годности, а доступный остаток числится без даты, карточка показывает напоминание проверить маркировку. После обычного подтверждения количества факт и складское списание сохраняют учётную группу `null`; ввода даты и дополнительного действия нет. Для известных дат прежняя автоматическая проверка просрочки при закрытии сохраняется.
- **SC-024**: Если ячейка «Хранения» содержит два SKU, маршрут не предлагает прямой палетный Отбор из неё даже при подходящем количестве одного SKU; потребность показывается для Подпитки. Ячейка с одним SKU и несколькими сроками остаётся допустимой при соблюдении FEFO.
- **SC-025**: Если до начала Отбора от сборки из двух РО 1С открепить один, план пересчитывается, а освобождённый документ можно прикрепить к другой сборке. Открепление оставшегося документа отменяет пустой черновик, не меняя статусы источников 1С.
- **SC-026**: Если во время Отбора изменился только получатель одного РО 1С, закрытие оператором отклоняется без складского списания; руководитель видит оба значения, сверяет группу товара и может закрыть сборку с аудируемым решением без PATCH получателя.
- **SC-027**: Если во время Отбора складская операция хотя бы одного связанного РО 1С изменилась, совпадение SKU и количеств не разрешает закрытие сборки ни оператором, ни руководителем; складского списания нет.
- **SC-028**: После смены очереди РО 1С с «СобственнаяДоставка» на «ЖиваяОчередь» не начатая Подпитка этой сборки поднимается в списке при очередном обновлении; начатое задание сохраняет исполнителя, а время его запроса не сбрасывается.
- **SC-029**: Если после начала Отбора в РО 1С изменились только плановая дата и направление доставки, ТСД показывает актуальные значения, а совпадающие план WMS и факт могут быть закрыты оператором без решения руководителя; порядок Подпиток от этих реквизитов не меняется.
- **SC-030**: Если после складского закрытия РО 1С неожиданно вернулся в статус «Подготовлен», автоматический повтор обмена останавливается; руководитель после свежей проверки может разрешить восстановление цели «Отгружен» без нового списания WMS. Если подтверждено проведение редакции РО 1С с целевыми строками и статусом, WMS фиксирует успех без PATCH/POST.
- **SC-031**: Если при первой попытке начать сборку из двух РО 1С первый документ успешно перешёл в «КОтбору», а второй остался «Подготовлен», WMS не разрешает Отбор или изменение состава. Повтор не переключает первый документ заново, пытается завершить переход второго и разрешает работу только после проверки обоих. Отмена всей сборки возвращает первый документ в «Подготовлен» лишь при неизменном состоянии источника.
- **SC-032**: Если после складского закрытия связанный РО 1С помечен на удаление, повтор обмена для него не отправляет PATCH/POST и не меняет складской факт. После восстановления того же документа в 1С руководитель видит новое состояние и может разрешить обмен.
- **SC-033**: Если подпитчик вместо рекомендованной ячейки X сканирует допустимую ячейку Y, WMS удерживает Y, оставляет другие не начатые заказы того же SKU и обновляет их рекомендуемые источники. Если свободного источника больше нет, оба рабочих места показывают «Нет доступного источника»; заказ не дублируется и снятый поддон не переназначается.
- **SC-034**: После подтверждения перемещения 5 шт. в целевую ячейку связь с ТСД пропадает до возврата поддона. Повторное открытие задания показывает проведённые 5 шт. и необходимость вернуть поддон; повтор подтверждения не добавляет ещё 5 шт. Сборщик видит 5 шт. доступными, а исходная ячейка остаётся удержанной до скана возврата.
- **SC-035**: Для Подпитки 10 шт. источник учитывает 10, но подпитчик обнаружил только 8. WMS блокирует спорные 2 шт. и разрешает провести найденные 8 шт.; сборщик видит «8 из 10» и может отобрать эти 8. Подпитчик сканирует исходную ячейку и подтверждает, что она физически пуста: удержание всей ячейки снимается, а блокировка спорных 2 шт. остаётся. Затем он берёт оставшиеся 2 шт. из другой допустимой ячейки в том же задании. Если источника нет, задание остаётся незавершённым с явной причиной ожидания.
- **SC-036**: Подпитчик сканирует источник для заказа 10 шт., после чего сборщик закрывает потребность другим Отбором. Задание подпитчика остаётся открытым с исходными 10 шт.; он выполняет Подпитку и завершает работу с поддоном. Переложенный товар остаётся доступным в целевой ячейке. Если источник ещё не был просканирован, невостребованный заказ отменяется до начала работы подпитчика.
- **SC-037**: Подпитчик подтвердил перенос 5 шт., но обнаружил, что физически переложил 4. Подтверждённые 5 шт. нельзя заменить на 4 простой правкой. Руководитель оформляет отдельное корректирующее движение на разницу с причиной и ссылкой на шаг Подпитки; история сохраняет оба движения, а итоговый остаток соответствует 4 шт.
- **SC-038**: В исходной ячейке числятся SKU A и B; задание требует SKU A. После скана ячейки экран выделяет A и показывает B для сведения. Подпитчик подтверждает количество A, WMS проводит только A, а B остаётся без движения. После возврата остатка поддона с B и скана источника удержание ячейки снимается.
- **SC-039**: После заказа Подпитки рекомендуемая целевая ячейка оказалась заблокирована либо в ней появился другой SKU при запрете смешения. Подтверждение не проводит товар и объясняет отказ; подпитчик сканирует другую допустимую ячейку. Исходная ячейка остаётся удержанной до возврата поддона или подтверждения, что она физически пуста.
- **SC-040**: Пользователь с ролью `Operator` может открыть отдельные рабочие места Отбора и Подпитки и выполнить допустимый прямой палетный Отбор, но не может снять блокировку недостачи или исправить проведённое количество. Пользователь с явной ролью `Manager` может выполнить такие решения; одно членство в `Administrator` не заменяет `Manager`.
- **SC-041**: Подпитчик начал задание на 10 шт., но сборщик полностью набрал заказ из других ячеек и успешно закрыл сборку. Задание подпитчика остаётся в работе до переноса 10 шт. и завершения работы с поддоном; проведённый позже товар учитывается в целевой ячейке и не создаёт второго списания по закрытой сборке.
- **SC-042**: Оператор открывает «i» в карточке SKU и видит доступное количество по ячейкам. Для ячейки с учётным остатком 10 и резервом 4 рядом с доступными 6 показан учётный остаток 10; без различия выводится одно число. Закрытие окна возвращает к работе без изменения остатков. В списке подбора такой кнопки нет.
- **SC-043**: Для потребности, требующей двух Подпиток, сборщик видит оба предложения и отдельно подтверждает их заказ; сам расчёт маршрута не создаёт задания подпитчику. После подтверждения первого переноса его количество доступно для Отбора, хотя исходный поддон ещё не возвращён; второе задание сохраняется отдельно.
- **SC-044**: Для строк одного SKU с планом 3 и 7 и распределением 8 адаптер записывает «Отгрузить» 3 и 5 в исходном порядке, а оставшиеся 2 оформляет «НеОтгружать» с сохранением связи распоряжения.
- **SC-045**: После закрытия сборки из двух РО 1С первый обмен подтверждён, по второму потерян ответ POST. Повторное нажатие «Закрыть и отгрузить» оператором пропускает первый документ, сверяет второй и повторяет его POST. В WMS остаётся одно складское списание.
- **SC-046**: Если перед повтором обнаружены новые изменения источника, оператор видит необходимость решения руководителя. Успешные документы и проведённое списание сохраняются.

## Допущения

- Склад ордера WMS определяется первым прикреплённым документом 1С и не меняется при добавлении следующих источников.
- «Не забрали» означает, что товар физически остался после закрытия сборки и уже исключён из учётного остатка WMS. Возврат товара покупателем после фактической передачи рассматривается отдельно.
- История списания сохраняет сроки исходных ячеек; распределение количества по РО 1С не определяет, какие сроки достались каждому документу. Физическая раскладка товара по бумажным РО 1С выполняется сборщиком без отдельного подтверждения каждой группы в WMS.

## Границы текущего этапа

- Рабочий режим один: «Закрыть и отгрузить». Отдельное рабочее место Отгрузки и переключение режимов в этом этапе не разрабатываются.
- После закрытия сборки её проведённый факт не редактируется. Если потребуется исправить уже проведённый складской результат, это будет отдельная операция с движением и аудитом, а не правка закрытой сборки.
- При отмене незакрытой сборки отобранный товар возвращается в исходные ячейки по согласованному сценарию. Дополнительный способ отмены без такого возврата в текущий этап не входит.
- Товар, не забранный после закрытия, уже списан со склада; для его оприходования руководитель организует инвентаризационную корректировку после её переработки либо новую Приёмку по приходному ордеру 1С. Правила этих операций определяются в их собственных процессах.
- Легаси Перемещение и Инвентаризация заменяются отдельными будущими процессами без перехода и переноса старой работы. Их адаптация к резервам в текущий этап не входит. Новые процессы должны использовать общие ограничения доступности. Возврат после передачи покупателю относится к отдельному этапу.

## Информация о SKU

В списках и карточках SKU, кроме списка подбора, оператору доступна небольшая кнопка «i». Она открывает просмотр SKU по ячейкам: что лежит, где и сколько доступно для новой работы. Если резерв или блокировка уменьшает доступность, рядом показывается учётный остаток. На этом этапе для просмотра достаточно роли `Operator`; действия с остатками из этого окна не выполняются.
