# План реализации: Отбор, подпитка и закрытие с отгрузкой

**Ветка**: `codex/011-outbound-workflows` | **Дата**: 2026-11-10 | **Спецификация**: [spec.md](spec.md)

## Суть

Заменить легаси Отбор и Отгрузку самостоятельной мультиордерной сборкой WMS и отдельным рабочим местом Подпитки. Текущий способ завершения — «Закрыть и отгрузить»: одно проведение отобранного товара непосредственно из исходных ячеек, затем независимый обмен с 1С по каждому связанному РО. До закрытия физический Отбор удерживает количество в ячейке; Подпитка проводит перенос при подтверждении целевой ячейки. Факт, резервы, блокировки недостач и обмен имеют явные разные состояния.

Подробные технические решения и варианты приведены в [research.md](research.md), модель — в [data-model.md](data-model.md), внешние границы — в [contracts](contracts/).

## Проверка конституции

**До исследования и после проектирования: пройдено.**

| Принцип | Применение |
|---|---|
| I. WMS владеет складским остатком | Физический факт и движения принадлежат WMS. После начала Отбора изменения 1С не меняют план сами; опубликованный факт не переписывается. Исправления дают новые движения. |
| II. Одно проведение на физическое событие | Закрытие сборки списывает факт один раз; Подпитка проводит каждый подтверждённый перенос один раз; исправление недостачи — отдельное движение. Старые пути Отбора/Отгрузки удаляются при включении замены. |
| III. Явная граница 1С | В Application находятся решения по снимкам и состояниям, в Integration — OData GET/PATCH/POST и маппинг. Ошибка 1С не откатывает складское проведение. |
| IV. Прямое устройство | Отдельный исполнитель на бизнес-команду, существующие проекты и `CommandExecutor`; маршрутизация и доступность — небольшие предметные компоненты без нового проекта или общего движка процессов. |
| V. Проверка риска | Новые проверки только для одновременной работы, повторов, атомарного проведения и потери данных; UI и реальные ответы 1С проверяет разработчик. |

Технических отступлений от конституции нет. Правило `AGENTS.md` о выполнении сборок, тестов и миграций разработчиком отражено в [quickstart.md](quickstart.md).

## Техническая схема

### Владение состоянием и проектные границы

| Состояние / действие | Где живёт | Граница записи |
|---|---|---|
| Текущий РО 1С, включая строки и реквизиты | Существующий импортируемый `ShippingOrder` как проекция источника; маппинг GET/уведомлений в `Wms.Integration` | Обновление источника не меняет план начатой сборки. Старые операционные поля записи остаются историческими до безопасного удаления; новый процесс их не использует для факта. |
| РО WMS, связи, план по документам, физический Отбор | Новые сущности `Wms.Domain`; исполнители и запросы `Wms.Application`; EF конфигурация `Wms.Infrastructure` | Одна активная связь на `Ref_Key`; после первой попытки начала набор источников заморожен. План, факт и текущий источник показываются раздельно. |
| Резерв, удержание ячейки, блок недостачи | Предметные состояния в Domain, расчёт доступности в Application, конкурентная запись в Infrastructure | Подтверждение физического действия, ограничения доступности, аудит и квитанция коммитятся вместе. Удержание не вычитается из остатка вторично. |
| Датированное проведение Отбора, Подпитки и коррекции | Именованные исполнители Application через существующий механизм движений/остатков/оборотов Infrastructure | Каждое физическое событие имеет одну точку проведения; отдельный 1С запрос не входит в складскую транзакцию. |
| Цель и ход обмена по каждому РО 1С | Сохранённое целевое состояние WMS, исполнитель обмена Application, OData адаптер Integration | PATCH/POST повторяются по документу без повторного складского списания. |
| Рабочие места | `Wms.Contracts`, `Wms.WebApi`, `Wms.Mobile`, `Wms.WebApp` | Роли проверяются сервером: физические действия — явный `Operator`, исключения — явный `Manager`. |

Новые проекты, общий движок маршрутов и универсальный процессный оркестратор не нужны. Общий расчёт доступности используется маршрутами, сканами, Подпиткой и окном «i». Действующие операции, меняющие те же ячейки, должны перед проведением учитывать резерв, удержание и блок недостачи: в частности, Перемещение, Инвентаризация, размещение в удерживаемую ячейку и корректировки. Если старый исполнитель не способен однозначно выбрать датированную группу, он отклоняет конфликтующий шаг, а не обходит ограничение. Именованный исполнитель отвечает за одну бизнес-команду; запросы чтения не проводят складской факт.

### Состояния и моменты, которые нельзя смешивать

| Объект | Переход | Обязательный эффект |
|---|---|---|
| Сборка | Черновик → попытка начала | Сохранить список документов и действующий план по каждому **до** внешних запросов в 1С. Частичный успех переходов оставляет сборку заблокированной, повтор обрабатывает только незавершённые документы. |
| Сборка | Начата → закрыта | Сначала свежий GET всех РО 1С и проверки, затем один складской коммит списания и целей обмена. После коммита факт неизменяем. |
| Сборка | Начата → отменена | Вернуть по исходным ячейкам весь физический факт, освободить резервы, дождаться начатых Подпиток; вернуть статусы 1С отдельным повторяемым обменом. |
| Отбор | Подтверждение / уменьшение записи | Подтверждение создаёт количественный резерв без движения. Уменьшение требует скана исходной ячейки и подтверждения физического наличия; резерв уменьшается вместе с фактом. |
| Подпитка | Предложена → заказана → источник снят → количество добавлено → источник возвращён/пуст | Предложение не резервирует товар. Скан источника удерживает всю ячейку и начинает задание; подтверждение назначения проводит одну группу срока; повторный скан источника освобождает удержание. Частично выполненное задание может начать новый цикл источника. |
| Обмен РО 1С | Ожидает → PATCH проверен → POST подтверждён либо ошибка/новое решение | Стадия каждого документа хранится отдельно. Сбой обмена не возвращает закрытую сборку в работу. |

Это логические состояния; точные имена enum и переходы БД определяются в коде. Поля и ограничения перечислены в [data-model.md](data-model.md).

### Исполнители и границы транзакций

| Группа команд | Исполнители Application | Что сохраняется атомарно / что идёт отдельно |
|---|---|---|
| Формирование | Создать сборку по скану, прикрепить/открепить источник, принять сборку другого сотрудника | Связи, план до начала, ревизия и аудит в `CommandExecutor`. Уникальность активного `SourceRefKey` проверяется БД. Скан уже связанного источника открывает его сборку, не создаёт вторую. |
| Начало | Начать Отбор, повторить незавершённый переход источников | Сначала зафиксировать набор документов и намерение перехода в WMS. Затем обращаться к 1С по одному документу, сохраняя подтверждённый результат каждого. Сетевые вызовы не держат транзакцию БД открытой. |
| Физический Отбор | Удержать палетную ячейку, подтвердить выбор, уменьшить запись после скана/возврата, сообщить о недостаче | Запись факта + соответствующий резерв/удержание/блок + ревизия сборки + аудит + квитанция одной командой. Движения остатков пока нет. Удержание всей ячейки не выдаётся, если в ней уже есть чужой резерв или удержание. |
| Решение недостачи | Подтвердить коррекцию либо снять ошибочный блок | Датированное корректирующее движение, остаток и оборот с освобождением блока либо только мотивированное освобождение; аудит и квитанция в том же коммите. Факт сборки не редактируется. |
| Подпитка | Заказать, удержать источник, подтвердить перенос группы, сообщить о недостаче, завершить работу с источником | При подтверждении переноса: шаг, датированное движение Хранение→Комплектация, оба остатка, обороты, прогресс, аудит и квитанция в одном коммите. Возврат источника снимает только удержание. |
| План и закрытие | Изменить план, утвердить распределение, закрыть оператором либо руководителем, отменить | Закрытие фиксирует итог по каждому SKU/документу, проводит все исходящие движения из исходных ячеек, завершает резервы/удержания и создаёт цели обмена одним коммитом. Общий нулевой факт даёт ноль движений. |
| Обмен | Отправить цель РО 1С, повторить обмен, разрешить новый конфликт источника | Чтение/запись 1С и сохранение стадий обмена отдельно от складского коммита. Повтор не вызывает исполнителя закрытия. |

Каждая меняющая команда использует идентификатор запроса, семантический хеш, аудит и квитанцию существующего `CommandExecutor`. Для двух разных команд, претендующих на один остаток, нужны сериализуемая проверка/запись либо равнозначный механизм БД: одного повторного ключа команды недостаточно. При конфликте клиент получает актуальное состояние и оставляет физическое действие для осознанного повтора.

### Расчёт доступности и маршрута

1. Читать учётные группы `(склад, ячейка, SKU, срок)`, активные резервы, блоки недостачи и удержания. Для новой работы доступно учётное количество за вычетом резервов и заблокированного количества; чужое удержание исключает ячейку целиком. Сообщение об обычной недостаче Отбора блокирует всю спорную свободную группу до разбора; при Подпитке найденное количество остаётся у владельца снятого поддона, а недостающее блокируется. Исторически нулевые ячейки могут предлагаться только как возможное назначение Подпитки, не как источник товара.
2. Сначала разложить потребность SKU по срокам FEFO: известные даты по возрастанию, группа `null` после них. Просроченные известные группы исключить. Для `null` карточка требует визуальной проверки маркировки, но не вводит дату; при закрытии автоматическая повторная проверка доступна только известным датам.
3. В пределах разрешённого срока выбирать ячейки так, чтобы освобождать подходящие малые остатки и уменьшать число операций. Полное совпадение потребности с остатком ячейки предпочесть частичному выбору. Прямое снятие полного поддона из Хранения допустимо только для ячейки с одним SKU и не может нарушать FEFO; несколько таких ячеек выбираются последовательно при необходимости. Иначе предлагать Подпитку.
4. Выбранные обычные адреса упорядочить по разобранному `Code` в иерархии помещение–ряд–стойка–уровень–ячейка и пройти в обратном порядке. Нетиповые адреса сравнивать по `Code`; `PickSequence` не учитывать. Палетный шаг может предшествовать адресному обходу, чтобы сначала снять поддон и затем доложить товар.
5. Возвращать список шагов как рекомендацию с версией доступности и полный список предложений Подпитки сразу. Выбор другого SKU/ячейки сборщиком проходит те же проверки по скану. После подтверждённого действия или изменения доступности перестроить только оставшуюся часть, не менять сохранённый факт и заказанные задания автоматически.

Точные предпочтения при равенстве и примеры находятся в [разделе маршрута спецификации](spec.md#выбор-ячеек-и-маршрут-отбора-рабочие-правила). Алгоритм допускает пересмотр рекомендаций без изменения учётной модели и команд физического Отбора.

### Закрытие и обмен с 1С

1. До закрытия получить свежий GET **каждого** привязанного РО 1С. Неуспешное чтение, снятие проведения, иной склад/операция, неожиданный статус или пометка удаления блокируют складской коммит для всех. Изменённого получателя может рассмотреть только руководитель. Очередь, дата и направление обновляют показ, не останавливая закрытие.
2. Сравнить план WMS по каждому документу с актуальными строками источника, затем общий план с фактом. Оператор закрывает только при полном совпадении. Руководитель либо меняет план и возвращает физическую работу сборщику, либо утверждает закрытие с явным распределением недобора общего SKU и причиной. Распределение по документу не выше утверждённого для него плана, сумма по документам равна факту SKU.
3. Непосредственно перед записью заново проверить ревизию сборки, соответствие каждой записи её собственному резерву, достаточность учётного остатка для списания с сохранением чужих резервов и известные сроки. В одном коммите записать движения списания, остатки, обороты, закрытый факт, завершение резервов/удержаний, распределение, рассмотренные версии источников, цели обмена, аудит и квитанцию. Не создавать промежуточный остаток зоны отгрузки и не требовать её скан.
4. Пропустить документы с подтверждённым успехом. Для каждого оставшегося РО 1С отдельно читать источник перед записью. Если цель уже достигнута, отметить выполненную стадию. Если документ менялся после рассмотренного состояния, остановить старое решение и показать новое расхождение. Иначе выполнить PATCH целевых строк/статуса `Отгружен`, проверить получившееся состояние, выполнить POST и подтвердить результат. Если PATCH уже принят, повторить POST. После потери ответа POST повторное проведение допускается той же кнопкой «Закрыть и отгрузить». Для закрытой сборки сервер выполняет только ветвь обмена с сохранёнными целями, защищая документ от параллельных попыток.
5. При отказе 1С сохранить стадию и понятную причину на конкретном документе. Складской факт, распределение и успешный обмен других документов остаются. Оператор или руководитель повторяет обычный сбой той же кнопкой. При новых расхождениях руководитель принимает решение после свежего GET; новый складской коммит не выполняется. Документ с нулевым распределением всё равно получает статус `Отгружен` и строки `НеОтгружать`.

Пользователь подтвердил отсутствие поддержки If-Match. Гонка внешней правки между GET и PATCH принимается на текущем этапе. Свежая сверка источника перед записью сохраняется. Последовательность заполнения строк и повтор POST описаны в [контракте обмена](contracts/one-c-exchange.md).

### Клиенты и замена старого пути

| Поверхность | Новая работа | Убираемый путь |
|---|---|---|
| Mobile старт | Две кнопки: «Отбор» и «Подпитка»; одна роль `Operator` | Общая кнопка «Отбор и отгрузка». |
| Mobile Отбор | Свои сборки, скан РО 1С, документы, SKU, маршрут, Подпитки, карточка скана ячейки и факта, закрытие | Старые страницы `Pages/ShippingOrders`, палет и ячейка отгрузки как обязательные сканы, отдельное действие Отгрузки. |
| Mobile Подпитка | Очередь, задание, скан источника, назначение и количество по сроку, возврат/пустая ячейка | Самостоятельное рабочее место вводится в этом этапе. |
| Web | Сборка WMS с тремя состояниями, текущими источниками, недостачами, распределением, решениями и стадиями обмена | Старые страницы `ShippingOrderPages`, ручное закрытие старого 1:1 РО и отдельная Отгрузка. |
| API и контракты | Новые Mobile V1 запросы с `ClientRequestId` и явными политиками ролей; чтение без побочного создания | `MobileShippingOrderEndpoints` и старые DTO/клиент, ведущие к прежнему проведению. |

Сканирование использует существующую границу устройства и защиту от устаревших callback по образцу Приёмки. Неясный ответ сохраняет тот же `ClientRequestId` на экране. Право физического действия определяется `Operator`, право решения — членством в `Manager`; наличие `Administrator` само по себе недостаточно. Контракты экранов и команд: [Mobile V1](contracts/mobile-v1.md), [Web руководителя](contracts/manager-web.md).

## Порядок инкрементов и критерии перехода

| № | Инкремент | Зависит от | Готовность для следующего шага |
|---|---|---|---|
| 1 | Модель РО WMS, связи с РО 1С, план по документам, схема БД; сохранение легаси истории | Существующая проекция источника | Два источника одного склада образуют одну сборку; один источник нельзя одновременно привязать дважды. Миграцию создаёт разработчик, агент проверяет её. |
| 2 | Атомарная доступность: резерв группы, удержание ячейки, блок недостачи, совместимое датированное проведение и защита затрагиваемых действующих операций | 1 и существующие остатки/движения | Ни два новых Отбора, ни действующее Перемещение/Инвентаризация не используют зарезервированный или удерживаемый товар; повтор команды не удваивает факт/движение. |
| 3 | Исполнители формирования и начала, перенос GET/PATCH/POST адаптера 1С в Wms.Integration | 1 | Частичный перевод источников в `КОтбору` виден и безопасно повторяется; начатый план не меняется от нового уведомления. |
| 4 | Маршрут, список SKU, предложения Подпитки и подтверждение Отбора/возврата | 2–3 | FEFO и адресный маршрут предлагают ячейки; произвольный допустимый скан сохраняет резерв; недостача явно блокирует группу. |
| 5 | Задание Подпитки с удержанием, датированным переносом и возвратом поддона | 2, 4 | После подтверждения цели товар доступен Отбору, а источник удержан до завершающего скана; прерывание и повтор не проводят перенос второй раз. |
| 6 | Web решение недостачи, изменение плана и распределение факта по РО 1С | 3–5 | Руководитель видит три состояния, может изменить план, исправить остаток отдельным движением и вручную распределить недобор общего SKU. |
| 7 | Атомарное «Закрыть и отгрузить» и независимый обмен по документу | 2–6 | Одно списание датированных групп, нулевой документ допустим, ошибка одного PATCH/POST не трогает склад и другой РО. Закрытие запрещено при недоступном/жёстко изменённом источнике. |
| 8 | Отмена незакрытой сборки и возврат статусов 1С | 4–7 | Факт и резервы равны нулю после сканов возврата; начатая Подпитка завершена; обратный обмен виден и повторяем. |
| 9 | Новые экраны Mobile/Web и API, удаление легаси маршрутов и регистраций | 1–8 | Пользователь проходит оба рабочих места и Web разбор через новые команды. Старый путь проведения недоступен; исторические записи читаемы. |

Инкременты описывают техническую зависимость и проверяемый результат, а не требуют нескольких одновременно действующих складских сценариев. До включения новых экранов проверить незавершённые легаси РО и черновые движения и завершить их прежним порядком. Если это невозможно, переключение откладывается до отдельного решения по переносу конкретных операций; скрытой конвертации черновиков нет. Не удалять исторические движения и обороты; не оставлять активными две команды проведения для одного физического события.

Декомпозиция по сценариям, файлам и зависимостям приведена в [tasks.md](tasks.md). Инкременты плана связаны с задачами через таблицу покрытия требований и критерии готовности сценариев.

## Проверки перед включением

- Конкурентное подтверждение двух Отборов за одну группу, параллельный Отбор и Подпитка, попытка действующего Перемещения/Инвентаризации использовать резерв или занятую ячейку, конфликт удержания источника, потеря ответа после проведения и повтор той же команды. Эти риски покрыть целевыми автоматическими тестами, если текущие тесты их не защищают.
- На реальной 1С проверить прямой переход `КОтбору` → `Отгружен`, документ со всеми строками `НеОтгружать`, отказ при ограничении документа-основания, восстановление после частичного PATCH/POST и последовательное заполнение нескольких строк одного SKU. Результат не должен менять уже проведённый складской факт.
- Разработчик выполняет сборку, тесты, создание/применение миграции и ручную проверку экранов ТСД/Web по [quickstart.md](quickstart.md); агент изучает результат и миграцию перед продолжением.

**Выбор структуры**: существующие проекты и направление зависимостей; нового проекта нет. Домен задаёт локальные правила, Application решает команды, Infrastructure сохраняет их одним изменением БД, Integration общается с 1С. Для выбранной ячейки и документа код идёт через именованную команду/исполнитель, а не через общий настраиваемый процесс.
