# План: приемка и остатки при изменяемом плане 1С

**Дата**: 2026-10-14

**Статус**: Draft; технический проект уточняется после открытых вопросов в
[спецификации](spec.md).

**Источник требований**: [spec.md](spec.md).

## Summary

Отделить зеркало документов 1С от ордера WMS. Закрытие приемной LPN станет
единственной точкой проведения прихода. Остатки и движения получат дату срока
годности. Изменение плана 1С не изменяет проведенный факт. Менеджерские
исправления создают новые движения, а действия и версии источников остаются в
истории. Эта архитектура пока является целью, а не описанием действующего кода.

## Technical Context

- .NET 10; старые прикладные сценарии находятся в `Wms`, интерфейсы — в
  `Wms.WebApi` и `Wms.WebApp`; Domain вынесен в `Wms.Domain`, существующий EF —
  в `Wms.Infrastructure`. `Wms.Application` и `Wms.Integration` пока пустые.
- EF Core и SQL Server; миграции создает и применяет разработчик по точной
  команде после завершения изменений модели.
- Старые прикладные сервисы и адаптер 1С остаются в `Wms`; он использует
  `Wms.Infrastructure`. Новые проекты не ссылаются на легаси-сборку.
- Сейчас `ReceivingOrder.Id` равен `Ref_Key` единственного документа 1С, а
  строки WMS привязаны к его номерам строк; их идентичности предстоит разделить.
- `CommandExecutor` уже предоставляет идемпотентный прием команд и атомарную
  финальную запись в БД. Его необходимо сохранить.
- Регрессионные проверки нужны для повторного закрытия LPN, атомарного
  проведения, изменяемого плана и допустимых отрицательных корректировок.
  Запуск сборок и тестов принадлежит разработчику согласно `AGENTS.md`.

## Constitution Check

- Складской факт проводит WMS; 1С обновляет план, не переписывая движения.
- Для физической приемки остается одна точка проведения: закрытие LPN.
  Прежний вызов проведения при завершении ордера удаляется до использования
  нового сценария.
- Источник 1С сохраняется даже при невозможности построить оперативный план;
  известный ноль и неизвестное значение не смешиваются.
- Изменения баланса, обороты, аудит и квитанция команды сохраняются согласованно.
- Новая структура проектов вводится лишь в той мере, которая облегчает
  переписывание сценариев без циклических зависимостей.

## Project Structure

До переписывания приемки выделен `Wms.Domain`, созданные проекты
`Wms.Application` и `Wms.Integration` пока пустые. `Wms.Infrastructure`
содержит единый EF-контекст, конфигурации и прежнюю цепочку миграций.
Старый `Wms` сохраняет действующие процессы и адаптер 1С, используя
Infrastructure. Новые проекты не ссылаются на `Wms`.
Типы `WarehouseQuantity`, `OperationResult`, `OperationError` и
`WeightCalculation` находятся рядом с моделями Domain; пространство имен
`Wms.Common` сохранено для существующих клиентов.

```text
Wms.Domain ← Wms.Application ← Wms.Infrastructure
                         └───── Wms.Integration

Wms.Domain ← Wms (старые Application, Integration.OneS) → Wms.Infrastructure
                      ↑
               Wms.WebApi / Wms.WebApp

Wms.Mobile → Wms.Contracts ← Wms.WebApi
```

Стрелки направлены к проекту, от которого зависит другой проект. По мере
замены сценариев WebApi и WebApp смогут подключать новые сборки как точки
композиции. Мобильный клиент использует транспортные контракты.

Новые сценарии в `Wms.Application` предлагается оформлять в формате `static class`
с вложенными `Command`/`Query`, `Handler` и `Result`, по образцу Myrmex.
Существующий `CommandExecutor` остается в легаси `Wms` до замены вызывающих
его процессов. При создании новых сценариев механизм идемпотентности и
атомарной записи нужно перенести или адаптировать без ссылки Application на
`Wms`. Контракты доступа к данным определить вместе с первыми новыми
сценариями; их EF-реализация будет принадлежать Infrastructure.

Новые процессы могут писаться рядом со старыми во время разработки. Перед
использованием новых маршрутов, экранов и команд старые вызываемые пути
приемки, включая проведение при завершении ордера, убираются. Два способа
изменить один складской факт одновременно не выпускаются.

## Current-to-target map

| Участок | Текущее допущение | Целевой результат |
|---|---|---|
| `ReceivingOrderItem`, `ReceivingOrderSynchronizationComparer`, `ReceivingCompletionComparer` | Строка определяется номером строки 1С; измененный состав блокирует работу; после начала локальный план защищен. | Устойчивый список SKU ордера, текущий план из 1С, независимый факт, версии исходного плана. Удаление строки 1С не удаляет принятый SKU. |
| `ReceivingOrder`, `ReceivingOrderCommandService` | Завершение хранится одним набором полей и проводит приход по агрегированному факту. | История циклов; приход проводится при закрытии палеты, завершение ордера не создает движений. |
| `LicensePlateNumber`, `LicensePlateNumberService` | Закрытую палету можно возобновить; у нее может быть несколько SKU. | Один SKU и одна дата на приемной LPN; после проведения только исправление или логическое удаление с аудитом. |
| `LicensePlateNumberPutawayService` | Размещение ждет завершения ордера; остаток палеты считается из исходной строки и размещений. | Размещение после проведения палеты; оставшееся количество учитывает корректировки. |
| Справочник SKU и Web | Локального признака срока нет; импорт каталога перезаписывает данные. | Локальный признак меняет менеджер; импорт 1С его сохраняет. |
| `InventoryBalance`, `InventoryMovement`, `InventoryTurnover`, `InventoryPostingService` | Ключ остатка — склад, ячейка, SKU; остатки неотрицательны. | Дата входит в движения и остатки; менеджерская корректировка может создать отрицательный остаток. |
| Отбор, отгрузка, перемещения, остатки, отчеты | Количество SKU в ячейке — одна строка без даты. | Операции выбирают и переносят дату, включая неизвестную; FEFO для помеченного SKU. |
| Mobile/Web и контракты | Ввод только количества; сравниваются первоначальный и текущий планы; палета возобновляется. | Дата при приемке, актуальные план/факт, история и корректировки, новые действия по палете. Старые элементы удаляются. |

## Design dependencies before tasks

1. Выбрать правило распределения корректировки частично размещенной палеты и
   предел достоверности происхождения товара после смешивания в ячейке.
2. Решить правило закрытия LPN при промежуточном недоборе, превышении плана и
   недоступности 1С. Только после этого определять права и UI закрытия.
3. Уточнить склейку строк одного SKU, доступность исходного документа и
   операции при изменении его склада или состава.
4. Выбрать безопасное временное поведение инвентаризации для датированных
   остатков. Полный пересчет по датам остается в backlog.
5. Разделить изменения схемы и процессы на проверяемые инкременты без двух
   действующих точек проведения; для каждого инкремента определить миграции,
   необходимую защиту данных и минимальную проверку.

Текущий импорт уведомления не проверяет `Posted` при создании ордера, если
статус источника — «К приемке»; обычный Web-список при этом скрывает
непроведенные ордера. Разделение зеркала 1С и WMS-ордера должно устранить эту
двусмысленность. Время последней успешной сверки и ручная повторная сверка
нужны, поскольку доставка уведомлений не гарантирована.

## Complexity Tracking

`Wms.Domain` вынесен, EF перенесен в `Wms.Infrastructure`, а старые прикладные
сценарии и адаптер 1С пока остаются в `Wms`. До переключения новой приемки
нужно реализовать ее процессы и адаптеры в новых проектах и убрать старый
путь проведения.
