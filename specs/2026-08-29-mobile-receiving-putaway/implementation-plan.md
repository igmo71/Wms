# План реализации мобильной приёмки и размещения

Спецификация: [`spec.md`](spec.md)

## Принцип реализации

Расширить существующий `ReceivingOrder` и его черновые движения, не создавая
нового мобильного документа. Веб и mobile V1 API используют одни доменные
операции и application services. Изменяющие мобильные команды оборачиваются в
существующий `MobileCommandExecutor`; состояние WMS и receipt сохраняются
одним `ApplicationDbContext` и одним `SaveChangesAsync`.

Работу выполнять вертикальными этапами. После каждого этапа собирать
затронутые проекты; после изменения EF-модели проверять migration drift.

## Этап 1. Nullable-факт и общие правила приёмки

### Домен

Изменить `ReceivingOrderItem.FactQuantity` с `double` на `double?`.

- Новый и импортированный ордер получает `null` во всех строках.
- Добавить доменную операцию принятого сканирования: `null -> 1`, затем `+1`.
- Ручное изменение принимает конечное неотрицательное абсолютное значение,
  включая явный ноль.
- Расчёты веса, отклонения, полного факта и итогов должны явно учитывать
  `null`, а не незаметно превращать его в ноль.
- `ReceivingOrder.SetReceived` отклоняет завершение, пока существует хотя бы
  одна непроверенная строка.
- Создание приходных движений после завершения использует только уже
  подтверждённые значения и пропускает явные нули.
- После `Received` факты неизменяемы по существующему жизненному циклу.

Не добавлять отдельный `IsFactConfirmed`: nullable-значение уже выражает
нужное состояние и повторяет принятую модель инвентаризации.

### Persistence

Создать миграцию с nullable-колонкой факта.

- Очистить разработческую базу согласованным способом до применения новой
  обязательной модели; существующие документы и движения являются тестовыми.
- Не добавлять data migration для различения прежних нулей, переходные колонки
  или compatibility branches.
- Обновить model snapshot и проверить, что миграция не затрагивает посторонние
  таблицы.

### Веб-совместимость

Обновить страницы деталей и приёмки:

- показывать `Не проверено` для `null`;
- редактировать nullable-факт и позволять явно сохранить `0`;
- показывать число непроверенных строк;
- блокировать `Завершить`, пока хотя бы одна строка не подтверждена;
- сохранить существующее редактирование комментария и отклонений.

Обновить серверные list/detail расчёты и отчётные места, которые используют
`FactQuantity`, чтобы компилятор заставил обработать nullable-состояние явно.

### Проверка этапа

- Новый ордер содержит непроверенные строки.
- Первый скан устанавливает `1`, повторный — `2`.
- Ручной ввод сохраняет `0` и положительное дробное значение.
- Нельзя завершить ордер с `null`; можно завершить полностью подтверждённый
  нулевой ордер, и размещение остаётся `Inactive`.
- Веб-приёмка и существующая 1С-интеграция собираются и сохраняют прежние
  переходы.

## Этап 2. Штрихкод документа и read-модель мобильной очереди

### Декодирование

Добавить небольшой `OneSDocumentBarcodeCodec` для документов 1С, без общего
barcode framework. Он содержит только чистое преобразование GUID и десятичного
payload и переиспользуется приходными и будущими расходными мобильными
процессами. Поиск документа нужного типа остаётся в соответствующем query
feature.

- Принимать только непустую десятичную строку.
- Допускать ведущий ноль, которым 1С может дополнить нечётную длину payload, и
  нормализовать ведущие нули перед разбором.
- Разбирать её как неотрицательный `BigInteger`.
- Отклонять значение больше `2^128 - 1`.
- Переводить в 32 hexadecimal-знака и разбирать как GUID.
- Проверять обратное преобразование нормализованного значения, чтобы не
  принимать недесятичный мусор.
- Не встраивать scanner prefix/suffix в алгоритм документа: нормализовать
  только тот payload, который фактически отдаёт общий scanner pipeline.

Контрольный round-trip:

```text
656c7b25-38a1-11f1-bac9-00155d01200c
<->
134815293320347409076716541911719026700
```

### Queries

Расширить receiving query feature прямыми read-моделями для мобильного API:

- очередь приёмки выбранного склада;
- очередь размещения выбранного склада;
- детали ордера со строками, фактами и прогрессом;
- черновые движения и прогресс размещения;
- разрешение document payload в ордер выбранного склада;
- разрешение SKU barcode в одну или несколько строк текущего ордера;
- поиск не более десяти строк текущего ордера по товару, коду или штрихкоду.

Не возвращать EF entities в contracts. Сортировку очереди сделать явной и
стабильной: приоритет 1С, дата, номер/идентификатор как последний ключ.

### Проверка этапа

- Контрольная числовая строка возвращает указанный `Ref_Key`.
- Отрицательное, недесятичное, переполненное и несуществующее значение даёт
  понятную ошибку.
- Документ другого склада и завершённый документ не открываются как активная
  работа.
- Одинаковый SKU на нескольких строках возвращает несколько кандидатов, не
  выбирая строку автоматически.

## Этап 3. Staged application operations и идемпотентность

### Общие command services

Сохранить публичные методы `ReceivingOrderCommandService` и
`PutawayCommandService` для веба, но вынести изменяющую работу в конкретные
internal `Stage...Async` методы с caller-owned `ApplicationDbContext` и без
`SaveChangesAsync`:

- начать приёмку вместе с установкой позиции;
- увеличить факт выбранной строки на единицу;
- установить абсолютный факт строки;
- завершить приёмку;
- начать размещение;
- добавить черновое движение;
- удалить черновое движение;
- завершить размещение.

Публичный веб-метод создаёт context, вызывает stage и сохраняет. Мобильная
обёртка вызывает тот же stage через `MobileCommandExecutor`, добавляет receipt
и сохраняет один раз. Не переносить доменные проверки в endpoint.

Для начала приёмки объединить выбор позиции и переход в одну мобильную
операцию, чтобы локально не оставался ордер с наполовину выполненным стартом.

### Вызовы 1С

`StageStartReceivingAsync` и `StageCompleteReceivingAsync` выполняют
существующий целевой вызов 1С до локального сохранения и проверяют возвращённый
статус. Receipt не изображает распределённую транзакцию:

- при отказе 1С локальные изменения и receipt не сохраняются;
- при успехе 1С и локальном сбое retry повторяет тот же целевой переход;
- это поведение проверить на используемой 1С и включить в пилотную инструкцию
  восстановления.

### Mobile wrapper

Добавить `MobileReceivingOrderCommandService` со стабильными command types и
детерминированными request hashes. Хэш включает все бизнес-входы команды в
инвариантном формате, но не включает данные authenticated user повторно.

Результирующим resource id использовать:

- order id для переходов и изменения факта;
- movement id для добавления/удаления чернового размещения.

Повтор с тем же request id и телом возвращает прежний resource id; иное тело —
conflict. Клиент после повтора всегда перечитывает детали ордера, поэтому
receipt не хранит целый response snapshot.

### Конкурентность

Не вводить эксклюзивный захват ордера и новый универсальный lock. Каждая
команда загружает свежее состояние, а финальные переходы повторно валидируют
все строки, движения, остаток и позиции. Идемпотентность защищает повтор одной
мобильной команды; она не объявляется назначением документа сотруднику.

Если при реализации обнаружится конкретная потеря обновления между вебом и
мобильным клиентом, добавить узкую optimistic-concurrency защиту только
затронутой строке/агрегату и зафиксировать её в спецификации до расширения
схемы.

### Проверка этапа

Добавить focused automated coverage для границ, которые нельзя доказать одной
статической проверкой:

- duplicate scan request увеличивает факт один раз;
- duplicate add movement создаёт одно движение;
- reuse request id с другим количеством/строкой даёт conflict;
- business change и receipt не сохраняются частично;
- completion повторно проверяет nullable-факты и точное распределение;
- отказ posting/1С не оставляет локальный завершённый документ.

Использовать реальный EF provider или тестовую конфигурацию, которая сохраняет
уникальные ограничения и транзакционную семантику receipt; EF InMemory для
этих проверок не использовать.

## Этап 4. Mobile V1 contracts и endpoints

### Contracts

Расширить `Wms.Contracts/Mobile/V1/MobileApiContracts.cs`:

- route `ReceivingOrders`;
- mobile enums статуса приёмки и размещения;
- queue summary, order details, line, movement и progress responses;
- resolve document/SKU requests and responses;
- request contracts для start, scan `+1`, absolute quantity, completion,
  add/delete movement;
- `ClientRequestId` во всех changing requests.

Не принимать с клиента user id, склад документа, исходную позицию размещения,
лимит строки или разрешение обходить блокировку.

### Endpoints

Добавить `MobileReceivingOrderEndpoints` под
`/api/mobile/v1/receiving-orders`, защитить общей warehouse-operator policy и
зарегистрировать в `Wms.WebApi/Program.cs`.

Предлагаемый прямой набор:

```text
GET  /?warehouseId=...
POST /resolve-document
GET  /{orderId}
POST /{orderId}/start-receiving
POST /{orderId}/lines/resolve-sku
GET  /{orderId}/lines/search?query=...
POST /{orderId}/lines/{lineNumber}/scan
POST /{orderId}/lines/{lineNumber}/quantity
POST /{orderId}/complete-receiving
POST /{orderId}/start-putaway
POST /{orderId}/putaway-movements
POST /{orderId}/putaway-movements/{movementId}/delete
POST /{orderId}/complete-putaway
```

`GET /` возвращает обе активные очереди одним response, чтобы экран склада
обновлялся одним запросом. Resolve endpoints ничего не меняют. Changing
endpoints получают user id только из authenticated principal и используют
общий `MobileEndpointResults` для ошибок.

После успешной команды endpoint перечитывает детали и возвращает
детерминированное актуальное представление вместе с выделенным изменённым
line/movement id, когда это полезно UI.

### API client

Добавить в `Wms.Mobile/Services/MobileApiClient.cs` прямые методы для contracts.
Сохранить текущую обработку bearer refresh и `MobileApiException`; не вводить
второй HTTP abstraction.

### Проверка этапа

- OpenAPI содержит все новые routes и responses.
- Unauthorized/role checks совпадают с другими mobile endpoints.
- Ошибки неверного склада, barcode, статуса, lock и количества имеют русское
  понятное сообщение.
- Повтор changing HTTP request с тем же `ClientRequestId` не повторяет действие.

## Этап 5. Экран очереди и скан документа

Добавить на `MainPage` действие `Приёмка и размещение` и зарегистрировать новые
страницы в `MauiProgram`.

Создать `Pages/ReceivingOrders/ReceivingOrderPage`:

- выбор склада тем же прямым паттерном, что в текущих процессах;
- две явные вкладки/секции `Приёмка` и `Размещение`;
- карточки активных ордеров с компактным прогрессом;
- pull-to-refresh и обновление при возврате;
- scanner card над очередями для document barcode;
- автоматический embedded scanner / inline camera через существующий
  `IOperationalBarcodeScanner`;
- открытие нужного этапа после успешного resolve;
- очередь остаётся доступной при нечитаемом штрихкоде.

Карточки очередей и строк выводить обычным `BindableLayout` с общим
вертикальным скроллингом. Не добавлять `CollectionView`, виртуализацию,
переиспользование visual tree или собственную инфраструктуру списков.

Не добавлять mobile history, paging, assignment или background sync.

### Проверка этапа

- Числовая строка от реального Urovo TD50 совпадает с контрольным payload либо
  документируется фактический scanner prefix/suffix и его обработка общим
  scanner pipeline.
- Скан контрольного ордера открывает его на выбранном складе.
- Карточка другого склада/завершённого этапа не открывается ошибочно.
- Камера и аппаратный scanner не работают одновременно.

## Этап 6. Мобильная приёмка

Создать страницу деталей приёмки с одной рабочей карточкой и общим списком
строк.

### Start mode

- Показать реквизиты и план до начала.
- По кнопке `Начать приёмку` перейти к сканированию receiving location.
- Проверить адрес и явно подтвердить объединённую start-команду.
- При неопределённом ответе сохранять request id и разрешать только retry той
  же команды.

### Active receiving mode

- Всегда показывать позицию приёмки и прогресс проверенных строк.
- Скан SKU сначала выполняет read-only contextual resolve.
- Для единственной строки отправляет идемпотентный `+1`.
- Для нескольких одинаковых строк показывает явный выбор и лишь затем
  отправляет `+1`.
- Акцентировать обновлённую карточку и отметку `+1`, без программной прокрутки.
- Ручной поиск ограничить строками ордера; выбор открывает абсолютный ввод и не
  увеличивает факт.
- В карточке поддержать подтверждение/отмену ручного значения, включая `0`.
- Показывать `Не проверено`, план, факт и отклонение.

### Completion

- Основную кнопку расположить выше списка.
- Блокировать её при наличии `null`.
- Перед командой показать план, факт, нулевые и отклоняющиеся строки и позицию.
- После успеха вернуть в обновлённую очередь; положительный факт появляется во
  вкладке размещения.

Использовать существующий scanner lifecycle, reserved progress strip, обычный
`BindableLayout` и общий вертикальный scroll. Не добавлять виртуализацию и не
создавать общий базовый класс страниц только ради сходства с инвентаризацией.

## Этап 7. Мобильное размещение

Создать страницу размещения и отдельный простой последовательный экран нового
движения.

### Details

- Для `Pending` показать принятое количество и явное `Начать размещение`.
- Для `InProgress` показать общий прогресс и карточки положительных строк.
- Под строкой показывать destination address и quantity каждого черновика.
- Дать выбрать строку с остатком напрямую либо начать со сканирования SKU.
- Удаление черновика выполнять с подтверждением и новым `ClientRequestId`.
- Редактирование не добавлять.
- `Завершить` доступно только при точном полном распределении.

### Movement flow

Последовательность фиксирована:

1. SKU/line;
2. scan storage destination;
3. quantity, заранее равное остатку строки;
4. confirmation;
5. add draft movement and return to refreshed details.

Для разделения партии оператор уменьшает количество. Destination принимается
только физическим сканированием; ручной location search отсутствует. При
duplicate SKU строка выбирается явно.

Неопределённый changing response удерживает экран на confirmation и допускает
только retry того же request id. После успеха выделить новое движение в
обновлённой карточке без принудительной прокрутки.

### Completion

Показать итог по строкам, позициям и количеству, запросить подтверждение и
отправить идемпотентную команду. После успеха вернуть в очередь, где ордер уже
не отображается.

## Этап 8. Сквозная проверка и документация

### Сборка и данные

- `dotnet build Wms.slnx`.
- Пересоздать очищенную разработческую базу полным набором миграций и проверить
  новую схему без compatibility data migration.
- Проверить отсутствие незапланированного migration drift.
- Проверить mobile build для Android и запуск на Urovo TD50/контрольном
  смартфоне.

### Ручные сценарии

1. Выбор ордера очередью и document barcode.
2. Start с допустимой, чужой, неверно типизированной и заблокированной позицией
   приёмки.
3. SKU scan `null -> 1 -> 2`, ручной итог, явный ноль, duplicate order lines и
   неизвестный SKU.
4. Блокировка завершения при `null`, нулевой общий факт и приёмка с
   расхождением плана.
5. Повтор start/scan/set/complete после искусственно оборванного HTTP response.
6. Размещение одной строкой, деление по двум ячейкам, удаление ошибки и
   возобновление после перезапуска.
7. Отказ заблокированной/чужой destination и изменение доступности перед
   completion.
8. Совместное изменение через веб и мобильный клиент с корректным свежим
   результатом либо понятным конфликтом.
9. Успешное завершение и проверка movements, balances, turnovers, audit и
   статусов 1С/WMS.

### Завершение issue

После ручной приёмки:

- перенести lasting mobile receiving/putaway rules в
  `docs/PROJECT_CONTEXT.md`;
- записать незавершённые ограничения/восстановление 1С в `docs/ROADMAP.md`, если
  они остаются;
- отметить спецификацию `Frozen reference` в registry;
- удалить этот implementation plan, когда он перестанет быть полезен для
  текущей работы.
