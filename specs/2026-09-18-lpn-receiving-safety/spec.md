# Безопасная приёмка и восстановление команд LPN

Статус: **Active**. R1–R3 приняты. R4 реализован и ожидает проверки разработчиком.
После принятия R4 закрыть эту спецификацию; дополнительных инкрементов в ней нет.

## Результат и исходная точка

Сотрудники могут совместно принимать допустимый ордер независимо от текущей
готовности его пересчёта. Manager решает количественное расхождение без
присоединения к приёмке. Сетевой сбой и уход с Mobile-экрана не приводят к
непреднамеренному движению или утрате возможности повторить текущую команду.

Основание: статическое ревью I01–I08, код `9ea6620`, документация `368c59b`,
ветка `2026-09-14-lpn-development-planning`. Исходные выводы получены без запуска
сборок и тестов. Замороженная спецификация I01–I08 остаётся историей решений.
Текущие правила — в [PROJECT_CONTEXT](../../docs/PROJECT_CONTEXT.md), общие
правила команд — в [ARCHITECTURE](../../docs/ARCHITECTURE.md).

## Объём

Пять связанных дефектов: смешение допуска к участию с готовностью завершения;
требование участия для Manager-решения; проведение по отложенному скану;
необработанный HTTP timeout; потеря доступа к повтору после обновления экрана.

Сохраняются существующие команды, receipts, атомарное проведение, проверки
остатка LPN и физического остатка, свежая сверка с 1С и защита от гонок.
Новые слои, универсальный автомат процессов и переработка учёта не требуются.
Не входят E1/E5/E6/E7, поддержка offline, восстановление после перезапуска,
отмена проведённого размещения и удаление всего legacy-кода.

## Последовательность: один инкремент — одна задача

### R1. Отделить допуск к участию от готовности завершения

Затрагиваются `ReceivingCompletionComparer`,
`ReceivingOrderSynchronizationService`, `ReceivingOrderCommandService`,
`MobileReceivingOrderQueryService` и отображение оценок в Web/Mobile.

- Сохранить отдельный смысл оценки допустимости источника и оценки завершения.
  Непроверенная строка, неполный факт и открытый LPN блокируют завершение,
  но сами по себе не запрещают присоединение к допустимому ордеру.
- Не записывать локальную неготовность пересчёта в общий статус так, чтобы её
  интерпретировали как блокирующее изменение 1С. Не снимать настоящие блокировки
  источника и не игнорировать их целиком для ордера в работе.
- Согласовать очередь, открытие/скан ордера и серверный join. Проверка готовности
  завершения через GET не должна менять доступность участия.
- Сохранить предварительный checkpoint завершения и fingerprint источника плюс
  полного состава LPN. Разделение оценок не ослабляет проверку свежести решения.

Приёмка: при неизменном допустимом источнике второй сотрудник присоединяется
после GET/refresh с непроверенными и частично пересчитанными строками. Удалённый,
непроведённый документ, неподдерживаемые единицы и повтор SKU по-прежнему
блокируют участие; локальная неготовность по-прежнему блокирует завершение.

### R2. Разделить полномочия участника и Manager

Затрагиваются `ReceivingOrder.ValidateToSetReceived`,
`ReceivingOrderCommandService` и Web `ReceivingOrderPages/InProcess`.

- Убрать требование участия именно для решения Manager по расхождению; не
  создавать фиктивного `ReceivingOrderParticipant` и не приписывать Manager
  пересчёт чужих LPN.
- Право определяется на сервере по роли `Manager`, не по полю клиентского
  запроса. `Administrator` без роли `Manager` не получает это право автоматически.
- Точное обычное завершение остаётся действием участника. Решение Manager не
  обходит открытые LPN, непроверенные строки, блокирующее изменение источника,
  изменившийся fingerprint и обязательную причину расхождения.
- Сохранить пользователя решения и его причину в аудите, а также существующую
  атомарность прихода и безопасный повтор. Web должен показывать действие
  неучаствующему Manager при выполнении соответствующих условий.
- Согласовано: Manager указывает причину и сразу завершает ордер. Финальный
  статус, аудит решения, приход, остатки, обороты и receipt сохраняются атомарно.
  Отдельного предварительного согласования и последующего завершения участником
  нет; новый lifecycle решения и отдельное хранилище согласований не нужны.

Не расширять право до произвольного завершения любого ордера всеми управляющими
ролями. Текущая схема хранения достаточна для выбранного пути; миграция не
планируется, если реализация не выявит отдельной необходимости.

Приёмка: Manager, не входящий в участников, решает допустимое расхождение;
Operator и Administrator без роли Manager не могут выполнить то же действие.
Состав участников и авторство пересчёта не меняются. Изменение LPN или источника
после показа решения отклоняет устаревшую команду без прихода.

### R3. Обрабатывать timeout как неопределённый результат команды

Затрагиваются `MobileApiTransport` и обработчики ошибок приёмки/размещения.

- Различить timeout HTTP и явную отмену вызывающим кодом. Ни один из них не
  подтверждает, что отправленная серверу команда не выполнилась.
- Довести timeout до существующего пути восстановления без необработанного
  исключения из `async void`; сохранить исходный request id и входные данные.
- Не повторять команду автоматически и не создавать новый id при нажатии
  «Повторить». Не разрешать менять параметры, пока исход неизвестен.
- Изменение общего транспорта проверить на совместимость с остальными его
  потребителями, без отдельной переработки их бизнес-процессов.

Приёмка: timeout до получения результата и после успешного server commit не
закрывает приложение; явный повтор возвращает результат исходной команды.
Частичное размещение не создаёт второе движение/историю/оборот. Проверить также
существующие случаи HTTP 408, 5xx и нечитаемого успешного ответа.

### R4. Сохранить восстановление на живом экране и отсечь поздние сканы

Затрагиваются `ReceivingOrderReceivingProcess`, страницы ордера, LPN и ввода
количества, а также `LicensePlateNumberPutawayPage`.

- Pending-команда хранит неизменяемый исходный запрос. Отображаемое после
  refresh состояние не заменяет его fingerprint, количество или назначение.
- Дать явное действие повтора независимо от актуальных `CanClose`, `CanCancel`,
  статуса ордера и других условий запуска новой операции. После повтора receipt
  разрешает pending-состояние, затем экран применяет актуальные данные.
- Пока результат неизвестен, блокировать конфликтующие действия и изменения
  параметров. Учесть переходы между уже живыми экранами приёмки; не вводить
  долговременную очередь и не превращать процесс в общий singleton всех ордеров.
- Перед обработкой отложенного скана проверять актуальность экрана; отписка от
  события сама по себе не отменяет callback в очереди UI. Повторное появление
  экрана не должно оживлять скан из предыдущего периода его активности.
- Уход с экрана не считать отменой уже отправленной команды.

Приёмка: после потерянного ответа закрытия/отмены LPN и refresh повтор остаётся
доступен, даже если обычная кнопка действия уже не применима. Для завершения
ордера повтор использует исходный fingerprint после refresh. Поздний скан
назначения после ухода с экрана не создаёт движения. Обычный скан и повторное
открытие страниц продолжают работать.

## Проверка и завершение

Сборки и тесты запускает разработчик. Для каждого инкремента передать точные
команды только затронутых проектов и сфокусированных проверок; дождаться
результатов перед закрытием инкремента.

- R1: проверить цепочку check-completion → join на допустимом и блокированном
  источнике; по умолчанию ручная проверка через поддерживаемый API/Mobile.
  Не добавлять отдельную инфраструктуру тестов ради этого сценария.
- R2: расширить существующий SQL-тест
  `Completion_racing_lpn_change_rolls_back_and_repeat_does_not_receive_twice`
  случаем Manager вне участников, сохранив проверку гонки и однократного прихода.
  Проверки отказа в праве добавить в существующую фикстуру только в объёме риска
  несанкционированного прихода. Роли Web/Mobile проверить на реальных учётках.
- R3–R4: ручные проверки с контролируемой задержкой/потерей ответа и сканером.
  Если для транспортного риска возможен небольшой тест без MAUI-инфраструктуры,
  решить необходимость по testing policy при реализации; не добавлять наборы,
  дублирующие общие гарантии `CommandExecutor`.

Минимальные команды сборки по затронутым проектам:

```powershell
dotnet build Wms.WebApi/Wms.WebApi.csproj -nologo -v:minimal
dotnet build Wms.WebApp/Wms.WebApp.csproj -nologo -v:minimal
dotnet build Wms.Mobile/Wms.Mobile.csproj -nologo -v:minimal
```

Сфокусированная существующая проверка для R2 после её расширения:

```powershell
dotnet test Wms.Tests/Wms.Tests.csproj --filter "FullyQualifiedName~Completion_racing_lpn_change_rolls_back_and_repeat_does_not_receive_twice"
```

Это команды для будущих checkpoints, не требование запускать всё при планировании.
После принятия всех инкрементов обновить текущие документы, реестр и ROADMAP,
заморозить эту спецификацию. До этого не объявлять дефекты исправленными.

## Открытые вопросы

Блокирующих бизнес-вопросов нет. Транспорт проверяется в Wms.Tests через
подключение исходных platform-independent файлов без MAUI; ручная проверка
восстановления Mobile после серверного commit остаётся необходимой.
