# План реализации блокировки складских ячеек

План выполняется как один связный инкремент. Этапы определяют безопасный порядок
работы, а не отдельные частичные поставки оператору. Автоматизированные тесты не
создаются и не запускаются; проверка выполняется сборкой, проверкой модели EF и
ручными сценариями.

## 1. Доменная модель и хранение

- Добавить `StorageLocationLockOwnerType` с начальными значениями `Manual` и
  `InventoryCount`.
- Добавить активную сущность `StorageLocationLock` без отдельного идентификатора
  и без soft-delete.
- Зафиксировать инварианты сочетания владельца и `OwnerId`, обязательной причины,
  пользователя и времени.
- Добавить к `StorageLocation` операционную ревизию и доменную операцию её
  продвижения.
- Настроить ревизию как concurrency token, связь one-to-zero-or-one и
  каскадное удаление блокировки вместе с ячейкой только на уровне недостижимого
  для используемой позиции физического удаления.
- Добавить `DbSet`, EF-конфигурацию, централизованные технические имена и
  миграцию с обновлением snapshot.

Результат этапа: существующая база после миграции содержит ноль блокировок, а
каждая ячейка имеет начальную операционную ревизию.

## 2. Общие команды и запросы блокировки

- Добавить прямолинейный `StorageLocationLockCommandService` для ручного
  захвата и освобождения.
- Получать пользователя и время на серверной application boundary.
- При захвате проверять активность, `IsFolder`, существующую блокировку и
  продвигать ревизию в том же `ApplicationDbContext`.
- При ручном освобождении запрещать удаление документной блокировки и также
  продвигать ревизию.
- Расширить административный запрос топологии сведениями о текущей блокировке.
- Подготовить внутреннюю модель владельца, которую следующая спецификация
  инвентаризации сможет использовать без изменения wire-контрактов ручной
  команды.

Результат этапа: блокировка имеет единый серверный жизненный цикл, но ещё не
считается защищённой, пока общий posting не обновлён.

## 3. Окончательный запрет и конкурентная координация

- Загружать в `InventoryPostingService` все участвующие `StorageLocation`
  вместе с активными блокировками как tracked entities.
- Проверять ручные и документные блокировки до вызова `InventoryMovement.Post`.
- Для документной блокировки сопоставлять владельца с `RecorderType` и
  `RecorderId` движения; не принимать override от UI или HTTP-контракта.
- Продвигать ревизию каждой различной участвующей ячейки ровно один раз на
  серверную команду.
- Расширить `InventoryPersistenceConflictClassifier` конфликтом ревизии
  `StorageLocation` и известным ограничением таблицы блокировок.
- Во всех save boundary, проводящих движения, переводить этот известный
  concurrency conflict в `OperationResult.Conflict`:
  - `ReceivingOrderCommandService`;
  - `PutawayCommandService`;
  - `ShippingOrderCommandService`, включая компенсационный откат;
  - `Picking` на стадии окончательного проведения через shipping command;
  - `InventoryTransferCommandService` и мобильную receipt-обёртку;
  - `InventoryCountCommandService`.
- Не менять порядок сохранения движения, баланса, оборота и документа: одна
  операция по-прежнему фиксируется одним `SaveChangesAsync`.

Результат этапа: ни один существующий фактический путь изменения остатков не
обходит блокировку, а движение и конкурентный захват не могут оба сохраниться.

## 4. Раннее поведение существующих процессов

- Исключить заблокированные позиции из операционных списков назначения и
  доступных источников для размещения, отбора и перемещения.
- Не предлагать заблокированную транзитную позицию новому перемещению.
- Расширить контекстный resolver ячейки безопасным конфликтом с адресом и
  причиной вместо ответа «не найдено».
- Добавить ранние проверки в command services, создающие либо меняющие
  долгоживущие черновики.
- Не удалять существующие черновики автоматически, если их ячейка заблокирована
  позднее.
- Убедиться, что чтение остатков, истории и административной топологии остаётся
  доступным для заблокированной ячейки.

Результат этапа: оператор получает объяснение до финальной команды везде, где
это возможно, при сохранении общего posting guard как источника истины.

## 5. Ручное управление в веб-приложении

- Добавить компактное состояние блокировки в диалог свойств операционной
  ячейки.
- Для свободной ячейки показать обязательную причину и действие
  «Заблокировать».
- Для ручной блокировки показать причину, пользователя, время и действие
  «Разблокировать» с подтверждением.
- Для документной блокировки показать владельца без кнопки ручного снятия.
- Добавить различимый, но неброский индикатор к элементу дерева.
- После команды обновлять выбранную ячейку и дерево, не заставляя оператора
  вручную перезагружать страницу.
- Сохранить существующую авторизацию страницы ролью `Administrator`.

Результат этапа: администратор управляет фактическим состоянием ячейки из уже
знакомого экрана топологии.

## 6. Проверка цельного инкремента

- Собрать затронутые проекты и решение без запуска тестов.
- Проверить отсутствие незапланированного model drift после новой миграции.
- Вручную проверить:
  - блокировку и разблокировку пустой и непустой ячейки;
  - запрет повторной блокировки;
  - отказ для папки и неактивной позиции;
  - видимость причины в вебе и мобильном сканировании;
  - запрет каждого существующего вида проведения с источником и назначением;
  - отсутствие частичных изменений в пакетной команде;
  - сохранение черновика при последующей блокировке его ячейки;
  - успешность прежних операций после разблокировки;
  - две параллельные ручные блокировки;
  - конкурентные блокировку и прямое перемещение одной ячейки.
- Проверить `git diff --check` и убедиться, что изменения не затрагивают
  незаблокированные бизнес-правила документов.

## 7. Завершение задачи

- После ручной приёмки перенести реализованное общее правило в
  `docs/PROJECT_CONTEXT.md` и инженерную конкурентную конвенцию в
  `docs/ARCHITECTURE.md`.
- Удалить завершённую работу из `docs/ROADMAP.md`, заморозить спецификацию и
  остановить её дальнейшее расширение.
- Создать следующую активную спецификацию поячейковой инвентаризации, которая
  использует документное владение блокировками и приводит мобильный и веб-UI к
  одной серверной логике.
