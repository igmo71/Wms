# Мобильный контур WMS

## Статус и назначение

Статус: **Frozen reference**. Основание и первая мобильная вертикаль приняты
после ручной проверки на Urovo TD50 и контрольном Android-смартфоне.

Эта спецификация описывает эпик развития WMS для работы кладовщика с
мобильного устройства. Приоритетное устройство — промышленный Android-ТСД со
встроенным сканером штрихкодов. Обычный Android-смартфон с распознаванием кода
камерой является поддерживаемым запасным вариантом.

Мобильный контур не вводит отдельные складские бизнес-процессы. Он предоставляет
ориентированный на последовательное сканирование интерфейс к тем же операциям,
правилам остатков и аудиту, которые реализованы в серверной части WMS и доступны
в операторском веб-интерфейсе.

## Ожидаемый бизнес-результат

Кладовщик может выполнять физические складские действия непосредственно у
товара и ячейки, подтверждая контекст сканированием. Сервер WMS остается
единственным источником бизнес-правил и факта выполнения операции, а каждое
подтвержденное действие связывается с аутентифицированным пользователем.

## Принятые границы

- `Wms.Mobile` является Android-клиентом и не обращается непосредственно к базе
  данных, EF Core, application services или интеграции с 1С.
- Все мобильные операции выполняются через защищенный версионированный HTTP API
  в `Wms.WebApi`.
- `Wms.Contracts` содержит общие wire-контракты, используемые сервером и
  мобильным клиентом. Доменные сущности и платформенный код в него не входят.
- Сервер использует существующие application services и повторно проверяет все
  бизнес-условия независимо от проверок мобильного интерфейса.
- Первая версия работает только при доступном сервере. Offline-очередь
  складских команд не входит в начальный объем.
- Все изменяющие мобильные команды защищаются от повторного выполнения одним и
  тем же клиентским идентификатором запроса.
- Источники сканирования скрыты за общим мобильным интерфейсом. Операционный
  экран не зависит от производителя ТСД или от того, получен код встроенным
  сканером либо камерой.
- Первая прикладная вертикаль — внутрискладское перемещение, начиная с прямого
  перемещения между обычными ячейками.

## Последующие мобильные операции

После подтверждения платформы и первой вертикали предполагается адаптировать к
сканированию:

- приемку;
- размещение принятого товара;
- отбор и подготовку расходного ордера;
- отгрузку;
- инвентаризацию;
- продолжение и завершение перемещений через транзитную ячейку.

Порядок этих операций определяется после пилота первой вертикали. Их
существующие серверные бизнес-правила не меняются автоматически из-за появления
мобильного клиента.

## Не входит в текущий эпик

- iOS и альтернативные мобильные платформы;
- отдельная мобильная база данных с синхронизацией складских фактов;
- выполнение подтвержденных команд без ответа сервера;
- собственный универсальный workflow engine;
- изменение правил учета остатков ради мобильного интерфейса;
- привязка решения к Urovo или другому одному производителю;
- аутентификация одним только открытым идентификатором пользователя из бейджа;
- генерация или декодирование штрихкода документа 1С на мобильном клиенте.

## Критерии завершения эпика-основания

Основание мобильного контура считается подтвержденным, когда:

1. Пользователь входит с существующей учетной записью Identity, а сервер
   определяет его идентификатор из аутентифицированного запроса.
2. Мобильный клиент вызывает защищенный API через модели из `Wms.Contracts` и
   не ссылается на проект `Wms`.
3. На ТСД и смартфоне один диагностический экран получает одинаковую модель
   события сканирования из доступных источников.
4. Ячейка разрешается по WMS QR `WMSL:{storage-location-guid-N}`, SKU — по
   импортированному штрихкоду.
5. Повтор одного подтвержденного запроса не создает второе складское движение.
6. Прямое внутрискладское перемещение выполняется от сканирования исходной
   ячейки до подтвержденного сервером изменения остатков и оборотов.

## Открытые внешние зависимости

- Получить у команды 1С точный алгоритм представления `Ref_Key` в штрихкоде
  документа и контрольные примеры кодирования/декодирования.
- На реальных поддерживаемых ТСД определить broadcast actions, extras, режимы
  keyboard wedge и способ проверки доступности службы сканера.
- Отдельно выбрать безопасный сценарий входа по бейджу.
