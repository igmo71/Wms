# План реализации мобильного контура

Статус: активный план возобновленной разработки. Этап считается выполненным
только после указанного результата и проверки; наличие проектной заготовки не
закрывает этап.

План определяет последовательность проверяемых поставок. Каждый этап должен
закончиться работающим результатом и проверкой на устройстве; последующие
операции не должны начинаться поверх неподтвержденного сканерного или сетевого
основания.

## Этап 0. Обследование и фиксация внешних данных

- Получить алгоритм и контрольные штрихкоды документов от 1С.
- На Urovo TD50 зафиксировать доступные режимы broadcast/intent/keyboard wedge,
  action/extras, поведение аппаратных кнопок и настройки scanner service.
  Обнаружен ScanWedge Profiles с профилем Default: scanner input включен,
  keyboard output включен, output via intent доступен, но выключен. В developer
  options доступны отдельные значения Intent action и Intent string extra.
- Зафиксировать модель обычного смартфона для контрольной проверки камеры.
- Определить пилотный принтер и размер этикетки ячейки.
- Подтвердить использование существующего административного создания
  подтвержденных учетных записей без мобильной саморегистрации.

Результат: заполненные открытые вопросы, достаточные для foundation и
диагностического сканирования. Алгоритм документа 1С не блокирует первое прямое
перемещение, но блокирует мобильные операции с документами 1С.

## Этап 1. Контракты и защищенный API

- Удалить шаблонный тип из `Wms.Contracts` при появлении первых контрактов.
- Добавить ссылки на `Wms.Contracts` из `Wms.WebApi` и `Wms.Mobile`.
- Создать пространство имен `Wms.Contracts.Mobile.V1` и базовый маршрут API.
- Настроить Identity bearer authentication в `Wms.WebApi` без мобильной
  саморегистрации.
- Требовать существующую роль `Operator` или `Administrator` для мобильных
  складских операций.
- Реализовать login/refresh и `/me`.
- Получать user id из claims во всех новых мобильных командах.
- Реализовать единый API client, token handler и `ISecureStorage` session store
  в мобильном приложении.
- Согласовать problem responses и экран сетевых/сессионных ошибок.
- Выбрать и проверить механизм `ClientRequestId` на тестовой изменяющей команде.

Текущее состояние: общие identity-контракты, bearer login/refresh, защищенный
`/me`, получение автора из claims, secure session store и минимальный экран
входа реализованы. Вход, защищенный `/me` и сохранение сессии после полного
перезапуска проверены на Urovo TD50. До выхода из этапа остаются проверка
обновления токена на устройстве и атомарная идемпотентность первой изменяющей
команды.

Условие выхода: пользователь входит, перезапускает приложение, вызывает
защищенный `/me`, обновляет токен и не может подменить автора команды.

## Этап 2. Диагностическое сканирование

- Ввести общий интерфейс и нейтральную модель scan event.
- Реализовать жизненный цикл Android broadcast receiver.
- Добавить конфигурацию первого проверенного ТСД без vendor-зависимостей в
  операционных экранах.
- Проверить/при необходимости добавить keyboard wedge adapter.
- Выбрать camera library, добавить `CAMERA` permission и runtime flow.
- Реализовать определение доступности, предпочтительный источник, ручное
  переключение и диагностический экран.
- Проверить ведущие нули, повторные сканы, паузу/resume и аппаратные кнопки.

Текущее состояние: добавлены нейтральная модель события, keyboard wedge adapter
и первый диагностический экран. Получение кода через keyboard wedge проверено
на Urovo TD50. Добавлен Android broadcast receiver для документированных
значений профиля Urovo Default: action `android.intent.ACTION_DECODE_DATA`,
string extra `barcode_string`, symbology extra `barcodeType`. Intent mode без
экранной клавиатуры, сохранение ведущих нулей, повторные сканы, pause/resume и
обе аппаратные кнопки проверены на устройстве. Для камеры
выбран `BarcodeScanning.Native.Maui` поверх Google ML Kit; реализованы явное
включение на отдельном модальном экране, runtime permission и передача результата
в общую модель scan event. На Urovo TD50 подтверждены закрытие камеры без
остаточного preview, AimMode с центральным прицелом и получение одного выбранного
результата. Чтение камерой проверено на контрольном Android-смартфоне.

Условие выхода: один диагностический экран получает единый результат на Urovo
TD50 и контрольном смартфоне.

## Этап 3. QR ячеек и server resolvers

- Реализовать parser существующего доменного формата `WMSL:{guid-N}`.
- Добавить контекстные endpoints разрешения ячейки и SKU.
- Проверять существование, активность, склад и допустимый тип зоны.
- Создать единичный web preview/печать этикетки с человекочитаемыми полями.
- Напечатать и проверить этикетку на реальном оборудовании.
- После проверки определить отдельный объем массовой печати.

Текущее состояние: реализованы точный parser `WMSL:{guid-N}`, защищенные
контекстные endpoints разрешения активной операционной ячейки и SKU по точному
импортированному штрихкоду. Диагностический мобильный экран позволяет выбрать
контекст «Ячейка» или «Товар» и показывает найденный сервером объект. В web-
карточку рабочей ячейки добавлены единичный QR-preview и печать этикетки со
складом, зоной и крупным адресом. Оба resolver проверены на реальных данных и
устройствах. Остается напечатать этикетку на пилотном оборудовании; точная
геометрия отложена до выбора принтера и носителя.

Условие выхода: оба устройства устойчиво разрешают напечатанную ячейку и
существующий штрихкод SKU через сервер.

## Этап 4. Прямое внутрискладское перемещение

- Добавить mobile V1 query/command contracts для transfer.
- Реализовать защищенные endpoints поверх существующих
  `InventoryTransferQueryService` и `InventoryTransferCommandService`.
- Обеспечить атомарную идемпотентность direct movement и completion.
- Реализовать пошаговый экран сканирования и явное подтверждение.
- Добавить различимые состояния ожидания, успеха, бизнес-ошибки и сетевой
  неопределенности.
- Покрыть API интеграционными тестами, включая один `ClientRequestId`,
  параллельный дубль, конкурентные movement/completion, конкурирующие изменения
  остатка, недостаточный остаток и подмену пользователя.
- Выполнить ручной end-to-end сценарий на ТСД и смартфоне.

Текущее состояние: добавлена элементарная мобильная навигация. После входа
оператор выбирает отдельную страницу «Перемещение» либо техническую страницу
«Диагностика сканера». Страница перемещения показывает прямую последовательность
первого сценария. Добавлены read-only mobile V1 endpoints активных складов и
незавершенных перемещений; страница позволяет выбрать склад и показывает его
документы. Изменяющие команды еще не подключены.

Условие выхода: выполнены критерии этапа A из `inventory-transfer.md`.

## Этап 5. Перемещение через транзитную ячейку

- Добавить выбор и сканирование транзитной ячейки.
- Поддержать pick/put и свободное чередование действий.
- Показывать актуальный состав транзитной ячейки.
- Открывать активный transfer по транзитной ячейке либо предлагать создание,
  когда она свободна.
- Подтвердить эксклюзивность и запрет завершения с ненулевым остатком.

Условие выхода: существующие правила полной спецификации внутрискладского
перемещения доступны в мобильном workflow.

## Этап 6. Следующие процессы

На основании наблюдений пилота отдельно специфицировать порядок:

1. приемка;
2. размещение;
3. отбор/подготовка к отгрузке;
4. отгрузка;
5. инвентаризация.

Для операций с документами 1С до начала реализации должен быть принят и покрыт
контрольными примерами server-side decoder штрихкода документа.

## Отложенные отдельные эпики

- безопасный вход по бейджу и жизненный цикл бейджей;
- детальные разрешения и назначение складов операторам;
- массовая генерация/печать этикеток;
- управление парком устройств и удаленный отзыв сессии;
- offline-режим с формальной моделью конфликтов;
- расширение списка сертифицированных ТСД и профилей сканеров.
