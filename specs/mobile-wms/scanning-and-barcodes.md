# Сканирование, распознавание кодов и этикетки

## Цель

Операционные экраны получают одинаковое событие сканирования на промышленном
Android-ТСД и смартфоне, не зная производителя устройства и способ получения
кода. Считанное значение разрешается сервером в ожидаемом контексте операции.

## Термины

В коде и пользовательском интерфейсе используется нейтральный термин
«встроенный сканер». Термин «лазерный сканер» не используется как общий, потому
что допустимое оборудование может применять 1D/2D imager или другую технологию.

## Мобильная абстракция

Мобильный слой предоставляет общий контракт, условно `IBarcodeScanner`, и
нейтральный результат сканирования. Точные имена определяются при реализации,
но событие должно уметь передать:

- исходное строковое значение без преобразования в число;
- symbology, если источник ее сообщает;
- время получения;
- нейтральный вид источника: встроенный сканер, камера или keyboard wedge;
- технические данные, необходимые диагностике, без попадания vendor-specific
  типов в операционный экран.

Адаптер удаляет только транспортные символы, которые добавляет конкретный
сканер, например настроенный завершающий Enter. Значимые ведущие нули и регистр
payload сохраняются. Глобальное подавление одинаковых последовательных кодов не
применяется: повторное сканирование одного SKU может быть осмысленным действием,
и соответствующее правило задает текущий workflow.

## Источники

### Встроенный сканер Android-ТСД

Основной переносимый механизм — Android Intent/Broadcast. Однако action, extras,
настройка профиля и проверка доступности службы могут различаться между
производителями.

Vendor-specific сведения изолируются в адаптерах или декларативных профилях.
Они не появляются:

- в названии общего интерфейса;
- в операционных view models;
- в `Wms.Contracts`;
- в API и доменной модели;
- в пользовательских названиях режима работы.

Keyboard wedge поддерживается отдельным источником, когда устройство умеет
вводить считанный код как клавиатуру. Он требует явного управления фокусом и не
должен мешать ручному вводу.

### Камера

Камера является запасным источником на ТСД и обычным источником на смартфоне.
Приложение объявляет Android-разрешение `CAMERA`, запрашивает runtime permission
при первом фактическом использовании камеры и объясняет назначение разрешения.
Отказ в разрешении не блокирует встроенный сканер и ручной ввод.

Конкретная библиотека распознавания выбирается отдельным техническим решением
после проверки поддержки Android API 28, необходимых 1D/2D форматов, скорости и
условий лицензирования.

## Выбор доступного источника

Android не предоставляет единого системного признака наличия промышленного
сканера. Поэтому приложение не опирается только на производителя/модель и не
фиксирует выбор навсегда при первом запуске.

При запуске и возвращении приложения на передний план оно:

1. Проверяет доступность зарегистрированных аппаратных адаптеров и связанных
   служб/пакетов.
2. Проверяет наличие камеры; разрешение запрашивается только при ее выборе.
3. Выбирает доступный встроенный сканер источником по умолчанию.
4. Предоставляет явное переключение на камеру или ручной ввод.
5. Показывает понятную ошибку и предлагает альтернативу при отказе выбранного
   источника.

Диагностический экран до первой операции отображает обнаруженные источники,
активный источник, последние считанные значения и безопасные технические
сведения. Он необходим для обследования реального парка ТСД.

## Контекстное разрешение кодов

Сканер возвращает строку, но не определяет бизнес-сущность. Операция задает
ожидаемый контекст и вызывает соответствующий API resolver.

Примеры контекстов:

- `StorageLocation` — ожидается WMS QR ячейки;
- `StockKeepingUnit` — ожидается импортированный штрихкод SKU;
- `ReceivingOrder` или `ShippingOrder` — ожидается поддерживаемый штрихкод
  документа 1С;
- будущий `OperatorBadge` — ожидается credential бейджа, а не идентификатор
  складского объекта.

Resolver возвращает минимальную карточку найденного объекта или стабильную
ошибку: неверный формат, объект не найден, объект деактивирован, объект не
подходит текущему складу/документу либо код неоднозначен. Окончательное
бизнес-ограничение все равно проверяется command service при подтверждении.

Универсальный endpoint, который без контекста угадывает тип любого кода, не
входит в первую версию.

## Форматы

### SKU

Штрихкоды SKU импортируются из 1С и сохраняются строками. Мобильный клиент не
нормализует их как числа. Разрешение выполняется на сервере точным правилом,
согласованным с текущим каталогом `SkuBarcode`.

### Ячейка хранения

Первый собственный формат WMS:

```text
wms:location:v1:<storage-location-guid>
```

GUID записывается в каноническом формате `D`. Префикс отличает WMS-код от
внешних кодов, тип `location` задает назначение, версия оставляет возможность
эволюции формата. Идентификатор не является секретом.

QR формируется сервером или операторским web UI из существующего
`StorageLocation.Id`. Переименование ячейки не меняет payload, но требует
перепечатки этикетки, если изменился человекочитаемый текст.

Печатная этикетка содержит как минимум:

- QR достаточного физического размера и контраста;
- имя склада;
- имя зоны;
- имя ячейки крупным читаемым текстом.

Макет должен быть проверен печатью и сканированием на предполагаемом расстоянии,
а не только просмотром на экране. Массовая генерация PDF/листов этикеток является
отдельной поставкой после подтверждения единичного формата.

### Документ 1С

Мобильный клиент передает считанную строку серверу. Серверный decoder определяет
тип документа и `Ref_Key`, затем ищет локальный WMS-документ. Алгоритм и
контрольные примеры предоставляет команда 1С; WMS не изобретает альтернативное
кодирование, чтобы сохранить обратную совместимость с этикетками 1С.

Decoder должен допускать версионирование или несколько поддерживаемых форматов,
если это потребуется по результатам уточнения. До получения алгоритма
разрешение документов остается заблокированной частью roadmap.

### Бейдж пользователя

Namespace и формат бейджа не смешиваются с QR ячейки. Открытый
`ApplicationUser.Id` может помочь идентифицировать учетную запись, но не может
быть единственным аутентифицирующим credential. Правило определяется отдельной
спецификацией мобильного входа по бейджу.

## Критерии приемки

1. Одна view model принимает одинаковую модель scan event от встроенного
   сканера и камеры.
2. Операционный код не содержит проверки конкретного производителя ТСД.
3. На поддерживаемом ТСД приложение получает broadcast/keyboard scan без
   обязательного открытия камеры.
4. На смартфоне оператор может дать разрешение и считать поддерживаемый код
   камерой; отказ в разрешении обработан без аварии.
5. Пользователь может переключиться с автоматически выбранного источника.
6. Ведущие нули SKU сохраняются от сканера до server resolver.
7. QR ячейки разрешается только в контексте ячейки и возвращает существующую
   активную ячейку с ее складом и зоной.
8. Этикетка читаема человеком без сканирования и успешно проверена на реальном
   принтере и устройстве.
9. Диагностический экран позволяет обследовать новый тип ТСД без изменений в
   складской операции.
