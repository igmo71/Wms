# Мобильная платформа и HTTP API

## Цель

Создать минимальное общее основание, через которое `Wms.Mobile` безопасно и
предсказуемо вызывает существующие складские операции. Основание должно быть
достаточным для первой вертикали и не превращаться заранее в универсальную
интеграционную платформу.

## Граница проектов

```text
Wms.Mobile ---------+
                    +--> Wms.Contracts
Wms.WebApi ---------+
    |
    +--> Wms --> application services, domain, EF Core, 1C integration
```

`Wms.Mobile` и `Wms.WebApi` ссылаются на `Wms.Contracts`. Только серверная часть
ссылается на `Wms`.

### Содержимое `Wms.Contracts`

Допускаются:

- request/response records и классы;
- API-представления перечислений;
- контракты пагинации и прикладных ошибок;
- версия мобильного API и небольшие общие константы протокола, когда они
  действительно исключают расхождение клиента и сервера.

Не допускаются:

- EF Core и доменные сущности WMS;
- application services и бизнес-правила;
- MAUI, Android, ASP.NET middleware и типы конкретного сканера;
- секреты, адрес сервера и настройки окружения;
- утилиты, не относящиеся к wire-контракту.

Контракты первой версии располагаются в пространстве имен
`Wms.Contracts.Mobile.V1`. Базовый маршрут прикладного мобильного API —
`/api/mobile/v1`.

## Аутентификация

### Первая версия

- Используются существующие `ApplicationUser` и хранилище ASP.NET Core Identity.
- Пользователь входит по текущей паре email/пароль.
- Мобильный клиент получает access token и refresh token через token-based
  Identity flow; cookies для мобильного API не используются.
- Access и refresh token хранятся через MAUI `ISecureStorage`, а не в обычных
  preferences, файле или логах.
- Клиент обновляет истекающий access token. После окончательного отказа refresh
  он удаляет локальную сессию и возвращает пользователя на вход.
- Мобильный клиент не предоставляет самостоятельную регистрацию, изменение
  пароля и восстановление учетной записи в первой версии.
- Все прикладные мобильные endpoints требуют авторизацию, кроме явно
  перечисленных endpoints входа, обновления токена и технической проверки
  доступности.

Сервер получает `ApplicationUser.Id` из `ClaimsPrincipal` и сам передает его в
command service. Идентификатор пользователя не принимается от клиента как
автор команды. Это заменяет временный фиксированный user id в существующих
endpoint'ах.

Endpoint `GET /api/mobile/v1/me` возвращает минимальные сведения о текущей
сессии: идентификатор и отображаемое имя/email. Он используется для проверки
сессии и отображения текущего оператора.

### Будущий вход по бейджу

`ApplicationUser.Id` является открытым идентификатором, а не доказательством
личности. QR или штрихкод, содержащий только этот id, нельзя использовать как
единственный фактор входа.

Отдельная спецификация должна выбрать один из безопасных вариантов:

- бейдж идентифицирует пользователя, после чего оператор вводит PIN или пароль;
- бейдж содержит отдельный случайный, достаточно длинный, отзывной credential,
  связанный с пользователем; сервер хранит только безопасное представление
  credential и поддерживает перевыпуск;
- управляемое устройство предварительно привязывается к оператору, а бейдж
  участвует в дополнительном подтверждении.

До этого решения вход по бейджу находится в roadmap и не входит в foundation.

## Результаты API и ошибки

- Успешный ответ содержит только данные, необходимые текущему мобильному
  сценарию, а не сериализованную доменную сущность.
- Ошибки аутентификации возвращают `401`, недостатка прав — `403`, отсутствия
  ресурса — `404`, конфликта актуального состояния — `409`, ошибки запроса или
  бизнес-валидации — согласованный problem response.
- Сообщение для оператора не должно зависеть от разбора текста исключения.
  Контракт ошибки содержит стабильный машинный код и безопасное отображаемое
  сообщение.
- Внутренние исключения, SQL, stack trace и данные интеграции с 1С клиенту не
  возвращаются.

## Идемпотентность изменяющих команд

Каждая прикладная команда мобильного клиента, способная изменить данные,
содержит сгенерированный клиентом `ClientRequestId` (`Guid`). Для повторной
отправки одной физической команды используется то же значение.

Сервер обеспечивает следующие свойства:

- уникальность учитывает аутентифицированного пользователя и вид команды;
- одновременные запросы с одним id не выполняют действие дважды;
- повтор после успешного выполнения возвращает эквивалентный успешный результат;
- повтор с тем же id, но другим содержимым отклоняется как конфликт;
- запись результата выполняется атомарно с бизнес-изменением либо иным способом,
  исключающим повтор складского действия после неоднозначного сетевого сбоя.

Конкретная таблица, срок хранения ключей и общий middleware либо явная обработка
в командах выбираются до реализации первой изменяющей мобильной команды.

## Сетевое поведение

- Начальная версия online-only: подтверждение физического действия показывается
  только после успешного ответа сервера.
- GET-запросы могут безопасно повторяться после временного сетевого сбоя.
- Изменяющий запрос можно повторить автоматически только с тем же
  `ClientRequestId` и только после неоднозначной транспортной ошибки.
- Ошибки валидации, конфликты и отказ в доступе автоматически не повторяются.
- Клиент явно различает отсутствие связи, ожидание ответа, отказ сервера и
  успешное подтверждение.
- Считанный код может оставаться на текущем экране при кратком сбое, но не
  считается выполненной складской операцией.

Адрес API задается конфигурацией приложения/сборки. Производственное соединение
использует HTTPS с сертификатом, которому доверяет Android-устройство. Обход
проверки сертификата допускается только как локальный диагностический режим и
не входит в поставляемое приложение.

## Критерии приемки foundation

1. `Wms.Mobile` и `Wms.WebApi` используют один набор контрактов первой версии.
2. Мобильный проект не ссылается на `Wms` и не содержит копий серверных доменных
   сущностей.
3. Подтвержденный пользователь входит по email/паролю и сохраняет сессию между
   запусками без хранения пароля.
4. Истекший access token обновляется refresh token либо приводит к корректному
   завершению локальной сессии.
5. `/me` возвращает текущего пользователя; подмена user id в бизнес-запросе
   невозможна, потому что такого поля в контракте нет.
6. Защищенный endpoint без токена возвращает `401`, а не HTML-страницу входа.
7. Логи и сообщения об ошибках не раскрывают access token, refresh token или
   пароль.
8. Повтор тестовой изменяющей команды с одним `ClientRequestId` не создает
   второе изменение.

## Не входит в первую версию

- внешний OAuth/OIDC provider и SSO;
- JWT как обязательный формат токена;
- самостоятельная мобильная регистрация;
- вход по бейджу;
- роли, разрешения и ограничения пользователя по складам;
- offline-команды и последующая синхронизация;
- генерация API-клиента из OpenAPI до появления практической необходимости.
