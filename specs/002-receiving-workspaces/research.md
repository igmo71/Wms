# Research: решения для пространства приёмки

Исходные правила: [spec.md](spec.md), текущая [приёмка](../../.specify/memory/current/receiving.md) и [клиенты](../../.specify/memory/current/clients.md). Ниже решения для реализации, а не описание уже работающего интерфейса.

## Номер и фактическое время

**Решение**: хранить у `ReceivingOrder` обязательную строку `Number` длиной 13 символов и существующее `CreatedAtUtc` отдельно. Номер строить из локального времени WMS по принятому в других внутренних документах шаблону `yyMMdd-HHmmss`. Если кандидат занят, двигаться по одной секунде до первого свободного номера. Номер не меняется после создания, даже при другой временной зоне клиента или переводе часов.

**Причина**: внутренние перемещения и инвентаризации уже используют этот шаблон через `LocalDateTime`; фактическая дата не должна искажаться из-за коллизии. БД проверяет уникальность индексом. В существующей `Serializable` транзакции `ReceivingOrderStore.CreateCoreAsync` выделение номера защищается транзакционной SQL Server блокировкой `sp_getapplock` для одного ресурса «receiving-order-number»; после проверки источников и повторного `RequestId` номер записывается вместе с ордером, связями, receipt и аудитом. Уникальный индекс остаётся последней защитой. Неудачная команда не оставляет номера или частичного ордера.

**Альтернативы**: GUID в интерфейсе (нечитабелен); суффикс-счётчик (отклонён пользователем); только проверка занятости без синхронизации (гонка при двух запросах); глобальный номер из SQL sequence (не соответствует формату). Блокировка сериализует редкое создание ордера, что для текущего масштаба приемлемо.

Для новых номеров используется локальный часовой пояс среды WMS, как у других внутренних документов. Миграция не выполняет пересчёт времени.

## Миграция номера

**Решение**: поскольку при развёртывании таблица приходных ордеров пуста, миграция сразу добавляет обязательную колонку `Number`, уникальный индекс и проверку формата. SQL Server 12.x не поддерживает `AT TIME ZONE`, поэтому в миграции нет SQL для исторического заполнения. Миграция выполняется до приёма новых команд.

**Причина**: существующих ордеров для нумерации нет. Если они появятся в другой среде до применения миграции, для неё потребуется отдельное решение о переносе.

**Альтернативы**: заполнение исторических данных в миграции (лишнее для этой поставки); ленивое заполнение при чтении (временные пустые номера и гонки); вывод вычисляемого номера без хранения (изменчивость при совпадениях).

## Страницы и доступ Web

**Решение**: сохранить существующие GUID маршруты WMS `/receiving-orders` и `/receiving-orders/{id}`; добавить `/receiving-sources`. В `MudNavGroup` «Приёмка» поместить два `MudNavLink`. Вынести свободные/привязанные документы, поиск и создание ордера на страницу 1С; на WMS странице оставить только поиск и список ордеров. Стандартные `MudTable`, `MudDialog`, кнопки и сообщения заменяют постоянно открытую большую форму. Web-компоненты допускают просмотр Operator, но повторно проверяют Manager в серверных обработчиках действий создания, смены состава, сверки, корректировки/удаления LPN и управления циклом. Для канала Web менеджерское условие также проверяется внутри `ChangeReceivingOrderSources`; Mobile сохраняет существующие правила.

**Причина**: существующая `Index` смешивает документы и ордера, а `Details` содержит операции физической приёмки. Серверная проверка защищает вызов даже при обходе скрытой кнопки. Отдельного второго жизненного цикла не появляется.

**Альтернативы**: новый набор WMS маршрутов с редиректами (не нужен); второй полный экран редактирования источников (избыточен); постоянно раскрытая форма (перегружает карточку).

## Список документов 1С

**Решение**: выборка всех `ReceivingSourceDocument` с последней успешной версией и активной связью `ReceivingOrderSourceLink`, вместе с `ReceivingOrder.Number`. Она переиспользует `GetReceivingSources` для номера, даты, состояния, отправителя и плана; имена склада/партнёра/SKU разрешаются пакетно существующим `IReceivingReferenceNames`. Поиск по номеру или `Ref_Key`; свободные документы доступны для группового создания одного WMS ордера.

**Причина**: прежний `ListUnlinkedSourcesAsync` скрывает уже привязанные документы. Тип `StandardODATA.Catalog_Партнеры` остаётся техническим признаком ссылки на каталог партнёров 1С, а в интерфейсе показывается имя партнёра при наличии импорта.

**Альтернативы**: получать каждый связанный ордер отдельным запросом (N+1); показывать только свободные источники (не выполняет поиск связанного ордера).

## Предпросмотр изменения состава

**Решение**: диалог по кнопке «Изменить состав» открывает поиск и выбор одного источника для прикрепления или открепления. Предпросмотр возвращает выбранный документ, склад, пары «текущий план → новый план» только по изменившимся SKU, отдельные неизвестные значения, предупреждение о сохранении факта/движений и непрозрачный маркер состояния. Для прикрепления перед предпросмотром выполняется свежая сверка 1С; ошибка блокирует подтверждение. Расчёт нового плана использует ту же `ReceivingOrderPlanProjection.Sum`, что команда. При подтверждении команда ещё раз проверяет текущие версии/связи/ревизию и маркер внутри транзакции. Если за время просмотра источник, состав или ордер изменился, команда отказывает с просьбой повторить предпросмотр. Действующие ограничения склада, статуса и одновременной привязки остаются.

**Причина**: текстовый прогноз, вычисленный только в Razor, может устареть или разойтись с командой. Маркер подтверждает именно показанное решение и не меняет механизм проводки.

**Альтернативы**: расчёт в UI (дублирование бизнес-правил); подтверждение без защиты от устаревшего просмотра (менеджер мог бы подтвердить иное изменение); блокировка документа на время открытого диалога (долго держит ресурс).

## Mobile и проверка

**Решение**: в существующий Mobile V1 ответ ордера добавить строковый номер и `CreatedAtUtc`, сохранив `Id` как ключ команд/маршрутов; на экранах очередь/ордер показывать номер и локально форматированное фактическое время. Регрессионные проверки сосредоточить на уникальности при конкурентном создании, receipt replay, миграции пустой таблицы, устаревшем предпросмотре и отсутствии изменения факта/движений. Вёрстку и доступность действий проверить вручную под Manager и Operator.

**Причина**: Mobile V1 уже служит текущему клиенту; аддитивное поле не требует нового API. Правила физической приёмки остаются в Mobile.

**Альтернативы**: заменить GUID в API на номер (ломает существующие ссылки и команды); новые Mobile маршруты (дублируют действующие).
