# Quickstart: проверка разделённой приёмки

Этот сценарий выполняется **после реализации**. Согласно [AGENTS.md](../../AGENTS.md), команды сборки, тестов, запуска и EF выполняет разработчик; агент проверяет сообщённые результаты и созданную миграцию до её применения. Ожидаемые поля и действия приведены в [контракте](contracts/receiving-workspaces.md).

## Подготовка

1. Перед миграцией убедиться, что таблица `ReceivingOrders` пуста; миграция не переносит старые ордера. Проверить `SERVERPROPERTY('ProductVersion')` и `compatibility_level` целевой базы: для предполагаемого SQL Server 2014 ожидаются версия `12.x` и уровень `120`. После миграции подготовить хотя бы два документа 1С одного склада, включая свободный и привязанный, и WMS ордер. Для проверки истории создать ордер с закрытой LPN; для коррекции — закрытую LPN без размещения. Нужны учётные записи Manager и Operator.
2. Убедиться, что локальный часовой пояс работающего WMS соответствует принятому для внутренних документов: новые номера используют локальное время процесса. Миграция не преобразует временные метки.
3. Миграция `20261019152315_AddReceivingOrderNumber` создана командой EF и
   проверена агентом: обязательная колонка, уникальный индекс и проверка формата
   присутствуют; SQL, несовместимого с SQL Server 12.x, нет. Файл миграции
   вручную не исправляется. Применение — по действующему
   [runbook](../../.specify/runbooks/staging.md), разработчиком. Для выбранной
   тестовой базы:

   ```powershell
   dotnet ef database update --project Wms.Infrastructure/Wms.Infrastructure.csproj --startup-project Wms.WebApp/Wms.WebApp.csproj --connection "<test connection string>"
   ```

## Сборка и риск проверки

Разработчик запускает после реализации и миграции:

```powershell
dotnet build Wms.slnx -nologo -v:minimal
dotnet test Wms.Tests/Wms.Tests.csproj --filter "FullyQualifiedName~Receiving" -v:minimal
```

Ожидается, что проверены: миграция на пустой таблице создаёт обязательный уникальный номер; два создания в одну секунду дают разные номера и сохраняют фактическое время; повтор одного `RequestId` возвращает тот же ордер/номер; устаревший предпросмотр отклоняется; прикрепление/открепление меняет план, но не факт и движения. Остальные UI изменения проверяются вручную.

## Web вручную

1. Открыть группу «Приёмка»: должны быть два пункта. На «Документы 1С» найти свободный и привязанный документ по номеру и `Ref_Key`, увидеть их собственные номера, имена склада и отправителя, статус сверки, а у привязанного — номер WMS и ссылку. Под Manager создать ордер из двух свободных документов одного склада; под Operator создание недоступно.
2. На «Ордера WMS» найти созданный ордер по номеру. Проверить уникальный постоянный номер, отдельное фактическое время, склад, статус, число источников и расхождения. Открыть карточку; GUID остаётся лишь в маршруте/технических данных.
3. В карточке проверить краткий блок «Источники». Нажать «Изменить состав», прикрепить свободный документ и открепить связанный; до подтверждения увидеть склад, изменение плана и предупреждение о сохранении факта. В другом сеансе изменить источник между предпросмотром и подтверждением: Web должен попросить обновить предпросмотр. Ошибки другого склада и занятого источника объясняются явно.
4. Под Manager проверить ручную сверку, допустимую поправку и удаление закрытой LPN с её существующим предпросмотром, завершение/новый цикл. Под Operator действия менеджера недоступны. На карточке нет подбора фактического SKU, ввода открытой LPN, закрытия LPN и подтверждения нулевого факта. После изменения источников ранее проведённые LPN, факт и движения остаются прежними, новый план виден отдельно.

## Mobile вручную

1. В очереди и карточке связанного WMS ордера увидеть его номер и фактическое время; открыть тот же ордер по скану документа 1С. Сверить номер с Web.
2. Проверить, что создание ордера и физическая приёмка через Mobile сохраняют прежние действия и правила, команды используют прежний GUID, а повтор неопределённого ответа не создаёт второй ордер.
