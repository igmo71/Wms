# Implementation Plan: Разделение приёмки и нумерация ордеров WMS

**Branch**: `codex/002-receiving-workspaces` | **Date**: 2026-10-19 | **Spec**: [spec.md](spec.md)

## Summary

Добавить постоянный номер `yyMMdd-HHmmss` каждому приходному ордеру WMS, разделить Web на «Документы 1С» и «Ордера WMS», оставить физическую приёмку в Mobile и сосредоточить Web на просмотре и менеджерских решениях. Создание и привязка источников сохраняют действующие правила плана, факта и проводки. Технические решения и альтернативы описаны в [research.md](research.md).

## Technical Context

**Language/Version**: C# / .NET 10, Razor Components, XAML для .NET MAUI Android
**Primary Dependencies**: ASP.NET Core, MudBlazor 9, EF Core 10, SQL Server, .NET MAUI
**Storage**: существующая SQL Server БД (предположительно 12.x) через `ApplicationDbContext`; обязательная колонка и уникальный индекс ордера при пустой таблице
**Testing**: существующий xUnit/SQL Server LocalDB для рисков конкуренции, повторов и сохранения факта; ручные Web/Mobile сценарии разработчика
**Target Platform**: Web через `Wms.WebApp`, Android через `Wms.Mobile`, Mobile V1 через `Wms.WebApi`
**Project Type**: существующее многопроектное WMS решение
**Performance Goals**: списки не выполняют отдельный запрос на каждый документ или ордер; поиск по номеру и `Ref_Key` остаётся пригоден для обычного рабочего списка
**Constraints**: GUID и действующие ссылки сохраняются; номер неизменяем; 1C не получает новых исходящих вызовов; проводка прихода остаётся при закрытии LPN; Web не вводит фактическую приёмку
**Scale/Scope**: один тип WMS ордера, одна страница документов 1С, одна страница ордеров WMS и существующая карточка; Mobile получает дополнительное отображение номера/времени

## Implementation Approach

1. Добавить номер в `ReceivingOrder` и EF-конфигурацию. Миграция для пустой таблицы сразу создаёт обязательную колонку, уникальный индекс и проверку формата без исторического SQL. Разработчик создаёт/запускает миграцию, агент проверяет созданный файл до дальнейшей работы.
2. В существующей транзакции создания захватить транзакционную блокировку номера до чтений в `Serializable`, чтобы параллельные создания не удерживали конфликтующие блокировки диапазонов. После проверки receipt и источников определять свободное значение на основе локального времени фактического создания; при занятой секунде последовательно искать следующую. Уникальный индекс защищает от иных записей; повтор `RequestId` возвращает прежний ордер. Не смешивать номер с `CreatedAtUtc`.
3. Расширить read-модели ордера номером и временем; добавить выборку всех зеркальных документов 1С вместе с текущей связью. Переиспользовать сопоставление имён склада, отправителя и SKU, уже внесённое в рабочее дерево.
4. Разнести Web-страницы и навигацию. Страница документов показывает оба состояния связи и создание из свободных источников для Manager; страница ордеров содержит только WMS список. Карточка показывает номер и время, компактный блок источников и менеджерские действия; старые Web контролы приёмки и их обработчики удаляются.
5. Изменение состава источников оформить как открываемый по кнопке диалог: поиск свободного источника, предпросмотр затронутых SKU и подтверждение. Предпросмотр использует правила `ReceivingOrderPlanProjection` и возвращает маркер актуальности; команда сверяет его с состоянием в транзакции и сообщает о необходимости обновить предпросмотр при изменении исходных данных. Web Manager проверяется в обработчике команды для канала Web; правила Mobile остаются прежними.
6. Дополнить ответ Mobile V1 номером и временем без смены маршрутов и внутреннего GUID; обновить экран списка/карточки. Обновить `current/receiving.md`, `current/clients.md` и при необходимости `architecture.md` только вместе с реализованным изменением.
