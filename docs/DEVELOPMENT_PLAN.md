# Развитие WMS: адресация, LPN, приёмка и размещение

Статус: **проект для обсуждения**, 2026-09-14. Реализация не начата.
Обследование выполнено по исходному коду; сборки, SQL-проверки и работа на ТСД
в рамках планирования не выполнялись. Это карта изменений, не аудит всей системы.

Точка входа для эпика, который выполняется в нескольких задачах/чатах.
Текущее поведение описано в [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md),
инженерные правила — в [ARCHITECTURE.md](ARCHITECTURE.md),
активная спецификация выбирается через [реестр](../specs/README.md).
Наблюдения старой WMS служат источником бизнес-потребностей; её формы и внутренние
механизмы не являются требованиями к реализации.

## 1. Результат и границы

Сотрудники параллельно принимают один ордер через отдельные LPN. Завершение
приёмки оприходует товар. Другие сотрудники самостоятельно размещают LPN целиком
или извлекают из них товар, сохраняя происхождение, авторство и историю.
Система поддерживает принятую адресацию и ограничения хранения.

Базу разрешено пересоздать. Перенос старых документов, остатков, command receipts
и реестра этикеток не входит в работы. Это не отменяет поддержку физически
наклеенных адресных этикеток РЦ. В рамках этого плана база не очищается.
Этапы проверяются на воспроизводимо создаваемой чистой базе.

Сохраняем прямую архитектуру по бизнес-функциям, EF Core, общие application-команды
для Web/Mobile, CommandExecutor, атомарность, decimal(15,3), online-only и текущую
аутентификацию. LPN не требует новой платформы задач или универсального движка.

## 2. Согласованные исходные правила

| ID | Правило |
|---|---|
| B01 | Приёмка и размещение — самостоятельные процессы с отдельными входами на главном экране. |
| B02 | Остатки появляются только при завершении всего приходного ордера. Закрытый LPN до этого размещать нельзя. |
| B03 | Этикетки LPN печатаются заранее. Скан свободной этикетки в открытом ордере связывает LPN с ордером до первого SKU. «Сформировать паллет» закрывает его пересчёт. |
| B04 | Один ордер могут принимать несколько сотрудников через разные LPN. Multi-SKU LPN допустим. |
| B05 | Сохраняются родительский ордер, строки происхождения и авторство. Исторический факт приёмки не уменьшается при размещении/расформировании LPN. |
| B06 | В интерфейсе используются «С палетой» / «Без палеты». Рабочая модель: сохранить LPN при размещении целиком либо извлечь товар в обычный остаток. Частичное размещение необходимо. |
| B07 | Web-размещение — таблица LPN со статусом, сотрудником, ссылкой на ордер и детализацией SKU. Отдельный процент прогресса не требуется. |
| B08 | Адрес: область/помещение, ряд, секция, позиция, уровень. Пример QR: `1A01A1`, латинские буквы, без разделителей. Адреса могут повторяться на разных складах. |
| B09 | Физическое дерево, печатный адрес, функциональная зона и PickSequence — разные характеристики. Генерация и печать своих этикеток нужны наряду с использованием существующих. |
| B10 | Одна ячейка по умолчанию содержит один SKU; для отдельных ячеек разрешается несколько. Правило действует при любом поступлении, включая товар внутри LPN. Один SKU может лежать в нескольких ячейках. |
| B11 | Приёмка получает данные из 1С и сверяет актуальный документ перед завершением, но не меняет его в 1С. Расхождение плана и факта требует Manager с автором, временем и причиной подтверждения. Завершённый ордер имеет единый локальный статус завершения. |
| B12 | ТСД: полные названия, компактные строки, явный текущий LPN, сканирование как основной ввод; один SKU найден — сразу ввод количества, одно подтверждение — сохранение и возврат. |

B11 взято из предоставленного конспекта как целевое требование; точные правила
сверки и полномочия приведены ниже как ещё не принятые проектные решения.

## 4. Предлагаемая целевая модель (на обсуждение)

Имена сущностей ниже рабочие, не готовая схема таблиц.

- `ReceivingOrder`: локальный lifecycle, план источника и результат финальной
  сверки, ячейка приёмки, участники; без жизненного цикла размещения.
- `ReceivingOrderParticipant`: участие userId в ордере для «моих документов».
  Не эксклюзивное назначение и не основание приписать сотруднику весь факт.
- `LpnLabel`: выпущенный уникальный штрихкод и его привязка. Печать не создаёт
  складской остаток. Повторная печать не означает новое назначение.
- `LicensePlate`: номер/штрихкод, ордер происхождения, создатель, ответственный
  за пересчёт, закрытие и текущая позиция после оприходования.
- `ReceivingLpnItem`: строка ордера, SKU и принятое количество. После завершения
  ордера — сохраняемый факт; движение товара его не редактирует.
- `InventoryBalance`: текущая аналитика `(Warehouse, Location, SKU, LPN?)`.
  Loose и LPN складываются в общий остаток для обзора, но различаются при списании.
- `InventoryMovement`/`InventoryTurnover`: происхождение, источник и назначение
  с LPN-аналитикой, исполнитель и количество. Исходный LPN остаётся виден в
  истории извлечения даже при loose-остатке назначения.

Не хранить второй независимо изменяемый «текущий состав» рядом с остатками.
Если итог строки ордера материализуется, он производный и пересчитывается
в той же операции, а не редактируется напрямую.

Одно LPN находится в одном месте. «С палетой» перемещает весь оставшийся состав
атомарно. «Без палеты» извлекает выбранный SKU и количество, оставляя LPN с
остатком в исходной ячейке. После полного извлечения LPN остаётся в истории.
Прогресс первичного размещения нельзя вычислять из текущего остатка после
последующего отбора: использовать записи выполненного размещения.

Отдельный PutawayTask пока не обязателен. Вводить его только при принятой
потребности в назначении/очереди заданий; для текущего потока достаточно LPN
как рабочего объекта и записей размещения.

Для топологии предлагается дерево физических узлов внутри склада; функциональная
зона задаётся операционным ячейкам. Тогда один стеллаж может содержать Picking
и Reserve на разных уровнях. Не дублировать тип зоны вторым enum назначения.
Точный способ представления папок без функциональной зоны решается на этапе E1.
Первая схема адреса фиксирована под подтверждённые сегменты; универсальный
язык шаблонов не нужен. Сортировка маршрута остаётся отдельной настройкой.

## 5. Решения, которые нужно принять

Предложения не считать уже одобренными. ID сохраняются при обсуждении в других чатах.

| ID | Предложение для MVP | Когда решить |
|---|---|---|
| D01 | Количество — абсолютный итог SKU в текущем LPN. Повторное открытие показывает сохранённое значение. Скан сам количество не увеличивает. | До E3 |
| D02 | Один ответственный принимает LPN. Переоткрытие до завершения ордера разрешить ответственному и Manager с аудитом; передача ответственности явная. После завершения факты неизменяемы. | До E3 |
| D03 | Нулевой факт по отсутствующей строке ордера подтверждается отдельно; пустой LPN не нужен. Не считать отсутствие LPN автоматическим подтверждением проверки строки. | До E2/E3 |
| D04 | Излишек известного SKU допустим как факт и требует Manager на завершении. SKU вне плана пока блокировать до исправления документа в 1С; не вводить фиктивную связь со строкой. | До E2 |
| D05 | При изменении состава/нумерации строк 1С с уже заполненными LPN блокировать автоматическую замену. Нужен явный разбор с сохранением связей; нельзя тихо перепривязать по номеру строки. | До E2 |
| D06 | Manager имеет операции Operator плюс подтверждение расхождения. Administrator не получает бизнес-подтверждение неявно; выбрать матрицу с учётом одной роли аккаунта. | До E2 |
| D07 | Подтверждение Manager выполняет завершение на свежем плане/факте; изменение факта или источника требует новой сверки. Удалённый/недопустимый документ и недоступность 1С не обходятся разрешением на недостачу. | До E2 |
| D08 | Выбрать допустимые состояния источника при старте/завершении, правила обновления плана после старта и реакцию на поздние уведомления после локального завершения. Предложение: завершённый факт и статус не переписывать. | До E2 |
| D09 | Уникальность адресного QR внутри склада; рабочий склад известен до скана. LPN-штрихкоды предлагается делать глобально уникальными и не переиспользовать. Формат и размеры этикетки выбрать перед печатью. | До E1/E3 |
| D10 | Свободная этикетка назначается атомарно; занятая открывает существующий допустимый LPN, но не переносится в новый ордер. Пустой ошибочно созданный LPN можно отменить с сохранением следа, этикетку повторно не выдавать. | До E3 |
| D11 | Подтверждение размещения сразу проводит указанную часть. Ошибочное проведённое размещение исправляется обратным движением с проверкой текущего товара; scope коррекции согласовать до рабочего выпуска. | До E4 |
| D12 | Выбор источника в перемещениях/отборе учитывает LPN либо loose. Инвентаризация различает эти же части; суммарная разница по SKU не распределяется по LPN автоматически. | До E3/E4 |
| D13 | Из Reserve непосредственный отбор запрещён. Разделение типов зон вводить вместе с доступным способом подпитки; первую подпитку делать ручной задачей с запрошенным и фактическим количеством. | До E6 |
| D14 | Неизвестные вес/объём не равны нулю или бесконечной вместимости. В первом ранжировании явно отмечать непроверенную вместимость; решить, когда это предупреждение, а когда запрет. | До E5 |
| D15 | Первый участник задаёт ячейку приёмки, остальные используют её. Скан документа присоединяет сотрудника; неизвестный WMS документ не импортировать скрытно, показать отсутствие и путь синхронизации. | До E2/E3 |

Дополнительно до E3 определить выбор строки, если один SKU встречается в плане
несколько раз: скан SKU не гарантирует единственную строку ордера.
До E4 определить физическое движение между сканом источника и подтверждением
назначения: первая версия предлагает сразу подтвердить результат в назначении;
отдельный транзит размещения вводить только при принятой необходимости.

## 6. Этапы и зависимости

Каждый этап получает собственную датированную спецификацию перед реализацией.
Ни один из этапов ниже пока не начат. Этап — результат, не обязательно один чат/PR.

| Этап | Результат | Зависимости | Критерий завершения |
|---|---|---|---|
| E0 — план | Принята общая граница и порядок работ | Текущее обследование | Разрешены вопросы первого этапа; остальные имеют ID и этап решения. |

Удалены старые страницы и команды размещения ордера. |
| E5 — допустимость и рекомендации | Один SKU, проверка конкурентного поступления, простое ранжирование ячеек | E4, D14 | Недопустимый SKU отклоняется во всех путях поступления; рекомендации перепроверяются при проведении; неполные физические данные явно отражены. |
| E6 — отбор/резерв и подпитка | Типы зон и ручная задача подпитки с source/destination/SKU/requested/actual | E1, E4, D13 | Товар из резерва достигает отбора по задаче; direct picking из Reserve запрещён; остатки и фактическое количество корректны. |
| E7 — репетиция выпуска | Проверка полного процесса на Web и ТСД, актуальные документы и настройка чистой базы | E1–E6 | Сканеры/печать/сеть/права/отчёты и сквозные сценарии приняты, нет старых рабочих путей, обходящих LPN. |

E1 и E2 логически независимы, но выполнять последовательно для простоты проверки.
E3/E4 — один функциональный блок выпуска: E3 можно проверять командами и на тестовой
базе, но не выдавать пользователям новый LPN-остаток с несовместимым размещением.
Совместимость потребителей проектируется до изменения ключа, а реализуется в этом
блоке. Не маскировать её суммированием там, где операция обязана выбрать источник.
E5 включается до рабочего запуска ограничения «один SKU».
E6 может стать следующим самостоятельным выпуском: до него не активировать
запрет отбора из резерва без рабочего пополнения.

Корректность отчётов и плотный UX входят в соответствующие E3/E4, а не откладываются
на финальную косметику. Обновления Web, API и Mobile поставляются согласованно;
сохранение старых payload/hash с новым смыслом команд недопустимо. Выбрать явное
обновление контракта и отклонение старого клиента до E3, без лишнего периода
поддержки двух процессов при пересоздаваемой базе.

## 7. Критические проверки

1. Два пользователя назначают одну свободную этикетку: ровно один LPN и одно
   происхождение. Retry после потери ответа возвращает тот же результат.
2. Сотрудники независимо меняют разные LPN. Завершение ордера одновременно с
   новым LPN, изменением количества или переоткрытием не теряет факт и не
   оприходует несогласованный снимок. Общий барьер завершения необходим даже
   при отдельных ревизиях LPN; тестировать конфликт/retry, а не случайный last-write.
3. Закрытие LPN не создаёт остатков. Все LPN закрыты, все строки проверены,
   сверка выполнена — completion создаёт приход и receipt атомарно.
4. Manager подтверждает конкретное расхождение. Operator обойти проверку
   через прямой API не может; ошибка 1С не считается разрешённым расхождением.
5. Одновременно в ячейку идут разные SKU: при запрете multi-SKU проходит только
   допустимый результат, включая разные LPN и несколько движений одной команды.
6. SQL-уникальность нового ключа: одна loose-строка и по одной строке на LPN/SKU.
   Nullable LPN требует явной проверки поведения SQL Server filtered indexes,
   чтобы NULL не оставил loose-остатки без защиты от дубликатов.
7. Блокировки, папки, другой склад, недостаточный остаток и конкурентный перенос
   одного LPN отклоняются до успешного проведения; история не частичная.
8. Нет двойного подсчёта в балансах/отчётах; инвентаризация и компенсация отбора
   сохраняют выбранную аналитику. Историческая приёмка остаётся неизменной.

Сквозной сценарий: план 100 болтов + 20 гаек. A принимает LPN-1 с 40 болтами,
B — LPN-2 с 60 болтами и 20 гайками. После закрытия обоих остаток ещё нулевой.
Completion создаёт эти остатки в приёмке. LPN-1 размещают «С палетой».
Из LPN-2 извлекают 30 болтов «Без палеты», затем оставшиеся товары размещают
в допустимые ячейки. Приёмка сохраняет 100/20 и вклад A/B; размещение показывает
исполнителей своих операций. Повтор команды не удваивает ни факт, ни движение.
Затем проверить отбор, перемещение и инвентаризацию из полученных остатков.

Для изменённых этапов: подходящие существующие/новые сценарные тесты,
SQL LocalDB для ограничений и гонок, сборки затронутых проектов, проверка
создания схемы и migration drift; Web/ТСД-проверки для UI. Не заменять проверки
конкурентного SQL поведения in-memory provider. Сейчас эти проверки не запускались.

## 8. Что сохраняется за пределами этого эпика

Новый бизнес-процесс Shipping, универсальные связи LPN с любыми документами,
сложный slotting, оптимизатор маршрутов, классификация SKU из иерархии 1С,
автоматическая demand/min-stock подпитка и конверсия упаковок не входят в первый
выпуск. SkuStorageGroup — отдельное последующее решение после определения
источника классификации. В E5 первой версии: допустимые ячейки с тем же SKU,
затем пустые; предпочтительные группы появятся отдельным дополнением.

Существующие задачи [ROADMAP.md](ROADMAP.md) не отменены. Односторонняя приёмка
сократит область процедуры восстановления 1С, но отгрузка по-прежнему требует её.

## 9. Работа в нескольких чатах

Не удерживать эпик в одной переписке. У каждого этапа своя активная спецификация
и при необходимости несколько задач; одновременно активен один бизнес-результат.
План содержит связи этапов, спецификация — текущую работу, PROJECT_CONTEXT —
реализованные правила. Не копировать весь эпик в каждую спецификацию.

В начале задачи читать PROJECT_CONTEXT, реестр, этот план и выбранную активную
спецификацию. Предложения Dxx менять на «принято» только по явному решению,
с датой и коротким обоснованием здесь; не выводить согласие из молчания.
После этапа обновить текущие docs, статус этапа/ссылку на результат, заморозить
его спецификацию. В незавершённой спецификации оставить: сделано, проверки,
известные проблемы и конкретный следующий шаг. Отдельный бесконечный журнал
переписки не нужен.

Шаблон передачи следующей задаче:

> docs/PROJECT_CONTEXT.md и specs/README.md, затем активную спецификацию.
