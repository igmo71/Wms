# Развитие WMS: адресация, LPN, приёмка и размещение

Статус: **планирование завершено, 2026-09-15**. Реализация не начата.
Текущий результат подробно определён в [активной спецификации](../specs/2026-09-15-lpn-receiving-putaway/spec.md).
Этот документ сохраняет карту эпика; детали текущего процесса принадлежат спецификации.
Ближайший приоритет — демо приёмки и размещения через 2–3 дня (ориентир 17–18 сентября).
Это желаемый срок показа, а не подтверждённая оценка готовности.
Обследование выполнено по исходному коду; сборки, SQL-проверки и работа на ТСД
в рамках планирования не выполнялись. Это карта изменений, не аудит всей системы.

Точка входа для эпика, который выполняется в нескольких задачах/чатах.
Текущее поведение описано в [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md),
инженерные правила — в [ARCHITECTURE.md](ARCHITECTURE.md),
активная спецификация выбирается через [реестр](../specs/README.md).
Наблюдения старой WMS служат источником бизнес-потребностей; её формы и внутренние
механизмы не являются требованиями к реализации.

## 1. Результат и границы

Сотрудники параллельно принимают один ордер через отдельные LPN. Завершение
приёмки оприходует товар. Другие сотрудники самостоятельно размещают LPN целиком
или извлекают из них товар, сохраняя происхождение, авторство и историю.
Система поддерживает принятую адресацию и ограничения хранения.

Базу разрешено пересоздать. Перенос старых документов, остатков, command receipts
и реестра этикеток не входит в работы. Это не отменяет поддержку физически
наклеенных адресных этикеток РЦ. В рамках этого плана база не очищается.
Этапы проверяются на воспроизводимо создаваемой чистой базе.

Сохраняем прямую архитектуру по бизнес-функциям, EF Core, общие application-команды
для Web/Mobile, CommandExecutor, атомарность, decimal(15,3), online-only и текущую
аутентификацию. LPN не требует новой платформы задач или универсального движка.

## 2. Согласованные исходные правила

| ID | Правило |
|---|---|
| B01 | Приёмка и размещение — самостоятельные процессы с отдельными входами на главном экране. |
| B02 | Остатки появляются только при завершении всего приходного ордера. Закрытый LPN до этого размещать нельзя. |
| B03 | Этикетки LPN печатаются заранее. Скан свободной этикетки в открытом ордере связывает LPN с ордером до первого SKU. В старой системе «Сформировать паллет» закрывает пересчёт; в нашей кнопка «Завершить пересчёт LPN». |
| B04 | Один ордер могут принимать несколько сотрудников через разные LPN. Multi-SKU LPN допустим. |
| B05 | Сохраняются родительский ордер, строки происхождения и авторство. Приняли 100, разместили 40: принято остаётся 100, осталось разместить 60. |
| B06 | Единый поток: LPN → SKU → оставшееся количество по умолчанию → скан назначения сразу проводит движение. Переключатель «С палетой / Без палеты» исключён. Остаток назначения обычный, без LPN-аналитики. |
| B07 | Web-размещение — таблица LPN со статусом, сотрудником, ссылкой на ордер и детализацией SKU. Отдельный процент прогресса не требуется. |
| B08 | Адрес: область/помещение, ряд, секция, позиция, уровень. Пример QR: `1A01A1`, латинские буквы, без разделителей. На печати: `1 · A · 01 · A · 1`. Адреса могут повторяться на разных складах. |
| B09 | Физическое дерево, печатный адрес, функциональная зона и PickSequence — разные характеристики. Генерация и печать своих этикеток нужны наряду с использованием существующих. |
| B10 | Одна ячейка по умолчанию содержит один SKU; для отдельных ячеек разрешается несколько. Правило действует при любом поступлении, включая размещение всего состава LPN; включается на E5. Один SKU может лежать в нескольких ячейках. |
| B11 | Приёмка получает данные из 1С и сверяет актуальный документ перед завершением, но не меняет его в 1С. Расхождение плана и факта требует Manager с автором, временем и причиной подтверждения. Завершённый ордер имеет единый локальный статус завершения. |
| B12 | ТСД: полные названия, компактные строки, явный текущий LPN, сканирование как основной ввод; один SKU найден — сразу ввод количества, одно подтверждение — сохранение и возврат. |

Правила описывают целевое поведение. Общее согласие с D01–D15 получено
в обсуждении; D12 впоследствии заменено упрощением LPN. Нерешённые детали
и предлагаемые ограничения ближайшего демо отмечены отдельно ниже.

## 4. Принятая упрощённая модель

2026-09-15: LPN сопровождает приёмку и первоначальное размещение. После
размещения его этикетка показывает историю, но не гарантирует текущие состав
и местоположение физической палеты. Учет хранения по LPN не вводится.

Рабочие сущности:

- ReceivingOrder: локальный lifecycle, план и финальная сверка, ячейка приёмки.
- Участие сотрудника в ордере: несколько участников, собственные LPN.
- Выпущенная этикетка: уникальный штрихкод, привязка к LPN; печать не создаёт остаток.
- LicensePlate: ордер происхождения, создатель, ответственный, закрытие пересчёта.
- Состав приёмки LPN: строка ордера, SKU и принятое количество.
- Запись размещения: исходная строка LPN, количество, ячейка назначения,
  движение, пользователь и время; сохраняется атомарно с проведением.
- InventoryBalance: существующий ключ Warehouse + Location + SKU, без LPN.

Пример: A принял 40, B — 60. Итог ордера 100 рассчитывается из их LPN.
Исправляют конкретный LPN, а не независимо редактируют итог ордера.
Разместили 100, затем отобрали 30: принято 100, размещено 100, остаток ячейки 70.
Для определения оставшегося размещения используем принятое количество минус
записи размещения, а не текущий остаток целевой ячейки.

При завершении ордера обычный остаток появляется в ячейке приёмки. Каждое
размещение проверяет одновременно физический баланс источника и ещё не
размещённое количество выбранного LPN. Другой LPN не может использовать его
лимит, даже если общий SKU-баланс достаточен. Размещение выбранного SKU
подтверждается сканом ячейки; количество по умолчанию — всё неразмещённое.
До завершения ордера размещение запрещено.
В приёмке обычные операции не должны расходовать товар в обход записей размещения.

Свободная иерархия произвольной глубины сохраняется. РЦ — Warehouse.
Папки группируют ячейки и не обязаны иметь функциональную зону; операционная
ячейка относится к одной зоне своего склада. Тип зоны не дублируется.
Адрес независим от родительского пути. Пятисегментная адресация РЦ — схема
генерации и печати, а не обязательные уровни дерева всех складов.

Согласован пакетный генератор в выбранной папке: диапазоны сегментов,
предварительный просмотр, общая зона пакета, проверка уникальности внутри склада.
Автоматическое создание вложенных папок пока не требуется; ручные адреса допустимы.
PickSequence остаётся отдельным. Перенос между папками без смены адреса,
явная смена адреса с заменой этикетки и смена зоны пустой незаблокированной ячейки
без незавершённых операций согласованы по смыслу, но отложены на поздний этап.

## 5. Решения и оставшиеся уточнения

Направления D01–D15 в целом приняты пользователем 2026-09-14; D12 заменено
2026-09-15. Формулировки «выбрать», «определить» и ограничения демо остаются
незавершёнными деталями. ID сохраняются для работы в других чатах.

| ID | Решение / уточнение для MVP | Этап детализации |
|---|---|---|
| D01 | Количество — абсолютный итог SKU в текущем LPN. Повторное открытие показывает сохранённое значение. Скан сам количество не увеличивает. | До E3 |
| D02 | Один ответственный принимает LPN. Переоткрытие до завершения ордера разрешить ответственному и Manager с аудитом; один открытый LPN на ответственного в ордере; отдельный процесс передачи пока не нужен. После завершения факты неизменяемы. | До E3 |
| D03 | Ноль при вводе требует подтверждения отсутствия, если общий факт нулевой. Пустое поле не равно нулю. Удаление существующей строки LPN не подтверждает отсутствие по ордеру. Выбор отсутствующего SKU — «Добавить из ордера». | До E2/E3 |
| D04 | Излишек известного SKU допустим как факт и требует Manager на завершении. SKU вне плана пока блокировать до исправления документа в 1С; не вводить фиктивную связь со строкой. | До E2 |
| D05 | При изменении состава/нумерации строк 1С с уже заполненными LPN блокировать автоматическую замену. Нужен явный разбор с сохранением связей; нельзя тихо перепривязать по номеру строки. | До E2 |
| D06 | Manager имеет операции Operator плюс подтверждение расхождения. Administrator не получает бизнес-подтверждение неявно; существующая модель одной роли аккаунта сохраняется. | До E2 |
| D07 | Подтверждение Manager выполняет завершение на свежем плане/факте; изменение факта или источника требует новой сверки. Удалённый/недопустимый документ и недоступность 1С не обходятся разрешением на недостачу. | До E2 |
| D08 | Пометка удаления/распроведение и изменение состава блокируют завершение всем; количественное различие требует Manager. Недоступность 1С блокирует. Завершённый факт и локальный статус не переписываются уведомлением. | До E2 |
| D09 | Уникальность адресного QR внутри склада; рабочий склад известен до скана. LPN-штрихкоды глобально уникальны и не переиспользуются. Единый последовательный код LPN в интерфейсе, линейном штрихкоде и подписи; общая последовательность складов с защитой уникальности в БД. Для демо A4; длина кода и символика уточняются в I01, складской принтер позднее. | До E1/E3 |
| D10 | Свободная этикетка назначается атомарно; занятая открывает существующий допустимый LPN, но не переносится в новый ордер. Пустой ошибочно созданный LPN можно отменить с сохранением следа, этикетку повторно не выдавать. | До E3 |
| D11 | Скан назначения сразу проводит указанную часть. Закрепления LPN за размещающим нет. Коррекция ошибочного проведённого размещения — отдельное последующее решение; произвольное редактирование проведённой истории запрещено. | До E4 |
| D12 | Заменено: остатки хранятся по ячейке/SKU без LPN. Приёмка и записи размещения сохраняют происхождение; последующие операции используют существующие балансы. | До E3/E4 |
| D13 | Из Reserve непосредственный отбор запрещён. Разделение типов зон вводить вместе с доступным способом подпитки; первую подпитку делать ручной задачей с запрошенным и фактическим количеством. | До E6 |
| D14 | Неизвестные вес/объём не равны нулю или бесконечной вместимости. В первом ранжировании явно отмечать непроверенную вместимость; решить, когда это предупреждение, а когда запрет. | До E5 |
| D15 | Первый участник задаёт ячейку приёмки, остальные используют её. Скан документа присоединяет сотрудника; неизвестный WMS документ не импортировать скрытно, показать отсутствие и путь синхронизации. | До E2/E3 |

Последние уточнения включены в активную спецификацию: два экрана ордера,
личная/доступная очередь, один открытый LPN, ноль и удаление, SKU-дубликаты,
линейные этикетки, скан назначения и рекомендации. При дубликате SKU блокируется
начало с сообщением «SKU указан в нескольких строках», без указаний по исправлению.
Повтор pending-команды сохраняется только в живом экране. После перезапуска
читается серверное состояние, механизм восстановления команды отложен.

## 6. Ближайшее демо и этапы эпика

Приоритет пользователя от 2026-09-15: через 2–3 дня показать приёмку и размещение.
E1 больше не является условием начала E3. Демо использует существующие ячейки,
типы зон и QR WMS. Сохранение адресов старого РЦ остаётся целью следующего этапа.

### Объём текущей спецификации

- Реальные сохранения и движения на чистой демонстрационной базе.
- Две отдельные кнопки на ТСД: «Приёмка» и «Размещение».
- Открытие импортированного ордера, участие сотрудников, общая ячейка приёмки.
- Заранее подготовленные и напечатанные свободные этикетки LPN; минимальный
  выпуск этикеток без сложного редактора макетов.
- Скан LPN, SKU, абсолютное количество, одно подтверждение, закрытие пересчёта.
- Два сотрудника принимают разные LPN одного ордера без потери факта.
- Завершение ордера со свежей сверкой; приход ровно один раз, размещение доступно
  только после завершения. Приёмка не изменяет 1С, включая старт.
- Скан LPN, выбор SKU и количества, скан назначения как подтверждение;
  рекомендации: SKU есть сейчас, был в пустой ячейке, остальные допустимые пустые.
- Web: список LPN, статус, авторство, родительский ордер и детализация состава
  и размещений. Полный редактор приёмки Web можно выполнить после демо;
  старые изменяющие пути обязаны быть закрыты от обхода правил LPN.
- Проверка остатков и истории; запрет превышения количества LPN и общего баланса.

Сверка состава/количеств, запрет при удалении/распроведении и Manager-подтверждение
с причиной входят в текущую спецификацию. Основной показ дополнен веткой
количественного расхождения. Качество и понятность важнее календарного ориентира;
согласованный объём не урезается молча ради срока.

После демо: E1 целиком, изменение уже созданных ячеек, группы рекомендаций и вместимость,
ограничение одного SKU во всех операциях, подпитка, полный Web-ввод и расширенные
отчёты. Авторство в карточке LPN обязательно уже на демо. Старый отчёт выработки
не показывать как корректное распределение параллельной приёмки до его адаптации.
Удаление отката отбора не является задачей демо.

### Рабочая последовательность

Ближайшая реализация разделена на восемь инкрементов I01–I08:
этикетки → участие в ордере → создание LPN → пересчёт → завершение приёмки →
размещение → рекомендации → сквозная проверка. Их границы, зависимости и
критерии готовности ведутся в разделе 11
[активной спецификации](../specs/2026-09-15-lpn-receiving-putaway/spec.md).
Каждая часть включает необходимые команды, интерфейс и проверки; это заменяет
прежнюю последовательность «весь сервер, затем все экраны». Срок не гарантируется.
Историческая подсказка рекомендаций использует сохранённые нулевые остатки;
для неё не требуется запрос движений/оборотов.

Если срок сжимается, сокращать оформление, фильтры и редактирование Web.
Не сокращать защиту от повторного прихода, двойного размещения и гонки завершения.
До демонстрации отдельно проверить доступность 1С, сборку Android и физический ТСД;
их готовность пока не подтверждена обследованием кода.

## 7. Критические проверки

1. Два пользователя назначают одну свободную этикетку: ровно один LPN и одно
   происхождение. Retry после потери ответа возвращает тот же результат.
2. Сотрудники независимо меняют разные LPN. Завершение ордера одновременно с
   новым LPN, изменением количества или переоткрытием не теряет факт и не
   оприходует несогласованный снимок. Общий барьер завершения необходим даже
   при отдельных ревизиях LPN; тестировать конфликт/retry, а не случайный last-write.
3. Закрытие LPN не создаёт остатков. Все LPN закрыты, все строки проверены,
   сверка выполнена — completion создаёт приход и receipt атомарно.
4. Для текущего E2: Manager подтверждает конкретное расхождение. Operator обойти проверку
   через прямой API не может; ошибка 1С не считается разрешённым расхождением.
5. Для E5: одновременно в ячейку идут разные SKU: при запрете multi-SKU проходит только
   допустимый результат, включая разные LPN и несколько движений одной команды.
6. Ключ InventoryBalance не меняется. Проверить уникальность этикетки и
   лимит размещения LPN независимо от общего остатка: другой LPN того же SKU
   не позволяет повторно разместить уже израсходованное количество первого.
7. Блокировки, папки, другой склад, недостаточный остаток и конкурентный перенос
   одного LPN отклоняются до успешного проведения; история не частичная.
8. После размещения существующие отбор, перемещения и инвентаризация работают
   с обычными остатками. Принятое количество в истории остаётся неизменным.
   Приёмочные и размещённые количества не складываются как два складских остатка.

Сквозной сценарий: план 100 болтов + 20 гаек. A принимает LPN-1 с 40 болтами,
B — LPN-2 с 60 болтами и 20 гайками. После закрытия обоих остаток ещё нулевой.
Completion создаёт эти остатки в приёмке. Из LPN-1 размещают все 40 болтов.
Из LPN-2 размещают 30 болтов, затем оставшиеся товары размещают
в допустимые ячейки. Приёмка сохраняет 100/20 и вклад A/B; размещение показывает
исполнителей своих операций. Повтор команды не удваивает ни факт, ни движение.
Затем проверить отбор, перемещение и инвентаризацию из полученных остатков.

Для изменённых этапов: подходящие существующие/новые сценарные тесты,
SQL LocalDB для ограничений и гонок, сборки затронутых проектов, проверка
создания схемы и migration drift; Web/ТСД-проверки для UI. Не заменять проверки
конкурентного SQL поведения in-memory provider. Сейчас эти проверки не запускались.

## 8. Что сохраняется за пределами этого эпика

Новый бизнес-процесс Shipping, универсальные связи LPN с любыми документами,
сложный slotting, оптимизатор маршрутов, классификация SKU из иерархии 1С,
автоматическая demand/min-stock подпитка и конверсия упаковок не входят в первый
выпуск. SkuStorageGroup — отдельное последующее решение после определения
источника классификации. Уже в текущем размещении: ячейки с этим SKU сейчас, затем пустые с историей
этого SKU, затем остальные допустимые пустые. Группы — отдельное дополнение.

Существующие задачи [ROADMAP.md](ROADMAP.md) не отменены. Односторонняя приёмка
сократит область процедуры восстановления 1С, но отгрузка по-прежнему требует её.

## 9. Работа в нескольких чатах

Не удерживать эпик в одной переписке. У каждого этапа своя активная спецификация
и при необходимости несколько задач; одновременно активен один бизнес-результат.
План содержит связи этапов, спецификация — текущую работу, PROJECT_CONTEXT —
реализованные правила. Не копировать весь эпик в каждую спецификацию.

В начале задачи читать PROJECT_CONTEXT, реестр, этот план и выбранную активную
спецификацию. Предложения Dxx менять на «принято» только по явному решению,
с датой и коротким обоснованием здесь; не выводить согласие из молчания.
После этапа обновить текущие docs, статус этапа/ссылку на результат, заморозить
его спецификацию. В незавершённой спецификации оставить: сделано, проверки,
известные проблемы и конкретный следующий шаг. Отдельный бесконечный журнал
переписки не нужен.

Шаблон передачи следующей задаче:
